# 드롭 재고 점유 부하 테스트 보고서 (2026-11-17)

관련 이슈 #183. EXP-01 용량 측정 (`drop-reservation-step.js`, 대기열 없음).

## 결론

커넥션 풀을 10에서 20으로 늘리자 같은 부하에서 지연이 크게 줄었다. 원인은 DB 커넥션을 얻으려고 기다리는 시간이었다.

- 커넥션 획득 대기 평균: 416ms → 21~24ms
- 서버 측 재고 점유 처리 평균: 465ms → 51~53ms
- 200/s 단계 p95: 2,633ms → 149ms
- 풀 10은 225/s를 유지하지 못하고 중단했다. 풀 20은 250/s까지 계획 도착률을 유지했다 (248.5/s).
- 풀 20을 두 번 측정했고 (run3, run4) 결과가 거의 같았다.
- 모든 실행에서 드롭 불변식 (INV-01~09), 금액, FK 검사는 0이다. 초과 판매와 중복 주문은 없었다.

다음 한계는 250/s 근처다. 이 단계에서 p95가 758ms로 오른다. 핫 SKU 행 잠금 대기가 유력하지만 아직 확인하지 않았다.

## 단계별 지연 (k6, 클라이언트 측, ms)

같은 도착률 단계만 비교한다. run2의 첫 단계 150/s는 워밍업 없이 시작해 지연이 컸으므로 (중앙값 3,207ms) 비교에서 뺀다.

| 단계 | 풀 10 (run2) 중앙값 / p95 / p99 | 풀 20 (run4) 중앙값 / p95 / p99 | 풀 20 (run3, 근사) |
|---|---|---|---|
| 175/s | 29 / 240 / 452 | 22 / 46 / 294 | 24 / 46 |
| 200/s | 81 / 2,633 / 3,445 | 23 / 149 / 845 | 25 / 66 |
| 225/s | 실제 18/s에서 중단, 중앙값 1,929 | 24 / 138 / 599 | 27 / 84 |
| 250/s | 미도달 | 30 / 758 / 1,843 | 44 / 174 |

- run3 값은 10초 구간 스냅샷에서 추린 근사치다 (구간 중앙값과 구간 p95의 중앙값). run4와 같은 방식이 아니라서 참고용이다.
- run1(풀 10)도 200/s에서 p95가 337ms였다. run4의 149ms보다 높다.
- 지연에는 노트북과 EC2 사이 왕복 시간이 섞여 있다. 왕복 지연은 기록하지 못했다 (rtt.txt 비어 있음). 50/s 단계 중앙값 약 23ms가 왕복 지연을 포함한 기준선이다.

## 정합성

모든 실행 뒤 `verify capacity` 결과: 드롭 INV-01~09, 금액, 주문·결제 일관성, FK 고아 행 검사가 모두 0. `seed baseline: hot drop untouched` 하나만 실패했는데, 부하 뒤에는 실패하는 것이 정상이다. run4는 DB 예약 수 (216,159 - background 100,000 = 116,159)가 k6 성공 수와 정확히 같다.

## 한계

- 풀 10과 20의 이미지가 같은지 확인하지 못했다. run1, run2 태그가 기록되지 않았다.
- run2는 225/s에서 직접 중단했고, 첫 단계를 워밍업 없이 150/s로 시작했다. 풀 10의 225/s 이상 값은 없다.
- CPU 크레딧 모드가 실행마다 같은지 기록이 부족하다. run1은 실행 도중 무제한으로 바꿨다.
- EC2·RDS CPU, 메모리는 이 보고서에 넣지 않았다. CloudWatch에서 실행 시각대로 확인해야 한다.
- 왕복 지연을 재지 않았다.
