# ADR-0004. 요청 횟수 제한: 앱 안의 인터셉터로 시작

- 상태: IMPLEMENTED
- 날짜: 2026-11-20
- 관련: #271, PR #278, [공통 API 계약의 요청 횟수 제한](../contracts/api/common.md#요청-횟수-제한)

## 배경

로그인, 가입, 토큰 갱신, 대기열 진입과 상태 조회에 호출 횟수 제한이 없었다.
무차별 대입에 노출되고, 대기열 상태 조회는 호출마다 행 잠금과 heartbeat 쓰기를 해서 폭주하면 DB 쓰기 부하가 된다.
서버는 EC2 한 대에 Docker로 직접 띄우고 있고, 저장소에는 프록시 설정이 없다.

## 결정

1. 요청이 컨트롤러에 닿기 전에 Spring MVC 인터셉터가 횟수를 센다. 한도를 넘으면 429 `TOO_MANY_REQUESTS`와 `Retry-After`로 거절한다.
2. 센 값은 서버 메모리의 Caffeine 캐시에 둔다. 키마다 첫 요청부터 고정 길이의 창을 세는 고정 창 카운터다.
3. 키는 로그인, 가입, 갱신에는 접속 IP(`getRemoteAddr()`), 대기열 진입과 상태 조회에는 로그인 사용자 ID다. 위조할 수 있는 `X-Forwarded-For`는 쓰지 않는다.
4. 대상은 5개 경로뿐이다. 결제, 재고 점유, 취소, 조회 API는 제한하지 않는다.
5. 한도와 켜고 끄는 값은 `restless.ratelimit.*`로 바꾼다. perf 프로필과 일반 테스트에서는 끈다.
6. 캐시에 크기 상한과 만료를 둔다. 키를 바꿔 가며 보내는 공격으로 메모리가 늘지 않게 한다.
7. 시각은 주입된 `Clock`으로 얻고, 로그와 메트릭 태그에 IP나 사용자 ID를 넣지 않는다.

## 검토한 대안

| 대안 | 채택하지 않은 이유 |
|---|---|
| Nginx `limit_req` | 저장소에 Nginx 설정이 없어 구성부터 만들어야 한다. 로컬에서 검증하기 어렵고 IP 기준만 가능하다 |
| AWS WAF | EC2에는 직접 붙일 수 없어 ALB를 먼저 붙여야 한다. 추가 비용이라 예산 승인이 필요하다 |
| Redis 같은 공유 저장소 | 서버가 한 대라 필요하지 않다. 새 인프라가 늘어난다 |

## 결과와 한계

- 서버가 2대 이상이면 한도가 서버별로 나뉜다.
- 프록시나 ALB 뒤에 두면 모든 요청이 프록시 IP로 보여 전원이 함께 막힌다. 그때 신뢰할 프록시에 대한 전달 헤더 설정이 필요하다.
- 고정 창이라 창 경계에서 짧은 시간에 한도의 2배까지 들어올 수 있다.
- 키를 계속 바꾸는 공격은 캐시 퇴출로 카운터가 초기화될 수 있다. 한 키로는 한도가 지켜진다.
- 상태 조회는 heartbeat를 겸한다. 한도가 너무 빡빡하면 정상 사용자가 대기에서 이탈 처리된다. 프런트는 순번이 20 이내면 1초, 아니면 3초 간격으로 조회한다.
- 시작값은 제안값이다. 가입 분당 10회와 로그인 분당 20회는 같은 공유기를 쓰는 시연 환경에서 빡빡할 수 있다 ([열린 결정 사항](../product/open-questions.md)).
- 독립 검증이 `66ca50c`에서 PASS였다. 검증하지 못한 것은 IPv6 주소 정규화, 동기화 잠금 아래의 처리량, perf 프로필 기동과 k6다.

## 재검토 조건

- 서버를 2대 이상으로 늘릴 때
- 프록시나 ALB를 앞에 둘 때
- 정상 사용자가 한도에 걸리는 것이 관측될 때
