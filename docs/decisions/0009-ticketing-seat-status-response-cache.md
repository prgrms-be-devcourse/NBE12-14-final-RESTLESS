# ADR-0009. 좌석 상태 갱신 응답 압축과 0.5초 공유, 좌석도 분리는 보류

- 상태: DECIDED (#562). 티켓팅 담당(백엔드·프런트) 결정
- 날짜: 2026-11-28
- 관련: [ADR-0008 좌석 조회 응답 0.5초 공유](0008-ticketing-seat-response-cache.md)(범위를 `/seats/status`로 넓힌다), [티켓팅 API 계약 좌석 상태 갱신](../contracts/api/ticketing.md#좌석-상태-갱신), [공연장·배치 정합성](../domains/ticketing/venue-consistency.md), [ADR-0004 요청 수 제한](0004-request-rate-limit.md)

## 배경

팀 리뷰에서 F5 반복 상황을 위해 좌석도(배치·등급·가격)와 상태 응답을 나누고, 좌석도는 브라우저 캐시를 쓰자는 제안이 나왔다. 들어온 뒤 좌석이 풀리길 기다리며 화면을 계속 새로 여는 상황이다.

결정 전에 F5 반복을 측정했다(#561, 개인 AWS, `sha-a08c27a06b57`, 400명 동시 진입 뒤 5초마다 5번 다시 진입, 3회).

| 항목 | 결과 |
|---|---|
| 화면 진입 1회 전송량 | 약 11KB (2,400번에 27.0MB, 좌석 응답은 모두 gzip) |
| 다시 진입 p95 | 80 ~ 215ms |
| 서버 CPU | 화면 진입 1회당 약 5ms (구매 가능 정보 조회 포함) |

좌석 응답은 압축 전 약 160KB지만 브라우저가 받는 gzip은 약 11KB다. 좌석도를 나눠도 F5 한 번에 줄일 수 있는 전송은 많아야 약 11KB이고, 응답 생성은 ADR-0008로 이미 0.5초에 한 번이다. 백엔드·프런트·계약을 모두 바꾸는 비용에 비해 효과가 작다.

반면 화면의 새로고침 버튼이 쓰는 `/seats/status`는 압축 대상이 아니고(좌석 1,000개 약 37KB, JSON 추정) 요청마다 DB를 읽는다. 상태만 받는 버튼 새로고침이 전체 좌석 F5보다 더 많이 보낼 수 있다.

## 결정

1. `GET /api/performances/{performanceId}/seats/status` 응답 바이트(JSON, gzip)를 ADR-0008과 같은 방식으로 회차별 0.5초 공유한다. `/seats`와 따로 보관하고 설정(`restless.ticketing.seat-response-cache.enabled`, `.ttl`)은 함께 쓴다.
2. 좌석 압축 필터를 `/seats/status`에도 적용한다. 조건(2KB 이상, 클라이언트가 gzip 허용, 200 JSON)은 `/seats`와 같다.
3. 같은 회차를 동시에 처음 찾는 요청은 한 번만 계산한다. 계산 실패(없는 회차 404 등)는 보관하지 않는다.
4. 응답 형식(`seatId`, `status`, 좌석 ID 오름차순)은 그대로다.
5. 좌석도·상태 분리(좌석도 API와 `ETag` 재검증)는 보류한다. 재검토 조건을 둔다.

## 지켜지는 것

- 좌석 단일 소유자: 선점은 상태 응답을 보지 않고 좌석을 잠근 뒤 다시 검증한다(#559 잠금 전 확인 포함).
- 인증: 지금처럼 로그인이 필요하고 응답에 사용자별 값이 없다.

## 바뀌는 계약

`/seats/status`의 "조회 시점의 DB 상태"를 다음으로 바꾼다.

> 좌석 상태는 서버마다 최대 0.5초(설정값) 이전 상태일 수 있다. 실제 선점 가능 여부는 선점 요청에서 서버가 판단한다.

`/seats` 설명의 "조회 시점의 상태가 필요하면 `/seats/status`를 쓴다"는 지운다. 두 API 모두 최대 0.5초 이전 상태다. 압축 설명은 두 API에 적용한다.

## 고른 이유

| 선택지 | 판단 |
|---|---|
| 상태 응답 압축 + 0.5초 공유 (채택) | 버튼 새로고침 전송량이 압축으로 줄고 DB 조회가 0.5초에 한 번이 된다. 프런트 변경이 없다. ADR-0008 구현을 그대로 쓴다 |
| 좌석도 API 분리 + `ETag` 재검증 (보류) | F5마다 줄일 수 있는 전송이 gzip 약 11KB이고 서버 생성 비용은 이미 작다. 백엔드·프런트·계약 변경이 크다 |
| 압축만 | 전송은 줄지만 버튼을 누를 때마다 DB를 읽는다 |
| 지금 그대로 | 버튼 새로고침이 압축 없이 나가고 요청마다 DB를 읽는다 |

## 알려진 한계

- 새로고침 버튼을 0.5초 안에 다시 눌러도 같은 상태가 나온다.
- 서버가 N대면 서버마다 0.5초에 한 번씩 계산한다.
- 상태 응답 gzip 크기는 구현 뒤 측정한다.

## 범위 밖 (따로 정한다)

- `/booking-availability` 호출 줄이기: 프런트가 진입과 창 포커스마다 부른다. F5 비용에서 서버 CPU는 이 조회 몫이 크다.
- 좌석 조회 요청 수 제한: ADR-0004는 "조회 API는 제한하지 않는다"고 정했다. 넣으려면 ADR-0004를 고친다.

## 관측 방법

- `ticketing.seat_status_response` 캐시 적중·미스.
- k6 `page`의 버튼 새로고침(`REFRESH_COUNT`)과 F5 반복(`RELOAD_COUNT`)으로 받은 양(`data_received`)과 서버 CPU를 A/B로 본다.

## 재검토 조건

| 조건 | 검토 대상 |
|---|---|
| 좌석 수가 크게 늘어 좌석 gzip 응답이 수십 KB 이상 | 좌석도 분리 + `ETag` 재검증 |
| 사용자 기기에서 좌석 JSON 파싱이 화면 표시를 늦추는 것으로 확인됨 | 좌석도 분리 |
| CDN 도입 논의 | 좌석도 분리와 인증 요구 |
