# ADR-0005. 드롭 재고 행 분할: SKU 재고를 버킷으로 나눈다

- 상태: ACCEPTED (2026-11-22, 사용자 확정 D1~D5). 구현 #330
- 날짜: 2026-11-21 제안, 2026-11-22 채택
- 관련: #327, #330, [배포 전환](../operations/drop-inventory-buckets-cutover.md), [성능 계획 5절](../testing/drop-performance-plan.md#5-병목-기록), [불변식](../domains/drop/invariants.md), [트랜잭션 경계](../domains/drop/transactions.md)

## 배경

#322 뒤 TX1의 SKU 재고 행 락 구간에는 커밋 한 번(약 6ms)만 남았다 (#325). 같은 행이라 커밋이 하나씩 줄 선다.
3 SKU에 300건/초를 넣으면 SKU당 100건/초 x 락 약 8.5ms로 행 점유율이 약 0.85다. 작은 DB 정체 한 번이 긴 적체로 번진다.
커밋 지연의 원인 후보는 RDS의 redo와 binlog 동기화다. 스토리지 지연과 Multi-AZ 여부는 아직 확인하지 않았다. 내구성 완화는 결제 도메인이라 쓰지 않는다. 남은 수단은 한 SKU에서 동시에 커밋할 수 있는 행 수를 늘리는 것이다.

## 결정

1. 새 테이블 `drop_inventory_buckets(variant_id, bucket_no, total, available, reserved, sold, version)`에 SKU 재고를 K개로 나눈다. 버킷마다 보존식과 음수 금지 CHECK를 둔다. SKU 수량은 버킷 합이다.
2. 새 SKU의 K는 `restless.drop.inventory.bucket-count`(기본 4, 1~16)이고 생성 때 `min(K, 총재고)`로 정해 `drop_inventories.bucket_count`에 저장한다. 나머지는 앞 버킷부터 1개씩 더한다.
3. `drop_reservations.bucket_no`에 점유한 버킷을 기록한다. 확정, 반환, 환불 복원은 그 버킷만 바꾼다. 이 컬럼에서 버킷으로 가는 물리 FK는 두지 않는다. FK 검사의 S 락이 같은 버킷 UPDATE의 X 락으로 올라가며 교착이 나기 때문이다.
4. TX1은 무작위 시작 버킷부터 `FOR UPDATE SKIP LOCKED`로 잠기지 않은 재고 버킷 하나를 고르고, 한 문장 UPDATE로 그 버킷과 점유의 버킷 번호를 같이 바꾼다. 재고가 있는 버킷이 모두 잠겼을 때만 커밋된 재고가 보인 버킷 하나를 기다린다. 그 버킷이 비었으면 다시 고르고, 버킷마다 한 번만 기다린다. 이미 비어 있는 버킷은 기다리지 않으므로 대기 순환이 생기지 않는다. 재고가 마지막인 #322 순서와 READ_COMMITTED를 유지한다.
5. `drop_inventories`의 수량 컬럼은 TX1과 정산에서 더 갱신하지 않는다. 조회, 입장 진입, 입장 허가 작업은 버킷 합을 잠그지 않고 한 문장으로 읽는다.
6. 기존 데이터는 새 마이그레이션 두 개로 옮긴다. DDL과 이관을 나눈다. 기존 SKU도 점유와 판매는 버킷 0에 두고 남은 `available`만 최대 4개로 나눈다.

## 검토한 대안

| 대안 | 채택하지 않은 이유 |
|---|---|
| 커밋 동기화 완화 | 결제와 재고의 내구성을 낮춘다 |
| 버킷을 기록하지 않고 반환 때 아무 버킷이나 고르기 | 버킷 단위 정합성 검사를 못 한다 |
| 무작위 시작 뒤 버킷마다 조건부 UPDATE | 기다린 뒤 0행인 버킷의 락이 남아 교착이 난다. 로컬 MySQL 8.4에서 재현했다 |
| 한 번 기다린 뒤 0행이면 품절 | 다른 버킷에 재고가 남았는데 품절을 돌려준다. 로컬에서 재현했다 |
| 한 문장 UPDATE에 `ORDER BY ... LIMIT 1` | 어느 버킷을 잡았는지 알 수 없다 |
| Redis 같은 앞단 재고 | 새 인프라와 이중 기록이 필요하다 |

## 결과와 한계

- 공개 API의 요청, 응답, 오류 코드는 바뀌지 않는다. `soldOut`과 진입 품절은 버킷 합 = 0으로 판정한다.
- 품절은 한 문장 읽기에서 모든 버킷의 커밋된 재고가 0일 때만 나온다. 단일 행과 같은 의미다.
- 버킷 락을 얻은 뒤 UPDATE 왕복이 하나 더 들어가 락 보유가 약 0.4ms 길어진다.
- 재고 버킷이 모두 잠긴 순간에는 커밋 한 번을 기다린다. 포화 근처와 막바지에 잦다. 품절 응답은 왕복이 3번으로 늘어난다.
- 수량 컬럼이 멈춘 기간에는 그 값을 읽으면 틀린다. 측정으로 채택이 확정되면 별도 축소 마이그레이션에서 지운다.
- 하네스 SQL, dev 시드와 perf 시드, `drop_inventories`를 직접 고치는 테스트 도우미, 데이터 모델과 트랜잭션 문서, INV-03 문구를 같이 바꿔야 한다.

## 확정 (2026-11-22, 사용자)

| ID | 확정 내용 |
|---|---|
| D1 | `drop_inventories`의 수량 컬럼은 갱신하지 않고 멈춘다. 지우는 축소 마이그레이션은 성능 측정으로 채택이 확정된 뒤 별도 PR로 한다 |
| D2 | 기본 K=4. 새 SKU는 생성 때 `min(K, 총재고)`개로 나눈다. 재고 수량에 따라 K를 바꾸지 않는다. K의 기준은 SKU에 몰리는 초당 요청 수다. 재고는 보통 최대 1,000개다. 기존 SKU는 이관 때 남은 재고를 최대 4개로 나눈다 |
| D3 | 품절은 한 문장 읽기에서 모든 버킷의 커밋된 재고가 0일 때만 나온다. 그 직후 반환으로 재고가 생기는 창은 지금과 같은 의미로 받아들인다. 계약 D2에 적는다 |
| D4 | INV-03을 "예약, 확정, 반환, 환불 복원은 같은 SKU, 같은 재고 버킷을 대상으로 한다"로 바꾼다 |
| D5 | 판매 시간 조건은 두지 않는다. 배포 스크립트가 이전 컨테이너를 지운 뒤 새 컨테이너를 띄워 두 버전이 겹치지 않는다. 대신 이 배포 한 번만 `deploy.paused`로 자동 배포를 멈추고 직접 배포한다. 실패해도 이전 이미지로 되돌리지 않고 고쳐서 다시 배포한다. 배포 뒤 검사 SQL을 돌린다 ([절차](../operations/drop-inventory-buckets-cutover.md)) |

## 재검토 조건

- 버킷 분할 뒤 같은 조건 측정에서 포화 처리량이 늘지 않을 때
- 버킷당 락 보유가 동시 커밋 때문에 크게 늘 때
- 서버를 2대 이상으로 늘리거나 DB 사양을 바꿀 때
