# ADR-0007. 서버 여러 대에서 경매 실시간 전달: DB의 revision 확인

- 상태: DECIDED. 확인 간격(0.5초)은 여러 대 측정으로 조정한다
- 날짜: 2026-11-26
- 관련: [경매 정책 8·9절](../domains/auction/policy.md), [ADR-0001 이벤트 처리](0001-event-handling.md), [경매 부하 테스트](../domains/auction/load-test.md) AU-9

## 배경

경매 변경 이벤트(`AuctionChangedEvent`)는 커밋 뒤 같은 서버 안에서만 돈다 (ADR-0001). 서버 한 대일 때는 충분했다.

perf 환경은 ALB 뒤에 서버 여러 대를 두고, ALB는 요청을 서버마다 돌아가며 보낸다 (스티키 세션 없음). 관전자 A가 서버 1에 SSE로 붙어 있고 입찰자 B의 입찰이 서버 2에서 처리되면:

- 서버 1에는 이벤트가 오지 않아 A는 새 가격을 받지 못한다. 서버 1에서 그 경매에 다른 변경이 생길 때까지 계속 옛 가격을 본다.
- 서버 1의 조회 캐시(상세, 입찰 사전 확인)는 만료 시간(1초)까지 옛 값을 준다.

입찰과 낙찰의 정확성은 영향이 없다. 모든 쓰기는 같은 DB의 경매 행 잠금을 거친다.

## 결정

1. SSE 연결을 가진 서버마다 전용 스레드가 0.5초마다 그 서버에서 관전 중인 경매의 `revision`을 DB에서 읽는다. 기본 키 `IN` 조회 하나이고 잠그지 않는다. 관전 중인 경매가 없으면 조회하지 않는다.
2. 경매마다 그 경매의 연결 전부에 마지막으로 보낸 `revision`을 기억한다. DB 값이 더 크면 "바뀜"으로 표시하고, 기존 전송(0.2초마다 최신 상태 하나)이 보낸다. 경매가 없어졌으면(시작 전 삭제) 역시 "바뀜"으로 표시해 전송이 연결을 닫는다.
3. 같은 확인에서 바뀐 경매의 조회 캐시를 버린다 (세대 번호를 올린다).
4. 서버 안 이벤트는 그대로 둔다. 같은 서버의 변경은 지금처럼 바로 간다.
5. 간격은 설정값이다 (`restless.auction.stream.revision-poll-interval-ms`, 기본 500, 0이면 끈다).
6. 확인이 실패하면 로그와 메트릭(`auction.stream.failure{stage=poll}`)을 남기고 다음 주기에 다시 본다.

`revision`은 이미 경매가 바뀔 때마다(시작, 입찰 수락, 종료, 시작 전 수정) 하나씩 오르므로 새 열이나 테이블이 필요 없다.

## 고른 이유

| 선택지 | 판단 |
|---|---|
| DB revision 확인 (채택) | 지금 구조(DB 하나)로 된다. 새 인프라가 없다. 메시지를 놓쳐도 다음 확인에서 따라잡는다 |
| Redis 발행·구독 | 전달은 더 빠르다. 그러나 경매에 Redis 의존이 새로 생기고 (Redis는 드롭 대기실용으로 ADR-0006 제안 단계), 발행·구독은 받는 서버가 잠깐 끊기면 메시지를 잃어 결국 revision 확인 같은 따라잡기가 필요하다 |
| 스티키 세션 | 관전자와 입찰자는 다른 사람이라 같은 서버로 묶이지 않는다. 해결되지 않는다 |
| 변경 기록 테이블, Outbox | 입찰 트랜잭션에 INSERT가 늘고, ADR-0001이 정한 재검토 조건에 해당하지 않는다 |

간격 0.5초: 0.2초는 서버당 초당 5번이고 서버 수만큼 곱해진다. 1초는 다른 서버 관전자의 지연이 최대 1초 늘어난다. 측정으로 조정할 수 있게 설정값으로 둔다.

## 알려진 한계

- 다른 서버의 변경은 최대 "확인 간격 + 전송 간격"(기본 0.5 + 0.2초)에 조회 시간만큼 늦게 간다. 같은 서버의 변경은 지금과 같다.
- 캐시를 버리는 것은 이 서버에서 관전 중인 경매뿐이다. 나머지 경매의 상세·사전 확인 캐시는 만료 시간(1초)까지 옛 값을 줄 수 있다. 사전 확인은 "금액 부족"만 미리 거절하고, 진행 중 경매의 최소 입찰 금액은 오르기만 하므로 옛 캐시는 더 낮은 금액을 들고 있다. 잘못 거절하지 않고 잠금 경로로 보낼 뿐이다.
- 서버당 0.5초마다 조회 하나가 DB 연결을 잠깐 쓴다. 서버 4대면 초당 8번이다.

## 관측 방법

- `auction.stream.poll.changed`: 확인이 "바뀜"으로 표시한 수. 다른 서버의 변경과, 아직 전송 전인 같은 서버의 변경이 함께 들어간다.
- `auction.stream.failure{stage=poll}`: 확인 실패 수.
- AU-9: 관전은 서버 1, 측정 입찰은 서버 2로 보내 단계별 전달 지연과 마지막 CLOSED 전달을 잰다 (`PERF_BID_APP_IP`).

## 재검토 조건

| 조건 | 검토 대상 |
|---|---|
| 확인 조회가 DB 부하나 연결 대기로 측정됨 | 간격 늘리기, 또는 Redis 발행·구독 |
| 다른 서버 관전자의 전달 지연 요구가 0.7초보다 짧아짐 | Redis 발행·구독 |
