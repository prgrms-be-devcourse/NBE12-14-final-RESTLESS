# ADR-0006. 드롭 대기실 상태를 Redis로 옮기는 2단계 제안

- 상태: 실험 승인 (2026-11-28, 사용자 확정 Q1~Q11). (b)안 비교 실험을 한다. 채택은 측정 뒤 [합격 기준](#합격-기준-2026-11-28)으로 정한다. 채택 전에는 정본 문서와 공개 계약을 바꾸지 않는다
- 날짜: 2026-11-24 제안, 2026-11-28 실험 승인
- 관련: #538, #392, 측정 요약은 [#392 본문](https://github.com/prgrms-be-devcourse/NBE12-14-final-RESTLESS/issues/392), #377, #382, #383, #384, #385, #386, 1단계 #390, [열린 결정 사항 3절](../product/open-questions.md), [EXP-03](../testing/performance.md), [정책 7절](../domains/drop/policy.md), [불변식](../domains/drop/invariants.md), [장애 처리 F-12](../operations/failure-handling.md)

## 이 문서의 위치

2026-11-24 초안은 제안만 담았다. 1단계(`pollAfterMs`, 서버별 동시 처리 상한과 503 `DROP_QUEUE_BUSY`)는 #390에서 구현됐다.

2026-11-28에 사용자가 아래 질문 Q1~Q11과 실험 조건에 하나씩 답했다. 결정은 [2026-11-28 결정](#2026-11-28-결정) 절에 모았다. 본문의 설계 서술은 이 결정에 맞춰 고쳤다. 정확성 불변식 INV-01, 02, 06, 07, 10, 16, 17은 그대로 지킨다.

회차별 성능 수치는 이 문서에 넣지 않는다. 서버 2대 측정은 #392 본문, 예산 사양 측정 요약은 #538에 둔다. 결정 근거가 된 비율만 배경에 적는다.

## 배경

대기실은 판매 중 요청의 대부분을 차지하는 상태 조회와 진입을 처리한다. 이 요청이 가장 비싼 경로를 탄다. 인증, ORM, DB 드라이버를 모두 거치고 DB에서는 최신 대기 행 조회, heartbeat 조건부 쓰기, 순번 계산이 붙는다.

2026-11-24에 세 번 고쳤다.

| 개선 | 내용 |
|---|---|
| #377, #382 | 순번 COUNT를 커버링 인덱스로 처리 |
| #383, #384 | 순번을 서버마다 SKU별 1초 스냅샷으로 계산 |
| #385, #386 | 상태 조회를 무잠금으로 읽고 heartbeat를 10초 간격으로 기록 |

그 결과 DB가 첫 병목에서 물러났고 두 서버의 앱 CPU가 첫 병목이 됐다. 프로파일에서는 한 곳이 독차지하지 않았다. DB 드라이버와 ORM, 메트릭, 보안, 서블릿 처리가 나란히 나왔다. 요청 구성, 요청당 CPU, 회차별 수치는 [#392](https://github.com/prgrms-be-devcourse/NBE12-14-final-RESTLESS/issues/392)에 있다.

용어: 앱 CPU 병목의 프로파일은 JFR(자바 실행 프로파일러)로 봤다. 대표 판매 뒤 정합성 검사는 INV-06을 뺀 INV-01~09를 SQL로 확인하고, INV-06은 수용 테스트가 맡는다.

1단계는 응답에 조회 간격을 싣는 `pollAfterMs`와 넘치는 요청 거절 `DROP_QUEUE_BUSY`를 넣었다. 이 둘은 Redis 경로에서도 그대로 둔다.

1단계는 요청 수 자체를 줄인다. 2단계인 이 제안은 남는 상태 조회 한 건의 비용에서 DB 접근을 빼는 방법이다. 그래도 인증, 서블릿, 메트릭 몫은 그대로 남는다.

### 2026-11-28에 다시 본 병목

측정 사양이 예산 사양으로 바뀌었다. 앱 서버 4대와 DB 1대다. 이 사양에서는 판매 시작 뒤 몇 초 안에 DB CPU와 앱 4대 CPU가 함께 포화한다. DB 쪽 부담을 덜어야 다음 단계로 갈 수 있다고 보고, 이 제안의 효과는 DB 시간으로 본다.

판매 시작부터 매진까지 DB 문장 시간 중 대기열 문장(`drop_queue_entries`, `drop_queue_gates`)의 몫은 기준선 세 회차에서 25~31%였다. COMMIT을 빼면 30~38%다. 이 몫은 상한이다. (b)안에서도 진입의 슬롯 잠금과 최신 행 읽기, 입장 허가 작업의 허가 행 쓰기는 DB에 남으므로 실제로 빠지는 몫은 이보다 작다. 서버 8대와 큰 DB 사양에서 본 더 큰 비율은 예산 사양 판단에 쓰지 않는다. 측정 조건과 회차별 값은 #538에 있다.

현재 구조는 [정책 7절](../domains/drop/policy.md)과 [트랜잭션 D4](../domains/drop/transactions.md)에 있다. 대기, 입장 허가, 소비가 모두 `drop_queue_entries` 행의 상태이고, 입장 허가 작업이 SKU 게이트 행을 잠가 상태를 바꾼다. 순서는 SKU 안 `id` 오름차순이다.

### 합격 기준 (2026-11-28)

측정 전에 정했다. 기준선 D와 Redis 쪽을 같은 조건으로 각 3회 잰다. 아래를 모두 만족하면 채택한다.

- 점유 성공 p95 평균과 결제 승인 p95 평균이 둘 다 15% 이상 좋아진다
- 공식 기준 8개 중 새로 실패하는 항목이 없다
- 판매 구간 DB CPU 사용 시간이 줄어든다
- 정합성 검사 위반이 0이다
- 보고서에 지표 N개 중 개선, 유지, 악화 수를 적는다
- ElastiCache CPU 크레딧이 바닥난 회차는 무효로 하고 다시 잰다

## 선택지

### (a) 현재 DB 구조 유지, 1단계만

| 항목 | 내용 |
|---|---|
| 변경 | 1단계 #390만 한다 |
| 비용 | 새 인프라 없음. 추가 구현 없음 |
| 정확도 | 지금과 같다. 순번은 최대 1초 늦고 이탈자는 스냅샷 시점에 빠진다 |
| 장애 모드 | 새로 생기지 않는다. DB 장애는 지금처럼 전체 장애다 |
| 다중 인스턴스 | 성립한다. 서버마다 스냅샷이 달라 순번이 흔들릴 수 있다 |
| 불변식 | INV-16, INV-17, INV-06, id 순서 모두 변하지 않는다 |
| 마이그레이션, 롤백 | 없다 |
| 운영 비용 | 없다 |
| 한계 | 상태 조회 한 건의 DB 접근 비용은 남는다. 1단계가 요청 수를 충분히 줄이면 작성자 판단으로는 이것으로 끝날 수 있다. 판단은 사람이 한다 |

### (b) Redis 대기실: 번호표 카운터 (2026-11-28 실험 대상으로 결정)

대기 상태만 Redis로 옮긴다. 입장 허가, 소비, 재고는 DB에 둔다. 입장 허가 작업이 어디까지 처리했는지도 DB가 기준이다.

세 값의 관계: 카운터는 마지막으로 발급한 번호표다. 처리 위치는 입장 허가 작업이 처리를 끝낸 마지막 번호표다. 처리 위치 이하는 끝났고, 처리 위치 초과 카운터 이하가 대기 중이다. 순번은 내 번호표에서 처리 위치를 뺀 값이다.

| Redis 키 | 단위 | 역할 |
|---|---|---|
| 번호표 카운터 | SKU마다 값 하나 | 진입 때 `INCR`로 번호를 받는다 |
| 번호표별 회원 | SKU마다 해시. 필드는 번호, 값은 회원 | 작업이 번호에서 회원을 찾는다 |
| 마지막 조회 시각 | SKU마다 해시. 필드는 회원 | 주입된 `Clock` 값을 저장한다. TTL은 메모리 정리용이다. TTL이 있는 대기실 키는 판매 종료 시각 이후를 기준으로 통일한다 |
| 회원의 최신 번호표 | 드롭과 회원마다 값 하나 | 번호표와 SKU를 가리킨다. 처리돼도 지우지 않고 새 진입 때만 바뀐다. 드롭당 대기 한 건을 지킨다 |
| 대기 중인 SKU 집합 | 전체에 하나. TTL은 두지 않고 빼는 Lua로만 정리한다 | 대기가 남은 SKU를 담는다. 진입의 `INCR`와 `SADD`는 Lua 하나로 묶고, 빼는 쪽도 카운터 비교와 `SREM`을 Lua 하나로 한다 |
| 처리 위치 사본 | SKU마다 값 하나 | DB 처리 위치의 읽기용 사본이다. 작업은 더 클 때만 쓰는 Lua로 갱신해 뒤로 가지 않게 한다. 초기화는 `SET NX`로 한다. 복구 직후에는 아래 복구 규칙에 따라 DB 값으로 덮어쓴다 |
| 건너뜀 표시 | SKU마다 해시. 필드는 번호 | 작업이 이탈로 건너뛴 번호표를 표시한다. 조회 Lua가 보면 404다. TTL은 번호표별 회원과 같다 |

DB 변경은 컬럼 두 개다. `drop_queue_gates`에 SKU별 처리 위치를 더하고, `drop_queue_entries`에 번호표 번호를 더한다. 처리 위치는 입장 허가 작업이 게이트 행을 잠근 트랜잭션 안에서 올린다. 허가 행과 같은 커밋에 들어가므로 서버가 2대여도 같은 번호표를 두 번 처리하지 않는다. 게이트 행을 지금처럼 복구 작업이 다시 만들면 처리 위치가 기본값이 되므로, Redis 모드에서는 복구를 SKU 단위로 한다. 키 비우기와 재기록은 이번 호출이 실제로 게이트 행을 만들었을 때만 한다. 그 SKU의 Redis 대기실 키(카운터, 번호표별 회원, 마지막 조회 시각, 건너뜀 표시, 처리 위치 사본)를 비우고, 처리 위치와 사본을 그 SKU의 `drop_queue_entries` 최대 번호표 번호로 다시 쓴다. 이 값을 한 규칙으로 쓴다. 복구 직후 늦게 도착한 갱신으로 사본이 DB 값보다 커졌다면 작업이 게이트 안에서 DB 값으로 내려 맞춘다. 번호표별 회원 해시에는 진입 시각도 담아 허가 행의 진입 시각과 마지막 조회 시각을 채운다.

Redis는 전체가 유지되거나 전체가 사라지는 것을 전제로 한다. 단일 노드이고 퇴출을 끄고 백업 복원을 쓰지 않는다. 일부 키만 남는 상태는 지원하지 않는다. 그런 상태가 보이면 운영자가 대기실 키를 모두 비운다. 이 전제 덕분에 번호표 세대 같은 구분 장치가 필요 없다.

락 순서는 경로마다 아래와 같다. 슬롯은 `drop_purchase_slots`의 회원 행, 게이트는 `drop_queue_gates`의 SKU 행이다.

| 경로 | 잠그는 순서 | 기다리는 곳 |
|---|---|---|
| 진입 | 슬롯, 최신 대기 행. 슬롯 락 안에서 Redis를 부른다 | 슬롯 대기 |
| 입장 허가 작업 | 게이트(대기하지 않음), 슬롯(`SKIP LOCKED`로 대기하지 않음) | 슬롯이 잠겼거나 아직 보이지 않으면 바쁨으로 보고 그 번호표 앞에서 배치를 끊는다. 처리 위치는 올리지 않는다 |
| 현재 구매 불가 종료 | 게이트, 회원마다 슬롯 다음 대기 행 | 슬롯을 기다린다. INV-17 때문에 건너뛰지 않는다 |
| 카운터 초기화 | 게이트만 | 바쁘면 이번 진입을 오류로 답하고 다시 시도하게 한다 |
| 점유(TX1) | 슬롯, 최신 대기 행, 재고 버킷 | 지금과 같다 |

입장 허가 경로는 게이트를 쥔 채 슬롯을 기다리지 않는다. 종료 경로는 게이트를 쥔 채 슬롯을 기다리지만, 슬롯을 쥔 쪽은 게이트를 기다리지 않는다. 종료 경로는 슬롯 다음 대기 행 순서로 TX1과 같다. 그래서 순환이 없다. 종료가 슬롯을 기다리는 동안 게이트 보유가 길어질 수 있다. 슬롯은 드롭과 회원 단위라 서로 다른 SKU의 종료가 같은 회원을 두고 만날 수 있다. 그래서 슬롯을 잡기 전에 최신 번호표 키부터 확인해 낡은 번호표의 슬롯은 잡지 않고, 한 묶음 안에서는 슬롯을 회원 id 오름차순으로 잡는다. 그래도 교착이 나면 DB가 한쪽을 롤백하고 다음 실행이 다시 처리한다. 롤백 횟수는 메트릭으로 센다. 진입이 슬롯 락 안에서 Redis를 부르므로 작업과 진입이 겹쳐도 한쪽이 먼저 끝난 상태를 다른 쪽이 본다. 슬롯은 TX1도 오래 쥘 수 있어 한 회원 때문에 처리 위치가 멈출 수 있다. 끊긴 횟수를 메트릭으로 남긴다. 같은 번호표에서 연속 3회(약 3초) 끊기면 그 번호표를 행 없이 건너뛰고 건너뜀 표시를 남긴다(Q10). 그 회원은 대기를 잃고 다시 진입한다. 건너뛴 수는 메트릭으로 센다.

흐름

1. 진입
   - 판매 기간, SKU 소속, 재고를 지금처럼 DB에서 읽는다.
   - 회원의 슬롯 락 안에서 DB 최신 행을 본다. 기한이 지난 `ADMITTED`는 지금처럼 `EXPIRED`로 바꾼다. 미사용 유효 `ADMITTED`가 같은 SKU면 그대로 돌려주고 최신 번호표 키도 그 행의 번호표로 되돌리며, 다른 SKU면 `CLOSED`로 닫는다.
   - 같은 슬롯 락 안에서 Lua로 번호표를 받는다. 카운터가 이미 읽은 DB 처리 위치보다 작으면 먼저 올린다. 새 번호표를 받을 때 마지막 조회 시각도 현재 시각으로 쓴다. 같은 SKU에 유효한 대기가 있으면 새로 받지 않고 200으로 그대로 돌려준다. 유효 판정은 사본이 아니라 DB 게이트의 처리 위치를 잠금 없이 읽어 비교하고, 마지막 조회 시각이 40초 이내이고 건너뜀 표시가 없어야 한다. 하나라도 어기면 새 번호표를 받는다. 슬롯 락 안에서 읽은 DB 최신 행의 번호표가 Redis 최신 번호표와 같을 때도 처리된 번호표로 본다. 없거나 다른 SKU면 새 번호표를 받고 최신 번호표 키를 바꾼다. DB 변경은 그 뒤에 커밋한다.
   - Lua가 실패하거나 시간 초과를 받으면 DB를 롤백하고 오류로 답한다. 시간 초과는 Redis에서 Lua가 이미 실행됐을 수 있어 DB 커밋 실패와 같이 다룬다. 그 경우 새 번호표가 남고 이전 허가도 남는다. 작업이 슬롯 아래에서 DB 최신 행이 다른 SKU의 유효한 허가임을 보고 그 번호표를 건너뛴다. 슬롯 행은 번호표를 받기 전에 별도 짧은 트랜잭션으로 먼저 커밋해 둔다. 그래서 작업이 슬롯을 못 찾는 경우는 바쁨으로만 다루고, 오래 이어지면 Q10의 연속 끊김 처리로 넘긴다.
   - 카운터가 없으면 슬롯 락 밖의 짧은 트랜잭션에서 게이트를 잠그고 DB 처리 위치를 읽는다. 그 값으로 카운터와 처리 위치 사본을 `SET NX`로 초기화한 뒤 다시 시도한다. `SET NX`라 같은 초기화가 겹쳐도 값이 되돌아가지 않는다. 게이트가 바쁘면 이번 진입을 오류로 답한다. 게이트 행이 없으면 위 복구 규칙으로 만든 뒤 초기화한다. 초기화가 필요할 때는 먼저 슬롯 트랜잭션을 롤백하고 초기화한 다음 진입 전체를 다시 시도한다. 입장 허가 작업은 카운터가 없으면 카운터를 만들지 않고 번호표 처리만 이번 실행에서 건너뛴다. DB의 `ADMITTED` 종료와 `EXPIRED` 정리는 카운터와 상관없이 수행한다. 카운터가 없고 판매가 끝난 SKU는 대기 중인 SKU 집합에서 뺀다.
2. 상태 조회
   - 최신 번호표 키가 가리키는 번호표가 처리 위치 사본보다 크면 대기 중이다. 판매 기간이 끝났으면 404다. 판매 기간은 서버 메모리의 1초 캐시에서 읽는다(Q11). 마지막 조회 시각이 없거나 40초를 넘었거나 작업이 건너뜀 표시를 남겼으면 404다. 아니면 시각을 갱신하고 순번을 준다. 판정과 갱신은 Lua 하나로 한다.
   - 번호표가 처리 위치 사본 이하이면 처리된 것이다. 시각은 갱신하지 않는다. DB 최신 행의 SKU와 번호표 번호가 내 것과 같으면 그 행으로 답한다. 허가, 만료, 소비, 현재 구매 불가가 이렇게 나온다. 같지 않거나 행이 없으면 건너뛰어진 것이라 404다. 이 경우에는 40초와 판매 종료 규칙을 적용하지 않는다.
   - 최신 번호표 키가 없으면 DB 최신 행으로 판정한다. 키가 없는 이유는 가리지 않는다. DB 최신 행이 `ADMITTED`, `EXPIRED`, `CONSUMED`, `UNAVAILABLE`이면 지금처럼 판정해 답한다. 기한이 된 `ADMITTED`는 행을 바꾸지 않고 `EXPIRED`로 답한다. 그 밖에는 404다.
   - 대기 중 조회는 판매 기간 캐시가 비었을 때를 빼고 DB를 읽거나 쓰지 않는다. 마지막 조회 시각은 조회마다 갱신한다. 정책 7절의 10초 간격 기록은 DB 쓰기를 줄이는 규칙이라 Redis에서는 필요 없지만, 이탈 경계가 바뀌는 점은 정책 질문에 넣었다. 진입 재요청은 시각을 갱신하지 않는다.
3. 입장 허가 작업
   - 처리할 SKU는 Redis의 대기 중인 SKU 집합과 DB에서 살아 있는 SKU의 합집합이다.
   - 게이트 행을 잠그고 카운터를 처리 위치 이상으로 맞춘 뒤 허가 가능 수를 DB에서 계산한다.
   - 처리 위치 다음 번호부터 100개 묶음으로 읽는다. 이번 실행의 허가 수 상한은 실행을 시작할 때 정책 7-1 규칙 2대로 정하고 묶음 사이에 줄여 간다. 100은 한 번에 읽는 단위일 뿐 배치 제한이 아니다. 한 묶음은 한 트랜잭션이다. 묶음이 끝나 커밋하면 게이트가 풀리므로 다음 묶음은 새 트랜잭션에서 게이트를 다시 잠그고 처리 위치와 INV-16의 허가 가능 수를 다시 읽는다. 게이트가 바쁘면 그 SKU는 다음 주기로 넘긴다. 이렇게 허가 수를 채우거나 카운터에 닿을 때까지 이어 가므로 서버 2대의 허가 합이 `available`을 넘지 않는다. 번호표마다 그 회원의 슬롯을 `SKIP LOCKED`로 대기 없이 잡고 최신 번호표 키와 DB 최신 행을 다시 확인한다.
   - 판매 기간이 끝났으면 허가하지 않고 처리 위치를 카운터까지 올리고 SKU를 집합에서 뺀다.
   - 최신 번호표가 아니거나 마지막 조회가 40초를 넘은 번호표는 허가 없이 건너뛴다. 40초 판정은 Lua 하나로 시각을 다시 확인하고 건너뜀 표시를 남기는 일을 함께 한다. 조회 Lua는 그 표시를 보면 404를 준다. 그 뒤에 DB를 커밋한다. 슬롯 아래에서 DB 최신 행이 `ADMITTED`이고 기한이 지났으면 먼저 지금처럼 `EXPIRED`로 바꾼다. 남아 있는 `WAITING`은 `CLOSED`로 바꾼다. 유효한 다른 SKU 허가가 남았으면 건너뛴다. 이렇게 상태를 확인하므로 활성 유일 키 위반으로 배치가 롤백되지 않는다.
   - 나머지는 번호표 번호를 담은 `ADMITTED` 행을 넣고 처리 위치를 올려 한 트랜잭션으로 커밋한다.
   - 커밋 뒤 처리 위치 사본 갱신과 집합 정리를 한 Lua로 맞춘다. 집합에서 빼는 판단은 DB가 아니라 이 사본과 카운터를 비교해서 한다. 작업이 죽으면 DB가 그대로여서 같은 범위를 다시 읽는다.
4. 현재 구매 불가(`available = 0`)
   - 작업이 지금처럼 DB의 미사용 `ADMITTED`를 닫는다. 대상 회원 목록은 잠금 없이 읽고, 회원마다 슬롯을 잡은 뒤 그 행을 잠가 닫는다. 순서는 슬롯, 행이라 TX1과 같다.
   - 번호표 범위의 유효한 대기자마다 슬롯을 잡고 최신 번호표 키와 DB 최신 행을 다시 확인한다. 다른 SKU의 유효한 허가가 남은 회원은 행 없이 건너뛴다. 기한이 지난 `ADMITTED`가 남은 회원은 그 행을 먼저 `EXPIRED`로 바꾼다. 그렇지 않으면 활성 유일 키를 계속 쥔다. 나머지에 지금처럼 100명씩 묶음으로 번호표 번호를 담은 `UNAVAILABLE` 행을 넣고 처리 위치를 올린다. 묶음마다 `available`을 다시 읽어 재고가 돌아왔으면 멈춘다. 이탈한 번호표는 흐름 3과 같은 Lua로 시각을 다시 확인하고 건너뜀 표시를 남기며 행 없이 건너뛴다. 조회는 200 `UNAVAILABLE`을 돌려준다. 계약은 바뀌지 않는다.
5. 점유(TX1)는 지금과 같다. DB의 `ADMITTED`를 검증한다.

| 불변식, 다중 인스턴스, 롤백, 장애 모드 | (b)와 같다. 정리 작업이 하나 더 있다. 멈추면 순번이 부풀고, 서버 2대가 동시에 돌려도 결과가 같게 범위 삭제로 만든다 |
| 테스트 | (b)와 같다. 시각을 주입된 시계 값으로 저장하므로 고정 시계로 검사한다 |

### (d) 그 밖에 조사한 안

| 안 | 판단 |
|---|---|
| 프로세스 메모리 대기실 (Caffeine 등) | 서버가 2대면 번호가 서버마다 갈린다. 고정 세션이 필요하고 서버가 죽으면 대기가 사라진다. 작성자 판단으로 비교에서 뺐다. 채택 여부는 사람이 정한다 |
| 같은 EC2에 Redis 컨테이너 | 추가 과금 서비스가 없다. 두 서버가 한 컨테이너를 같이 쓸 수 있다. 그러나 병목인 앱 서버의 CPU와 메모리를 나눠 쓰고, 그 서버가 단일 장애점이 된다. 작성자 판단으로는 비교 실험용으로만 의미가 있다. 판단은 사람이 한다 |
| MySQL에 번호표 카운터 행 | 진입마다 한 행을 갱신하는 핫 행이 된다. 진입이 몰리면 새 핫 행이 되어 작성자 판단으로 비교에서 뺐다. 채택 여부는 사람이 정한다 |
| 순번을 `id` 차이로 근사 | `id`는 모든 SKU가 같이 쓴다. 이탈자도 못 뺀다. 작성자 판단으로 비교에서 뺐다. (b)는 SKU별 번호표로 이 문제를 피한다 |
| 조회 응답 캐시 | 응답이 회원별이고 heartbeat를 캐시가 삼키면 이탈 판정이 깨진다. 작성자 판단으로 비교에서 뺐다. 채택 여부는 사람이 정한다 |
| 서버 푸시(SSE, WebSocket) | 조회 요청 수를 줄이지만 연결 유지 비용이 생긴다. heartbeat가 조회에 묶여 있어 정책 7절을 다시 정해야 한다. 작성자 판단으로 이 ADR의 범위 밖에 둔다 |
| 관리형 Redis 호환 DB (MemoryDB) | 지속성이 있지만 비용이 더 크다. 최소 구성이 예산 안에 드는지 확인하지 못했다 |

## 장애 모드 (F-12 연결)

현재 [장애 처리 설계](../operations/failure-handling.md)의 F-12 구매 입장 제어 저장소 장애는 TBD다. (b)를 채택하면 아래를 F-12로 옮긴다.

| 장애 | 증상 | 제안 동작 | 복구 |
|---|---|---|---|
| Redis 연결 불가, 시간 초과 | 진입과 모든 상태 조회가 실패한다. 허가받은 회원도 자기 상태를 못 본다 | 대기실 API를 503 `DROP_QUEUE_UNAVAILABLE`과 `Retry-After`로 거절한다(Q8). 두 저장소에 순서가 갈리므로 DB 구현으로 자동 대체하지 않는다. Redis 오류 때 DB 최신 행으로 답할지는 정하지 않았다. 그렇게 하면 대기 중 회원에게 옛 행이 보일 수 있다 | Redis가 돌아오면 사용자가 다시 진입한다. 판매 중에는 `mysql`로 전환하지 않는다(Q9). 장애가 길면 판매를 연기하거나 재오픈한다 |
| 입장 허가 작업 중 Redis 실패 | 번호표를 읽다 실패한다 | DB는 바뀌지 않는다. 이미 이탈로 판정한 번호표의 건너뜀 표시만 남을 수 있다. 다음 실행이 같은 범위를 다시 처리한다 | 자동 |
| DB 커밋 뒤 처리 위치 사본을 못 맞춤 | 사본이 뒤처져 순번이 크게 보이고 허가받은 회원이 잠시 대기로 보인다. 입장 허가 5분은 허가 시각부터 흐르므로 그만큼 쓸 시간이 줄어든다 | 처리 위치는 DB 기준이라 중복 허가는 없다. 다음 실행이 사본을 맞춘다 | 자동 |
| Redis 재시작, 노드 교체 | 대기와 카운터가 모두 사라진다. 일부만 남는 상태는 지원하지 않는다 | 대기자는 다시 진입한다. 카운터가 없으면 진입이 게이트 락 안에서 DB 처리 위치로 `SET NX` 초기화한다. 백업 복원이나 일부 키만 남은 것이 보이면 운영자가 대기실 키를 모두 비운다. 판매 종료 뒤 TTL 정리만 일부 상태를 허용한다. 작업은 매 실행 카운터를 처리 위치 이상으로 올린다 | 사용자 재진입. 입장 허가와 점유는 DB에 있어 유지된다. 진입 때 DB의 미사용 `ADMITTED`를 먼저 확인하므로 이중 허가가 생기지 않는다 |
| 게이트 행 복구 | 처리 위치가 기본값이 되어 사본과 어긋난다 | 복구를 SKU 단위로 한다. 그 SKU의 대기실 키를 비우고 처리 위치와 사본을 그 SKU의 최대 번호표 번호로 다시 쓴다. 다른 SKU의 대기는 그대로다 | 그 SKU의 대기자는 다시 진입한다 |
| 메모리 부족, 키 퇴출 | 번호표나 기준 번호만 사라질 수 있다 | 퇴출 정책은 `noeviction`으로 둔다. 쓰기 실패는 거절한다. 대기 중인 SKU 집합을 뺀 대기실 키에 판매 종료 뒤 일정 시간이 지나면 지우는 TTL을 둔다. 판매 종료 뒤에는 키가 없으면 DB로 답하는 경로가 있어 지워도 정확성은 유지된다. 판매 중에는 키가 사라지면 안 되므로 ElastiCache에서는 사용자 지정 파라미터 그룹으로 `noeviction`을 건다. 기본 퇴출 정책은 TTL이 있는 키를 퇴출할 수 있다 | 용량 점검 |
| 지연이 큰 Redis | 요청이 쌓이고 작업의 번호표 읽기가 길어져 게이트 보유 시간이 늘어난다 | 짧은 Redis 시간 초과를 두고 작업은 시간 안에 못 읽으면 배치를 포기한다. 요청 쪽은 1단계(#390)의 동시 처리 상한을 쓴다 | 자동 |
| 서버 시계 차이 | 서버마다 이탈 판정이 다르다 | 마지막 조회 시각에 각 서버의 주입된 `Clock` 값을 저장해 비교한다. 서버 시계 오차는 지금 DB 방식과 같이 받아들인다 | 시계 동기화 |
| 진입과 허가 작업이 겹침 | 같은 회원의 이전 번호표가 허가될 수 있다 | 작업이 슬롯을 잡고 최신 번호표 키와 DB 최신 행을 다시 확인한다. 슬롯이 바쁘면 배치를 끊는다 | 자동 |
| 진입의 Lua 성공 뒤 DB 커밋 실패 | 새 번호표는 있고 이전 SKU의 허가가 남는다. 조회는 새 대기로 답하다가 작업이 번호표를 건너뛰면 404로 답한다 | 오류로 답한다. 이 상태는 잠시 생기고 규칙 9의 대기 1건과 어긋난다. Q5에서 허용했고 발생 수를 메트릭으로 센다 | 사용자가 다시 진입한다 |

결제와 재고는 대기실 저장소와 독립이다. 대기실이 멈춰도 이미 입장 허가를 받은 사람의 점유와 결제는 계속된다. 이 점은 테스트로 확인해야 한다.

- small을 고른 이유: ElastiCache T4g, T3 노드는 CPU 크레딧 standard 모드로 고정이라 무제한 모드가 없다. 크레딧이 바닥나면 기준선 성능으로 내려간다. 기준선은 micro가 코어 0.2개분, small이 0.4개분이다. 대기실 부하를 어림하면 코어 0.1~0.3개분이라 micro 기준선과 겹친다. 그래서 small로 정했다. 그래도 크레딧이 바닥난 회차는 Redis가 느려진 결과라 무효로 한다.
- 서울 온디맨드 단가 (AWS Pricing API, 2026-11-28): `cache.t4g.small` Redis OSS 시간당 0.047달러(하루 약 1.13달러, 7일 약 7.9달러), Valkey 0.0376달러. `cache.t4g.micro` Redis OSS 0.024달러, Valkey 0.0192달러. 데이터 전송은 넣지 않았다.

## 테스트 전략

- 저장소 경계 뒤에 구현 두 개를 두고 `DropSkuQueuePolicyAcceptanceTest`를 두 구현에 모두 돌린다. Redis 쪽은 Testcontainers를 쓴다.
- 대기 인원 게이지는 Redis에서 센다. INV-17 확인은 DB에 더해 Redis에 남은 유효 번호표가 없는지도 본다. 하네스 SQL은 DB만 보므로 수용 테스트가 이를 맡는다.
- INV-16, INV-17은 같은 동시 입장 허가 시나리오를 Redis 구현에도 돌려 위반 0을 확인한다.
- 입장 허가 작업의 DB 커밋 전후에 Redis 실패를 주입해 중복 허가가 없고 같은 범위를 다시 처리하는지 본다. 건너뜀 표시만 남은 경우도 포함한다.
- Redis 컨테이너를 멈춘 상태에서 대기실 API가 정해진 오류로 거절하고 허가받은 회원의 상태 조회가 어떻게 답하는지 확인하며 이미 입장 허가를 받은 사람의 점유와 결제가 성공하는지 본다.
- 번호표 순서, SKU 바꿔 진입, 이탈 건너뛰기를 고정 시계로 확인한다. 마지막 조회 시각을 주입된 `Clock` 값으로 저장하므로 TTL에 기대지 않고 고정 시계로 경계를 검사한다. 정확히 40초는 유지, 넘으면 건너뛰는지 확인한다.
- 근사 순번의 오차를 재는 테스트를 둔다. 이탈자가 앞에 있을 때 표시 순번과 실제 허가 순서의 차이를 기록한다.
- 장애를 주입하지 않은 상태에서 같은 회원의 진입, 다른 SKU 진입, 입장 허가 작업을 동시에 돌려 허가와 대기가 함께 남지 않는지 확인한다.
- 서버 2대에서 입장 허가 작업이 동시에 돌 때 같은 번호표가 두 번 허가되지 않는지 확인한다.
- 허가를 받은 회원이 다른 SKU로 다시 진입하는 시나리오가 INV-06과 규칙 9를 지키는지 수용 테스트로 확인한다.
- 같은 조건의 대표 판매 재측정 뒤 정합성 검사에서 INV-06을 뺀 INV-01~09를 확인한다. INV-06, INV-16, INV-17은 수용 테스트가 맡는다.

## 열린 문제

아래 셋은 실패 주입 테스트로 정한다. 채택이 정해진 뒤 dev 머지 전에 한다. 본문의 해당 서술은 현재 안이고 확정이 아니다.

1. 게이트 복구
   - 게이트 행이 다시 만들어지면 DB 처리 위치가 기본값이 되어 Redis 사본과 어긋난다. 본문은 SKU 단위로 키를 비우고 최대 번호표 번호로 다시 쓰는 안이다.
   - 복구가 여러 서버와 진입에서 동시에 돌 때 한 번만 효과가 나는지, 건너뛴 번호표 때문에 값이 뒤로 가는 경우가 안전한지는 동시성 테스트로 정한다.
2. Q5 상태: 2026-11-28에 정했다. 작업이 번호표를 건너뛸 때까지 새 대기로 보이고, 건너뛰면 404다. 발생 수는 메트릭으로 센다.
3. 카운터 초기화
   - Redis가 비었을 때 카운터를 DB 처리 위치로 `SET NX` 초기화하는 안이다. 진입, 입장 허가 작업, 복구가 겹칠 때 번호가 재사용되거나 대기를 잃는 경로가 없는지 확인해야 한다.
   - 부분 손실을 지원하지 않는다는 전제가 실제 운영에서 지켜지는지와 비우기 절차도 함께 확인한다.
4. DB와 Redis 부분 실패
   - 한 쪽만 성공한 경우의 처리 순서가 흐름마다 따로 적혀 있다. 진입은 Lua 뒤 DB 커밋, 작업은 DB 커밋 뒤 사본 갱신이다. 시간 초과는 성공과 구별되지 않는다.
   - 실패 주입 테스트로 중복 허가, 대기 손실, 처리 위치 정체가 없는지 확인한 뒤 순서를 확정한다. 확인 전에는 dev에 머지하지 않는다.

## 결정하지 않은 것

- (b) 채택 여부. 측정 뒤 합격 기준으로 정한다
- Redis 장애 때 허가받은 회원의 상태 조회를 DB 최신 행으로 답할지
- 요청 횟수 제한 카운터를 Redis로 옮기는 일. [ADR-0004](0004-request-rate-limit.md) 재검토 조건에 따로 있고, 이 결과를 본 뒤 따로 측정한다
- 서버 간 매진 표시 공유. 이 결과를 본 뒤 따로 측정한다
- 입장 허가, 점유, 결제의 저장소. 이 제안은 DB에 그대로 둔다
