이 위임은 근사 순번 허용 여부와 Redis 도입 여부를 정하지 않는다. 둘 다 아래 질문으로 남긴다.

## 배경

대기실은 판매 중 요청의 대부분을 차지하는 상태 조회와 진입을 처리한다. 이 요청이 가장 비싼 경로를 탄다. 인증, ORM, DB 드라이버를 모두 거치고 DB에서는 최신 대기 행 조회, heartbeat 조건부 쓰기, 순번 계산이 붙는다.

2026-11-24에 세 번 고쳤다.

| 개선 | 내용 |
|---|---|
| #377, #382 | 순번 COUNT를 커버링 인덱스로 처리 |
| #383, #384 | 순번을 서버마다 SKU별 1초 스냅샷으로 계산 |
| #385, #386 | 상태 조회를 무잠금으로 읽고 heartbeat를 10초 간격으로 기록 |

그 결과 DB가 첫 병목에서 물러났고 두 서버의 앱 CPU가 첫 병목이 됐다. 프로파일에서는 한 곳이 독차지하지 않았다. DB 드라이버와 ORM, 메트릭, 보안, 서블릿 처리가 나란히 나왔다. 요청 구성, 요청당 CPU, 회차별 수치는 [#392](https://github.com/prgrms-be-devcourse/NBE12-14-final-RESTLESS/issues/392)에 있다.

용어: 앱 CPU 병목의 프로파일은 JFR(자바 실행 프로파일러)로 봤다. 대표 판매 뒤 정합성 검사는 INV-06을 뺀 INV-01~09를 SQL로 확인하고, INV-06은 수용 테스트가 맡는다.

구현 중인 1단계는 응답에 조회 간격을 싣는 `pollAfterMs`와 넘치는 요청 거절 `QUEUE_BUSY`를 넣는다. 이 둘은 Redis 경로에서도 그대로 둔다.

1단계는 요청 수 자체를 줄인다. 2단계인 이 제안은 남는 상태 조회 한 건의 비용에서 DB 접근을 빼는 방법이다. 그래도 인증, 서블릿, 메트릭 몫은 그대로 남는다. 그래서 효과의 상한은 DB 접근이 요청당 CPU에서 차지하는 몫이다. 이 몫은 1단계 재측정에서 호출 스택을 더 깊게 잡은 프로파일로 다시 확인해야 한다.

현재 구조는 [정책 7절](../domains/drop/policy.md)과 [트랜잭션 D4](../domains/drop/transactions.md)에 있다. 대기, 입장 허가, 소비가 모두 `drop_queue_entries` 행의 상태이고, 입장 허가 작업이 SKU 게이트 행을 잠가 상태를 바꾼다. 순서는 SKU 안 `id` 오름차순이다.

| 장애 모드 | 새로 생기지 않는다. DB 장애는 지금처럼 전체 장애다 |

### (b) Redis 대기실: 번호표 카운터

대기 상태만 Redis로 옮긴다. 입장 허가, 소비, 재고는 DB에 둔다. 입장 허가 작업이 어디까지 처리했는지도 DB가 기준이다.

세 값의 관계: 카운터는 마지막으로 발급한 번호표다. 처리 위치는 입장 허가 작업이 처리를 끝낸 마지막 번호표다. 처리 위치 이하는 끝났고, 처리 위치 초과 카운터 이하가 대기 중이다. 순번은 내 번호표에서 처리 위치를 뺀 값이다.

| Redis 키 | 단위 | 역할 |
|---|---|---|
| 번호표 카운터 | SKU마다 값 하나 | 진입 때 `INCR`로 번호를 받는다 |
| 번호표별 회원 | SKU마다 해시. 필드는 번호, 값은 회원 | 작업이 번호에서 회원을 찾는다 |
| 마지막 조회 시각 | SKU마다 해시. 필드는 회원 | 주입된 `Clock` 값을 저장한다. TTL은 메모리 정리용으로만 길게 둔다 |
| 회원의 최신 번호표 | 드롭과 회원마다 값 하나 | 번호표와 SKU를 가리킨다. 처리돼도 지우지 않고 새 진입 때만 바뀐다. 드롭당 대기 한 건을 지킨다 |
| 대기 중인 SKU 집합 | 전체에 하나 | 대기가 남은 SKU를 담는다. 진입의 `INCR`와 `SADD`는 Lua 하나로 묶고, 빼는 쪽도 카운터 비교와 `SREM`을 Lua 하나로 한다 |
| 처리 위치 사본 | SKU마다 값 하나 | DB 처리 위치의 읽기용 사본이다. 더 클 때만 쓰는 Lua로 갱신해 뒤로 가지 않는다 |

DB 변경은 둘이다. `drop_queue_gates`에 SKU별 처리 위치 컬럼을 더하고, `drop_queue_entries`에 번호표 번호 컬럼을 더한다. 처리 위치는 입장 허가 작업이 게이트 행을 잠근 트랜잭션 안에서 올린다. 허가 행과 같은 커밋에 들어가므로 서버가 2대여도 같은 번호표를 두 번 처리하지 않는다.

락 순서는 경로마다 아래와 같다. 슬롯은 `drop_purchase_slots`의 회원 행, 게이트는 `drop_queue_gates`의 SKU 행이다.

| 경로 | 잠그는 순서 | 기다리는 곳 |
|---|---|---|
| 진입 | 슬롯, 최신 대기 행. 슬롯 락 안에서 Redis를 부른다 | 슬롯 대기 |
| 입장 허가 작업 | 게이트(대기하지 않음), 슬롯(짧게만 대기) | 슬롯을 짧은 시간 안에 못 잡으면 그 번호표 앞에서 배치를 끊고 처리 위치는 올리지 않는다 |
| 현재 구매 불가 종료 | 게이트, 대기 행. 슬롯은 잡지 않는다 | 지금 D4처럼 대기 행 락 |
| 카운터 초기화 | 게이트만 | 없음 |
| 점유(TX1) | 슬롯, 최신 대기 행, 재고 버킷 | 지금과 같다 |

게이트를 쥔 쪽이 슬롯을 길게 기다리지 않고, 슬롯을 쥔 쪽은 게이트를 잡지 않는다. 종료 경로는 슬롯을 잡지 않아 TX1의 슬롯, 대기 행 순서와 엇갈리지 않는다. 그래서 순환이 없다. 진입이 슬롯 락 안에서 Redis를 부르므로 작업과 진입이 겹쳐도 한쪽이 먼저 끝난 상태를 다른 쪽이 본다. 슬롯은 TX1도 오래 쥘 수 있어 한 회원 때문에 처리 위치가 멈출 수 있다. 끊긴 횟수를 메트릭으로 남긴다. 한 번호표에서 계속 끊길 때 어떻게 할지는 정하지 않았다. 행 없이 건너뛰면 그 회원이 대기를 잃으므로 사람이 정할 정책에 가깝다.

흐름

1. 진입
   - 판매 기간, SKU 소속, 재고를 지금처럼 DB에서 읽는다.
   - 회원의 슬롯 락 안에서 DB 최신 행을 본다. 기한이 지난 `ADMITTED`는 지금처럼 `EXPIRED`로 바꾼다. 미사용 유효 `ADMITTED`가 같은 SKU면 그대로 돌려주고, 다른 SKU면 `CLOSED`로 닫는다.
   - 같은 슬롯 락 안에서 Lua로 번호표를 받는다. 카운터가 처리 위치 사본보다 작으면 먼저 올린다. 새 번호표를 받을 때 마지막 조회 시각도 현재 시각으로 쓴다. 같은 SKU에 유효한 대기가 있으면 새로 받지 않고 200으로 그대로 돌려준다. 없거나 다른 SKU면 새 번호표를 받고 최신 번호표 키를 바꾼다. DB 변경은 그 뒤에 커밋한다.
   - Lua가 실패하면 DB를 롤백하고 오류로 답한다. 이전 허가는 그대로 남고 회원이 다시 진입한다. DB 커밋이 실패하면 새 번호표가 남지만, 작업이 슬롯 아래에서 DB 최신 행이 다른 SKU의 살아 있는 허가임을 보고 그 번호표를 건너뛴다.
   - 카운터가 없으면 슬롯 락 밖의 짧은 트랜잭션에서 게이트를 잠그고 DB 처리 위치로 `SET NX` 초기화한 뒤 다시 시도한다.
2. 상태 조회
   - 최신 번호표 키가 가리키는 번호표가 처리 위치보다 크면 대기 중이다. 판매 기간이 끝났으면 404다. 판매 기간은 서버 메모리의 짧은 캐시에서 읽는다. 저장된 마지막 조회가 40초를 넘었으면 404다. 아니면 시각을 갱신하고 순번을 준다. 판정과 갱신은 Lua 하나로 한다.
   - 번호표가 처리 위치 이하이면 처리된 것이다. 시각은 갱신하지 않는다. DB 최신 행의 SKU와 번호표 번호가 내 것과 같으면 그 행으로 답한다. 허가, 만료, 소비, 현재 구매 불가가 이렇게 나온다. 같지 않거나 행이 없으면 건너뛰어진 것이라 404다. 이 경우에는 40초와 판매 종료 규칙을 적용하지 않는다.
   - 최신 번호표 키가 없으면 Redis가 비었다는 뜻이다. DB 최신 행이 `ADMITTED`, `EXPIRED`, `CONSUMED`, `UNAVAILABLE`이면 그대로 답하고 아니면 404다.
   - 대기 중 조회는 DB를 읽거나 쓰지 않는다. 마지막 조회 시각은 조회마다 갱신한다. 정책 7절의 10초 간격 기록은 DB 쓰기를 줄이는 규칙이라 Redis에서는 필요 없지만, 이탈 경계가 바뀌는 점은 정책 질문에 넣었다. 진입 재요청은 시각을 갱신하지 않는다.
3. 입장 허가 작업
   - 처리할 SKU는 Redis의 대기 중인 SKU 집합과 DB에서 살아 있는 SKU의 합집합이다.
   - 게이트 행을 잠그고 허가 가능 수를 DB에서 계산한다.
   - 처리 위치 다음 번호부터 한 번에 100개를 읽는다. 번호표마다 그 회원의 슬롯을 짧게만 기다려 잡고 최신 번호표 키와 DB 최신 행을 다시 확인한다.
   - 판매 기간이 끝났으면 허가하지 않고 처리 위치를 카운터까지 올리고 SKU를 집합에서 뺀다.
   - 최신 번호표가 아니거나 마지막 조회가 40초를 넘었거나 DB 최신 행이 살아 있는 허가인 번호표는 허가 없이 건너뛴다. 슬롯 확인으로 충돌을 미리 막으므로 유일 키 위반으로 배치가 롤백되지 않는다.
   - 나머지는 번호표 번호를 담은 `ADMITTED` 행을 넣고 처리 위치를 올려 한 트랜잭션으로 커밋한다.
   - 커밋 뒤 처리 위치 사본 갱신과 집합 정리를 한 Lua로 맞춘다. 집합에서 빼는 판단은 DB가 아니라 이 사본과 카운터를 비교해서 한다. 작업이 죽으면 DB가 그대로여서 같은 범위를 다시 읽는다.
4. 현재 구매 불가(`available = 0`)
   - 작업이 지금처럼 DB의 미사용 `ADMITTED`를 닫는다.
   - 번호표 범위의 유효한 대기자에게 지금처럼 100명씩 묶음으로 번호표 번호를 담은 `UNAVAILABLE` 행을 넣고 처리 위치를 올린다. 묶음마다 `available`을 다시 읽어 재고가 돌아왔으면 멈춘다. 이탈한 번호표는 행 없이 건너뛴다. 조회는 200 `UNAVAILABLE`을 돌려준다. 계약은 바뀌지 않는다.
5. 점유(TX1)는 지금과 같다. DB의 `ADMITTED`를 검증한다.

| 항목 | 내용 |
|---|---|
| 비용 | 대기 중 상태 조회에서 DB 읽기와 쓰기가 사라진다. 판매 기간은 서버 캐시가 비었을 때만 DB에서 읽는다. 진입은 슬롯 락과 DB 읽기가 남고 Redis 왕복이 더해진다. 코드는 대기 저장소 경계 뒤에 구현 두 개를 유지한다. 효과의 상한은 요청당 CPU 중 DB 접근 몫이다 |
| 정확도 | 순번은 근사다. 이탈자가 앞에 있어도 즉시 빠지지 않고 작업이 그 번호에 닿을 때 건너뛴다. 처리 위치는 입장 허가 작업이 커밋한 뒤에만 오르므로 표시 순번이 작업 주기만큼 늦을 수 있다 |
| 서버 간 일치 | 같은 Redis를 보므로 서버마다 순번이 달라지지 않는다 |
| INV-16 | 게이트 행 직렬화와 허가 가능 수 계산이 DB에 그대로 있다. 바뀌지 않는다 |
| INV-17 | WAITING 종료와 미사용 `ADMITTED` 종료를 모두 작업이 게이트 안에서 한다. 진입 직후 짧은 지연을 허용하는 지금의 해석이 그대로 적용된다 |
| INV-06 | TX1이 DB의 `ADMITTED`를 검증하므로 바뀌지 않는다. 허가 행은 입장 허가 작업만 만든다 |
| id 순 입장 규칙 | 입장 순서 기준이 DB `id`에서 번호표로 바뀐다. 허가 행 `id`는 처리 순서대로 생기므로 한 SKU 안에서는 같은 순서다 |
| 규칙 9 (SKU 바꿔 진입) | 진입이 DB의 기존 `ADMITTED`를 닫고 최신 번호표 키를 바꿔 이전 번호표를 무효로 만든다. 작업이 건너뛴다 |
| 바뀌는 정본 문서 | policy 7절과 7-1절의 대기 행 설명, 규칙 5와 9의 종료 기록, id 순 서술, invariants.md의 INV-17 설명, state-machines.md의 WAITING 전이, data-model.md, transactions.md D4, 장애 처리 F-12, 계약의 입장 허가 절과 진입 절의 이탈 문장, 상태 조회 절의 heartbeat 기록 문장, position 정의. 이탈과 SKU 변경 때 대기 행의 `CLOSED` 기록이 남지 않는 점은 아래 정책 질문에 넣었다 |
| 마이그레이션 | 위 컬럼 두 개를 더하는 마이그레이션이 있다. 전환은 새로 둘 설정 `restless.drop.queue.store`로 한다. 판매 중에는 전환하지 않는다. 두 서버가 서로 다른 저장소를 보면 안 되므로 두 서버를 모두 내린 뒤 올린다. 자동 배포 일시 정지와 직접 배포 절차는 [ADR-0005](0005-drop-inventory-buckets.md)와 [배포 전환](../operations/drop-inventory-buckets-cutover.md)을 따르고, 서버가 2대라는 점을 절차에 더한다. 전환 때 DB의 `WAITING`은 닫고 사용자는 다시 진입한다 |
| 롤백 | 새로 둘 설정 `restless.drop.queue.store`를 `mysql`로 되돌린다. Redis의 대기는 버려지고 사용자는 다시 진입한다. 다시 Redis로 전환하기 전에 대기실 키를 비운다. 입장 허가와 주문은 영향이 없다. 추가한 컬럼은 남겨 둬도 된다 |
| 장애 모드, 운영 비용 | 아래 별도 절 |

| 비용 | 진입과 조회마다 로그 시간 연산이 붙는다. 메모리가 (b)보다 크다. 두 정렬 집합과 해시를 한 스크립트로 묶어야 한다 |

| 불변식, 다중 인스턴스, 롤백, 장애 모드 | (b)와 같다. 정리 작업이 하나 더 있다. 멈추면 순번이 부풀고, 서버 2대가 동시에 돌려도 결과가 같게 범위 삭제로 만든다 |
| 테스트 | 정리 작업의 시각을 주입된 시계로 제어할 수 있어 TTL보다 테스트가 쉽다 |

### (d) 그 밖에 조사한 안

| 안 | 판단 |
|---|---|
| 프로세스 메모리 대기실 (Caffeine 등) | 서버가 2대면 번호가 서버마다 갈린다. 고정 세션이 필요하고 서버가 죽으면 대기가 사라진다. 이 ADR에서 제외한다 |
| 같은 EC2에 Redis 컨테이너 | 추가 과금 서비스가 없다. 두 서버가 한 컨테이너를 같이 쓸 수 있다. 그러나 병목인 앱 서버의 CPU와 메모리를 나눠 쓰고, 그 서버가 단일 장애점이 된다. 비교 실험용으로만 의미가 있다 |
| MySQL에 번호표 카운터 행 | 진입마다 한 행을 갱신하는 핫 행이 된다. 진입이 몰리면 새 핫 행이 되어 이 ADR에서 제외한다 |
| 순번을 `id` 차이로 근사 | `id`는 모든 SKU가 같이 쓴다. 이탈자도 못 뺀다. 이 ADR에서 제외한다. (b)는 SKU별 번호표로 이 문제를 피한다 |
| 조회 응답 캐시 | 응답이 회원별이고 heartbeat를 캐시가 삼키면 이탈 판정이 깨진다. 이 ADR에서 제외한다 |
| 서버 푸시(SSE, WebSocket) | 조회 요청 수를 줄이지만 연결 유지 비용이 생긴다. heartbeat가 조회에 묶여 있어 정책 7절을 다시 정해야 한다. 이 ADR의 범위 밖이다 |
| 관리형 Redis 호환 DB (MemoryDB) | 지속성이 있지만 비용이 더 크다. 최소 구성이 예산 안에 드는지 확인하지 못했다 |

| 입장 허가 작업 중 Redis 실패 | 번호표를 읽다 실패한다 | DB 커밋 전이라 아무것도 바뀌지 않는다. 다음 실행이 같은 범위를 다시 처리한다 | 자동 |

| 진입과 허가 작업이 겹침 | 같은 회원의 이전 번호표가 허가될 수 있다 | 작업이 슬롯을 잡고 최신 번호표 키와 DB 최신 행을 다시 확인한다. 슬롯이 바쁘면 배치를 끊는다 | 자동 |

## 운영 비용

- 예산: 팀 AWS 한도는 75,000원이고 2026-12-07까지다. 기존 규칙은 EC2와 RDS 한 대씩 쓰는 것이다. [성능 실행 절차 6절](../testing/drop-performance-procedure.md)은 인프라를 추가하지 않는다고 적었다. ElastiCache는 이 규칙에 어긋나므로 도입 전에 예산 승인이 필요하다.
- 서버 2대 측정 조건은 #392를 따른다. 성능 실행 절차 문서는 아직 서버 한 대 기준이다.
- 최소 사양: 단일 노드 `cache.t4g.micro`, 복제본 없음이다. 요금은 시간 단위로 실행 시간만큼 든다.
- 참고 단가: 제3자 정리 글 기준으로 `cache.t4g.micro`가 Redis OSS 시간당 0.016달러, Valkey 0.0128달러다. 이 표는 지역을 밝히지 않았다. 서울 지역 단가는 확인하지 못했다. 도입 전에 [AWS 요금 페이지](https://aws.amazon.com/ko/elasticache/pricing/)에서 서울 지역으로 확인한다. 출처: [Upstash 정리](https://upstash.com/blog/aws-elasticache-pricing-explained-2026-full-cost-breakdown).
- 쓰는 시간만 켜고 끈다. 중지 기능이 없으므로 측정이 끝나면 삭제한다. 스냅샷이 남으면 별도 과금이므로 같이 지운다.
- 이 계정이 ElastiCache를 만들 수 있는지는 확인하지 못했다. 계정 제한으로 막혀 있을 수 있다.
- 복제본과 다중 AZ는 비용이 배가되므로 비교 실험에서는 쓰지 않는다. 그 대신 이 구성에서는 노드 장애 때 대기가 사라진다.

## 테스트 전략

- 저장소 경계 뒤에 구현 두 개를 두고 `DropSkuQueuePolicyAcceptanceTest`를 두 구현에 모두 돌린다. Redis 쪽은 Testcontainers를 쓴다.
- 대기 인원 게이지는 Redis에서 센다. INV-17 확인은 DB에 더해 Redis에 남은 유효 번호표가 없는지도 본다. 하네스 SQL은 DB만 보므로 수용 테스트가 이를 맡는다.
- INV-16, INV-17은 같은 동시 입장 허가 시나리오를 Redis 구현에도 돌려 위반 0을 확인한다.
- 입장 허가 작업의 DB 커밋 전후에 Redis 실패를 주입해 중복 허가가 없고 같은 범위를 다시 처리하는지 본다.
- Redis 컨테이너를 멈춘 상태에서 대기실 API가 정해진 오류로 거절하고 이미 입장 허가를 받은 사람의 점유와 결제가 성공하는지 본다.
- 번호표 순서, SKU 바꿔 진입, 이탈 건너뛰기를 고정 시계로 확인한다. 마지막 조회 시각을 주입된 `Clock` 값으로 저장하므로 TTL에 기대지 않고 고정 시계로 경계를 검사한다. 정확히 40초는 유지, 넘으면 건너뛰는지 확인한다.
- 근사 순번의 오차를 재는 테스트를 둔다. 이탈자가 앞에 있을 때 표시 순번과 실제 허가 순서의 차이를 기록한다.
- 장애를 주입하지 않은 상태에서 같은 회원의 진입, 다른 SKU 진입, 입장 허가 작업을 동시에 돌려 허가와 대기가 함께 남지 않는지 확인한다.
- 서버 2대에서 입장 허가 작업이 동시에 돌 때 같은 번호표가 두 번 허가되지 않는지 확인한다.
- 허가를 받은 회원이 다른 SKU로 다시 진입하는 시나리오가 INV-06과 규칙 9를 지키는지 수용 테스트로 확인한다.
- 같은 조건의 대표 판매 재측정 뒤 정합성 검사에서 INV-01~09를 확인한다.

## 정책 질문: 근사 순번을 허용할까

결정하지 않는다. 사람에게 묻는다.

| 항목 | 지금 정책 | (b)가 바꾸는 것 |
|---|---|---|
| 이탈자 | [정책 7절](../domains/drop/policy.md): 입장 순번과 대기 인원에서 heartbeat가 끊긴 대기를 뺀다 | 즉시 빼지 않는다. 입장 허가 작업이 그 번호에 닿을 때 빠진다 |
| 대기 기록 | 이탈과 SKU 변경 때 대기 행이 `CLOSED`로 남는다 | 대기 중 이탈과 SKU 변경은 DB 행을 남기지 않는다 |
| 신선도 | 2026-11-24 결정: 표시 순번이 최대 1초 늦고 서버마다 다를 수 있다 | 서버 간 차이는 없다. 대신 입장 허가 작업 한 주기만큼 늦을 수 있고 이탈자만큼 표시 순번이 실제보다 크다 |
| 입장 기준 | SKU 안 `id` 오름차순 | SKU 안 번호표 오름차순 |
| 대기 인원 메트릭 | 이탈자를 뺀다 | 근사다 |

근사 순번은 보수적이다. 표시된 순번이 실제보다 크게 나오고 실제 입장은 더 일찍 일어난다. 앞사람이 많이 떠난 판매에서 화면이 오래 안 줄다가 갑자기 입장 허가가 오는 일이 생길 수 있다.

물어볼 것

1. 표시 순번이 이탈자를 즉시 빼지 않아도 되는가
2. 입장 순서 기준이 `id`에서 번호표로 바뀌어도 되는가
3. 안 된다면 (c)처럼 정리 주기 지연을 허용하는 정확한 순번을 원하는가
4. 대기 중 이탈과 SKU 변경에 `CLOSED` 기록이 남지 않아도 되는가
5. SKU를 바꿔 진입하다 DB 커밋이 실패하면 새 대기와 이전 허가가 잠시 함께 남는다. 이 상태를 받아들이는가. Redis 호출이 먼저 실패하면 이전 허가는 그대로 남는다
6. 이탈 경계가 마지막 조회 기준 40초로 정확해지는 변화를 받아들이는가. 지금은 30~40초다

| 1단계 재측정 뒤에도 앱 CPU가 첫 병목이고 상태 조회가 요청의 대부분이다 | 같은 조건 재측정과 서버별 지표 |
| 상태 조회 한 건의 CPU 중 DB 접근 몫이 크다. 스택 깊이를 늘린 프로파일로 확인한다 | JFR. 몫이 작으면 Redis로 얻을 것이 작다 |
| 같은 조건의 Redis 실험 브랜치 재측정에서 서버 쪽 지표가 사람이 측정 전에 정한 폭 이상 좋아진다 | 개선 폭 기준은 사람이 정한다. 반복 횟수는 [측정 규약 5절](../testing/drop-performance-measurement.md)을 따라 전후 각 3회까지 간다 |
| 정합성 검사에서 INV-06을 뺀 INV-01~09 위반이 0이고 INV-06, INV-16, INV-17 수용 테스트가 통과한다 | 대표 판매 뒤 검사와 수용 테스트 |
| 정책 질문 1, 2, 4에 사람이 허용으로 답한다. 5와 6도 답한다 | 사람의 결정 |
| 예산 승인과 ElastiCache 생성 가능이 확인된다 | 팀과 AWS 관리자 |

(a)로 충분한 경우는 1단계 재측정에서 앱 CPU가 첫 병목에서 내려가거나, DB 접근 몫이 작다고 확인될 때다. 이때 이 ADR을 DEFERRED로 바꿀지는 사람이 정한다.

1단계 재측정 뒤에 이 문서를 다시 본다. 재검토 조건은 아래다.

- 1단계 재측정 결과가 나왔을 때
- 서버를 2대 이상으로 운영하기로 정했을 때
- 팀이 Redis 예산을 승인했을 때
- 근사 순번 정책이 정해졌을 때

## 결정하지 않은 것

- Redis 도입 여부, 근사 순번 허용 여부, 입장 순서 기준 변경
- 요청 횟수 제한 카운터를 Redis로 옮기는 일. [ADR-0004](0004-request-rate-limit.md) 재검토 조건에 따로 있다
- 입장 허가, 점유, 결제의 저장소. 이 제안은 DB에 그대로 둔다
- Redis 장애 때 대기실 API가 주는 오류 코드. 지금 계약에 없고 공개 계약 변경이다. 1단계의 `QUEUE_BUSY`를 재사용할지 포함해 사람이 정한다
