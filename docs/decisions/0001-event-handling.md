# ADR-0001. 이벤트 처리 방식: Spring Event로 시작

- 상태: Accepted
- 날짜: 2026-11-08
- 관련: Drop 구매 확정(TX3), 전액 환불 확정(TX5)

## 배경

구매 확정, 환불 확정 이후에 알림 같은 후속 작업이 필요하다.
Outbox + Kafka는 이벤트 유실을 막고 재처리를 지원하지만, 구현 비용과 운영 부담이 크고 구매 확정 트랜잭션에 INSERT가 추가된다.
현재는 유실이 실제로 문제가 되는지 측정한 근거가 없다.

## 결정

1. 재고, 주문, 결제 상태는 DB 트랜잭션 안에서 확정한다. 이벤트 리스너에 맡기지 않는다.
2. 후속 작업은 `@TransactionalEventListener(phase = AFTER_COMMIT)`로 처리한다.
3. 리스너가 실패하면 로그와 메트릭을 반드시 남긴다.
4. 알림은 알림 테이블에 행으로 저장해서 개수를 셀 수 있게 한다.
5. 판매 통계와 인기도는 이벤트로 누적하지 않고 주문 테이블에서 계산한다.
6. Outbox와 Kafka는 도입하지 않는다. 아래 재검토 조건을 충족하면 새 ADR로 다시 결정한다.

## 알려진 한계

이벤트는 메모리에만 있으므로, 커밋 후 리스너 실행 전에 서버가 종료되면 이벤트가 유실된다.
이 경우 로그도 남지 않으므로 대사(reconciliation)로만 유실을 관측할 수 있다.

## 관측 방법

- PAID 주문 수와 생성된 알림 수를 비교하는 대사 쿼리를 둔다.
- 장애 테스트: 부하를 거는 중 구매 확정 직후 서버를 강제 종료한 뒤 누락 건수를 측정한다.

## 재검토 조건 (결과를 보기 전에 미리 정함)

| 조건 | 검토 대상 |
|---|---|
| 원본 데이터로 복구할 수 없는 후속 작업에서 유실이 1건 이상 관측됨 | Outbox + MySQL 워커 |
| 이벤트를 받는 쪽이 여러 개로 늘어남, 또는 MySQL 워커 처리량이 병목으로 측정됨 | Outbox + Kafka |

Outbox를 검토할 때는 누락 건수와 함께 구매 확정 p95 변화를 같은 조건에서 비교한다.
유실이 관측되지 않으면 도입하지 않으며, 그 결과도 이 ADR 후속 기록으로 남긴다.
