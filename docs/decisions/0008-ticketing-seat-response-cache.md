# ADR-0008. 좌석 조회 응답을 회차별로 짧게 공유: 0.5초 응답 캐시

- 상태: DECIDED (#540). 만료 시간(0.5초)은 측정으로 조정한다. 구현은 별도 PR
- 날짜: 2026-11-28
- 후속: [ADR-0009](0009-ticketing-seat-status-response-cache.md)가 같은 방식을 `/seats/status`에 적용했다(결정 8의 범위 확장).
- 관련: [티켓팅 API 계약 좌석 조회](../contracts/api/ticketing.md#회차별-좌석-조회), [공연장·배치 정합성](../domains/ticketing/venue-consistency.md) 배치 좌석 위치 서버 캐시 절(#509), [ADR-0007 경매 실시간 전달](0007-auction-stream-cross-server.md)(조회 캐시 1초 선례), 드롭 품절 표시(`DropSoldOutCache`, 1초 선례)

## 배경

예매 오픈 순간 같은 회차에 사용자가 몰려 `GET /api/performances/{performanceId}/seats`를 거의 동시에 보낸다. 응답은 판매 좌석 1,000개(약 160KB, gzip 시 더 작음)이고 사용자별 값이 없다(소유자·선점 ID를 주지 않는다). 지금은 요청마다 같은 일을 반복한다.

1. 회차 존재·공개 확인과 판매 좌석 1,000행 조회 (DB 커넥션 사용)
2. 배치 좌석 위치와 결합 (위치는 #509·#537로 캐시됨)
3. JSON 변환 1,000개 x 10필드, gzip 압축

EC2 t3.small 1대 측정(2026-11-27·28)에서 좌석 조회는 CPU에 묶여 있다. 동시 400건이면 좌석 조회만으로 p95 약 2초, 좌석 화면 진입(좌석 + 구매 가능 정보) p95 약 2.8초다. 요청 1건 CPU는 약 13ms이고 인원에 정비례한다. #501·#503·#509·#537로 요청당 비용을 줄였지만 #503·#537은 측정 흔들림(±5%) 안이었다. 요청당 비용을 더 깎는 방식으로는 목표(입장 후 좌석 화면 p95 1초)에 닿기 어렵다.

## 결정

1. 회차별 좌석 조회 응답을 서버 메모리에 완성된 바이트로 보관한다. 키는 회차 ID, 값은 JSON 바이트와 gzip 바이트(처음 요청된 인코딩부터 만들고 다른 인코딩은 필요할 때 만든다).
2. 만료는 쓴 뒤 0.5초다 (`restless.ticketing.seat-response-cache.ttl`, 기본 500ms). 끌 수 있다(`...enabled`, 기본 true).
3. 같은 회차를 동시에 처음 찾는 요청은 한 번만 계산하고 결과를 나눈다 (Caffeine `get(key, loader)`). 계산 실패와 404·400 같은 오류 응답은 보관하지 않는다.
4. 회차 존재·공개 여부도 보관한 응답에 포함된다. 공개 취소·회차 삭제는 최대 0.5초 늦게 404로 바뀐다.
5. 선점·만료·반환·판매·환불로 좌석 상태가 바뀌어도 캐시를 바로 버리지 않는다. 0.5초 만료로만 따라간다. 1단계 결정이며 재검토 조건을 둔다.
6. 서버마다 따로 보관한다. 서버 간 무효화는 없다.
7. 응답 본문·헤더(Content-Type, Content-Encoding, Vary)는 지금과 같다. 이미 압축한 바이트는 압축 필터가 다시 압축하지 않는다.
8. 범위는 `GET /seats`만이다. `/seats/status`(새로고침 때만 호출), `/booking-availability`(사용자별 값), 선점·checkout은 바꾸지 않는다.

## 지켜지는 것

- 좌석 단일 소유자: 선점은 캐시를 보지 않고 판매 좌석을 잠근 뒤 상태를 다시 검증한다. 옛 상태를 보고 누른 사용자는 지금처럼 `SEAT_UNAVAILABLE`을 받는다.
- 인증: `/seats`는 지금처럼 로그인이 필요하다. 캐시는 인증을 통과한 요청에만 응답한다. 응답에 사용자별 값이 없어 공유해도 다른 사용자 정보가 섞이지 않는다.
- 구매 한도·활성 예약 안내는 `/booking-availability`가 요청마다 DB에서 준다.

## 바뀌는 계약

`/seats` 설명의 "현재 상태를 조회한다"를 다음으로 바꾼다.

> 좌석 상태는 최대 0.5초(설정값) 이전 상태일 수 있다. 실제 선점 가능 여부는 선점 요청에서 서버가 판단한다. 공개 취소·삭제된 회차도 최대 0.5초 동안 이전 응답이 나갈 수 있다.

`/seats/status`는 그대로 "조회 시점의 DB 상태"다.

## 고른 이유

| 선택지 | 판단 |
|---|---|
| 회차별 응답 바이트 0.5초 공유 (채택) | 몰린 N건이 계산 1번으로 준다. 조회·JSON·gzip을 모두 아낀다. 새 인프라가 없다. 경매 조회 캐시(1초), 드롭 품절 표시(1초)와 같은 방식 |
| 객체(`List<TicketSeatInfo>`)만 공유 | DB 조회는 아끼지만 JSON·gzip은 요청마다 남는다. 160KB 응답이라 이 몫이 크다 |
| 요청당 비용 계속 줄이기 | #503·#537이 측정 흔들림 안이었다. 남은 비용(드라이버 디코딩, JSON, JWT)은 한 곳에 몰려 있지 않다 |
| 배치와 상태 API 분리, 배치는 브라우저 캐시 | 효과는 크지만 응답 구조가 바뀌어 프런트 작업이 필요하다. 이 결정과 함께 쓸 수 있다 |
| 선점 커밋마다 캐시 버리기 | 같은 서버에서는 더 최신이다. 좌석 상태를 바꾸는 곳(선점, 만료 스케줄러, 반환, 판매, 환불, 주최자 수정)이 흩어져 있고 이벤트가 없어 빠뜨리기 쉽다. 오픈 순간에는 선점이 계속 일어나 캐시가 거의 매번 버려져 효과가 줄어든다 |
| 0.2초 / 1초 | 0.2초는 몰림 1초에 계산 5번. 1초는 표시 지연이 두 배. 0.5초로 시작하고 설정값으로 조정한다 |

## 알려진 한계

- 다른 사람이 방금 선점한 좌석이 최대 0.5초 동안 "가능"으로 보인다. 누르면 `SEAT_UNAVAILABLE`.
- 내가 방금 선점한 좌석도 0.5초 안에 `/seats`를 다시 부르면 "가능"으로 보일 수 있다. 프런트 좌석 화면(`performances/view.tsx`)은 선점 성공 시 선점 응답과 고른 좌석으로 내 좌석을 표시하고(`is-mine`, `is-held`), 새로고침 버튼은 캐시하지 않는 `/seats/status`를 쓴다. 좌석 목록이 달라질 때만 `/seats`를 다시 부른다. 그래서 화면 동작은 바뀌지 않는다. 페이지를 완전히 새로 열었을 때만 0.5초 안에 옛 상태가 보일 수 있고, 활성 예약은 `/booking-availability`가 요청마다 알려 준다.
- 서버가 여러 대면 서버마다 따로 계산한다. 서버 N대면 0.5초마다 최대 N번이다.
- 회차당 메모리: 응답 바이트(JSON 약 160KB + gzip). 동시에 보관하는 회차 수를 최대값으로 제한한다(예: 64).

## 기대 효과 (측정으로 확인)

- 몰림 동안 좌석 조회 계산이 0.5초마다 1번이 된다. 요청 1건 비용은 인증·필터·바이트 전송으로 줄어 약 13ms → 1ms 안팎으로 추정한다.
- 동시 400건 `simultaneous` p95 약 2초 → 수백 ms, `page` p95는 구매 가능 정보 조회가 남아 그만큼만 줄어든다(추정).

## 관측 방법

- `ticketing.seat.response.cache` 적중·미스, 계산 시간, 보관 중인 응답 나이.
- EC2 A/B: `simultaneous`, `page`, `mixed-distributed` 400명. mixed에서 선점 지연이 늘지 않는지 함께 본다.

## 재검토 조건

| 조건 | 검토 대상 |
|---|---|
| 프런트·사용자 확인에서 0.5초 지연이 문제로 확인됨 | 선점 커밋 시 같은 서버 캐시 버리기, 또는 TTL 축소 |
| 서버 대수가 늘어 서버별 계산이 DB 부하로 측정됨 | 공유 캐시(Redis) 검토 |
| 대기열 도입으로 동시 진입이 입장 속도로 제한됨 | TTL·범위 재검토 |
