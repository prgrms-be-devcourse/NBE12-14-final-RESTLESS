## 1. 서비스 소개 및 기획 의도

### 1-1. 서비스 소개

**FANQ: 아티스트와 팬을 연결하는 통합 이벤트 커머스 경험 제공**

FANQ는 **FAN + QUEUE**를 결합한 이름으로, 공연 티켓팅·한정판 판매·실시간 경매·팬미팅 응모를 제공하는 웹 서비스다.

팬은 공연과 연관 이벤트를 탐색하고 원하는 기능에 참여하며, 자신의 예매·구매·참여 결과를 확인한다. 판매자·주최자는 콘텐츠를 등록하고 운영한다.

### 1-2. 기획 의도

인기 공연과 한정 수량 이벤트는 요청이 몰리는 순간에도 좌석·재고·참가 자격을 정확하게 관리해야 한다. 중복 판매나 결제 결과 누락은 팬의 참여 기회와 서비스에 대한 신뢰에 영향을 주기 때문이다.

FANQ는 공연과 관련된 팬 활동을 하나의 서비스로 연결하면서, **사용자가 결제와 참여 결과를 신뢰할 수 있는 경험**을 만드는 것을 목표로 한다.

### 1-3. 프로젝트 목표

- 공연 예매와 연관 상품·이벤트 참여를 한곳에서 제공한다.
- 동시 요청에도 좌석·재고·크레딧·팬미팅 정원을 정확하게 유지한다.
- 중복 요청과 결제 응답 유실·서버 장애 이후 거래를 안전하게 복구한다.
- 성능 개선과 서버 확장 효과를 측정하고 결과와 한계를 기록한다.

## 3. 주요 기능 및 구현 범위

### 3-1. 핵심 기능

| 도메인 | 주요 기능·정책 | 핵심 검증 |
| --- | --- | --- |
| 티켓팅 | 지정석·다중 좌석 선점, 회차별 구매 제한, 예약 복구·전액 환불. 선점 5분 후 결제 시작 시 별도 5분 | 중복 점유·판매 방지, 다중 좌석 전체 성공 또는 전체 실패 |
| 한정판 판매 | 옵션별 재고 점유, 주문당 1개, 동시 활성 구매 1건, 완료 후 재구매, 전액 환불 | 초과 판매, 중복 차감, 중복 재고 반환 방지 |
| 경매 | 공개 최고가 입찰, 크레딧 확보·해제·낙찰 차감, 종료 연장, 실시간 조회 | 최고가·낙찰 결과·크레딧 원장 일치 |
| 팬미팅 | 행사별 응모 1건, 결정적 추첨, 당첨 결제 60분, 예비 순번 승격 | 정원 초과 방지, 기한 내 정상 승인자 자격 보호 |

### 3-2. 공통 거래 원칙

- 일반 결제는 토스페이먼츠 테스트 결제를 사용한다.
- 결제 결과가 불명확하면 실패로 단정하거나 자원을 먼저 반환하지 않는다.
- PG 결과와 내부 상태를 대조하고 재처리한다.
- 결제 기한·재시도·환불 정책은 각 도메인에 맞게 적용한다.
- 경매는 PG 대신 확보한 크레딧으로 정산한다.

### 3-3. 확장 및 제외 범위

| 구분 | 내용 |
| --- | --- |
| **대기열 구현** | Redis 기반 대기열·입장 제어를 구현한다. 티켓팅·한정판 판매에 적용하고, 경매·팬미팅은 진입 지점과 공정성 정책을 정해 적용한다. |
| **핵심 MVP 완료 후 추가** | 주최자·유저 전용 관리 기능 및 화면, 마이페이지의 주문내역 통합 조회, 관련 공연 티켓 구매자 대상 경매 참여 제한, 경매 낙찰자 팬미팅 참석, 티켓 구매자 팬미팅 자동 응모 |
| **이번 프로젝트 제외** | 카카오·구글 로그인, 장바구니, 실제 배송·송장, 비지정석·좌석 배치 편집기, 티켓 양도·부분 환불, 팬미팅 결제 후 참가 취소·본인인증 |

핵심 거래에 필요한 회원 식별·최소 권한 검사·개별 주문 결과 조회는 우선 구현하고, 주최자·유저 전용 관리 기능과 통합 마이페이지는 핵심 MVP 완료 후 추가한다.

## 4. 기술 스택 및 협업 방식

### 4-1. 기술 스택

| 영역 | 기술 | 사용 목적 |
| --- | --- | --- |
| **백엔드** | Java 21, Spring Boot 4.1.1, Spring Data JPA, Spring Security, JWT, SSE | 모듈형 모놀리식 API·거래 처리, 이메일 로그인, 인증·인가, 경매 실시간 갱신 |
| **DB** | MySQL 8.4, Redis, Flyway | 거래 데이터·정합성 관리, 대기열·입장 권한 관리, DB 스키마 변경 이력 관리 |
| **프론트엔드** | Next.js, TypeScript | 4인 공동 화면 개발, 페이지 라우팅, 타입 기반 API 연동 |
| **인프라/배포** | AWS EC2, Docker | 애플리케이션 실행·배포, 컨테이너 기반 환경 통일 |
| **기타** | GitHub Actions, GitHub, Notion, JUnit·Mockito·Testcontainers, k6, Prometheus·Grafana, 토스페이먼츠 테스트 결제 | CI/CD·협업, 단위·통합 테스트, 부하 테스트, 지표 수집·저장·시각화, 결제 승인·취소·조회 검증 |

### 4-2. 협업 방식

- 하나의 GitHub 저장소에서 백엔드·프론트엔드 폴더를 분리해 관리한다.
- 각 도메인 담당자가 백엔드·Next.js 화면·테스트를 함께 구현한다.
- 기능 브랜치에서 작업한 뒤 PR을 통해 `develop`에 병합하며, 최소 2인의 승인을 받는다.
- `develop`에서 기능 연결과 테스트를 확인한 후 `main`에 반영해 배포한다.
- GitHub Issue에 담당자·작업 범위·완료기준을 기록한다.
- Notion에 요구사항·정책·회의 결과·기술 결정 사항을 정리한다.
- API·공통 모델·결제 계약 변경은 영향을 받는 담당자와 사전에 협의한다.
- GitHub Actions로 빌드·테스트를 자동화하고, 주기적으로 화면과 API를 연결해 전체 사용자 흐름을 점검한다.

| 구분 | 요구사항 및 검증 기준 |

| **3주차** | 공유 상태·중복 작업 점검, 서버 확장 및 3차 측정, 장애 주입·복구, 회귀 테스트·배포·문서 갱신 | 정합성·복구 검증, 11/30 발표용 기능 버전 고정 |

### 7-3. 도메인별 진행 순서

- **송혜민:** 다중 좌석 선점 → 만료·복구 → 결제·환불 → 경쟁·화면 검증
- **홍승연:** 응모·추첨 → 당첨 주문·승격 → 보류·만료 → 정원·응모 부하 검증
- **이태호:** 재고, 구매 제한 → 주문, 승인 → 환불, 미완료 결제 재확인 → 재고, 결제 장애 검증
- **천종원:** 입찰·지갑 → 확보·해제·연장 → 종료·실시간 → 다중 경매·정산 검증

## 8. 검증·배포 및 완료기준

### 8-1. 기능·정합성 검증

각 도메인의 정상 흐름뿐 아니라 동시 요청·중복 실행·결제 장애 상황을 검증한다.

| 검증 대상 | 주요 시나리오 | 확인 기준 |
| --- | --- | --- |
| 티켓팅 | 동일 좌석 경쟁, 다중 좌석 선점, 구매 제한, 만료·환불 | 중복 예매 없음, 일부 좌석만 선점되지 않음 |
| 한정판 판매 | 마지막 재고 경쟁, 중복 구매 요청, 예약 만료·환불 | 초과 판매·중복 차감·중복 반환 없음 |
| 경매 | 동시 입찰, 여러 경매 참여, 종료 연장·중복 정산 | 잔액 초과 확보 없음, 최고 입찰·낙찰·차감 일치 |
| 팬미팅 | 중복 응모, 추첨 재실행, 예비 승격, 결제 보류 | 추첨 결과 일관성, 정원 초과 없음, 기한 내 정상 승인자 보호 |
| 공통 결제 | 승인·취소 재요청, 응답 유실, 서버 재시작 | 중복 반영 없음, 미완료 거래 추적·복구 가능 |

### 8-2. 성능·장애 복구 검증

k6로 부하를 발생시키고 Prometheus·Grafana로 서버 지표를 함께 관찰한다.

| 시기 | 검증 목적 | 주요 작업 |
| --- | --- | --- |
| 1차 측정 | 기준 성능과 병목 파악 | 동일 데이터·요청 시나리오로 처리량·응답시간·DB 대기 기록 |
| 2차 측정 | 개선 효과 확인 | 코드·쿼리·트랜잭션 개선 후 같은 조건으로 재측정 |
| 3차 측정 | 서버 확장 효과 확인 | 단일·다중 서버 비교, 공유 상태·중복 작업·DB 병목 점검 |
| 장애 검증 | 복구 가능성 확인 | PG 응답 유실·DB 반영 실패·서버 종료를 재현하고 재처리 확인 |

응답시간 p95·p99, 실제 RPS, 성공 거래 TPS, 시스템 오류율, DB·커넥션 대기를 측정한다. 성능 목표 수치는 기준 측정 후 결정한다.

측정 전후에 데이터 정합성을 확인하며, 예상된 품절·좌석 경쟁 실패는 시스템 오류와 구분한다. 실제 PG에는 대규모 부하를 발생시키지 않는다.

### 8-3. 배포 계획

AWS EC2와 Docker를 사용하고, GitHub Actions로 빌드·테스트·배포를 자동화한다.

| 항목 | 내용 |
| --- | --- |
| 백엔드 배포 환경 | AWS EC2에서 Spring Boot 애플리케이션을 Docker로 실행 |
| 프론트엔드 배포 환경 | AWS EC2에서 Next.js 애플리케이션을 Docker로 실행 |
| DB | MySQL 8.4 |
| CI/CD | GitHub Actions로 빌드·테스트 자동화, 배포 브랜치 병합 시 Docker 이미지 배포 |
| 모니터링 | Prometheus·Grafana로 서버 지표 수집·시각화 |

### 8-4. 최종 완료기준

- 좌석 중복·재고 초과·크레딧 음수·팬미팅 정원 초과 0건
- 요청·이벤트·작업 재실행에도 거래·환불·정산·추첨 중복 반영 없음
- PG 응답 유실·DB 반영 실패·서버 재시작 후 미완료 거래 복구 가능
- 정상·실패·재접속 사용자 흐름을 화면에서 시연 가능
- 측정 환경·조건·수치와 개선의 한계 기록
- 배포·실행 안내·ERD·API가 구현과 일치
- 미정 정책·알려진 오류·미완료 기능 공개
