# 성능 실험 계획

## 1. 연구 주제

고동시성 한정판 드롭의 거래 정합성 보장과 유입 제어(Admission Control) 기반 Throughput, Latency 최적화

핵심 질문: 한정된 재고에 구매 요청이 순간적으로 몰릴 때, 초과 판매와 중복 결제를 막으면서 높은 지속 처리량과 낮은 꼬리 지연을 어떻게 확보하는가?

## 2. 목표

| 우선순위 | 목표 | 지표 |
|---|---|---|
| P0 | Consistency | 초과 예약, 초과 판매, 중복 주문, 중복 차감·반환, 불변식 위반 모두 0건 |
| P0 | Throughput | 성공 예약 TPS, 구매 확정 TPS, 입장 신청·조회 RPS, 최대 지속 처리량 |
| P0 | Latency | 재고 점유, 입장 제어 API p50/p95/p99, 대기 체류 p95/p99, 전체 구매 소요 p95/p99 |
| P0 | 유입 제어 | 입장 허가율 제어, DB 커넥션 풀과 Lock Wait 보호, 5xx·타임아웃 억제, 정상 품절·대기 안내와 서버 오류 구분 |
| 확장 | Scalability | 서버 증설 전후 처리량, 지연 비교 |
| 확장 | Resilience | 장애 후 거래 복구 |
| 확장 | Efficiency | 같은 자원에서 처리 가능한 거래량, 비용 |

최종 기준: 정합성 위반 0건과 미리 정한 지연, 오류율 목표를 지키면서 달성 가능한 최대 지속 처리량을 높인다.

드롭의 목표, 진행 방식, 병목 기록은 [성능 개선 계획](drop-performance-plan.md), 측정 한 번을 돌리는 방법은 [실행 절차](drop-performance-procedure.md), 집계와 판정은 [측정 규약](drop-performance-measurement.md)에 둔다. 이번 범위는 한정 수량 판매의 쓰기 경로이며 PG 장애 복구 성능은 후속 과제다. 목표는 달성 결과나 운영 SLA가 아니다. 다른 도메인의 목표는 별도 계획을 따른다. 측정하지 않은 결과 수치는 쓰지 않는다.

## 3. 반복 방법

병목 하나를 풀고 다음 병목으로 넘어간다.

1. 측정해서 병목을 찾는다.
2. 원인을 확인하고 그 병목 하나만 고친다.
3. 같은 조건으로 다시 측정해 전후를 비교한다. 고치기 전에 예측을 한 줄 적는다.
4. 다음 병목을 찾는다. 목표에 닿으면 멈춘다.

- 한 번에 바꾸는 독립변인은 하나다.
- 매 실행 뒤 정합성 위반 0을 확인한다.
- 개선되지 않았으면 그 이유도 결과로 남긴다.
- 부하 생성기의 dropped iterations, CPU, 메모리 한계도 확인한다.
- 결과는 각자 PC의 `.ai-output/perf/<날짜>-<측정>/`에 측정 조건과 함께 남긴다. 원자료, 보고서, 성능 개선 기록은 레포에 올리지 않는다. `docs/`에는 준비 문서(전략, 계획, 절차, 측정 규약)만 둔다.

## 4. 개선 후보

순서대로 하는 실험 목록이 아니다. EXP-01 ~ 07은 개선 수단 후보이고, 3절의 반복에서 찾은 병목이 맞는 후보를 고른다. EXP-AU는 경매 도메인의 부하 테스트다. 드롭의 진행 상황은 [성능 개선 계획 5절](drop-performance-plan.md#5-병목-기록)에 있다.

| ID | 주제 | 비교 | 측정 |
|---|---|---|---|
| EXP-01 | 재고 동시성 제어 | SELECT→UPDATE, 비관적 락, 조건부 UPDATE | 초과 예약, 성공 TPS, p95/p99, Lock Wait |
| EXP-02 | 유입 제어 효과 | 입장 제어 끔, MySQL 입장 제어 | 예약 TPS, 오류율, p95/p99, 대기시간, DB 사용량 |
