# 드롭 성능 개선 계획: 병목을 하나씩 푼다

- 관련 이슈: [#130](https://github.com/prgrms-be-devcourse/NBE12-14-final-RESTLESS/issues/130), [#183](https://github.com/prgrms-be-devcourse/NBE12-14-final-RESTLESS/issues/183), [#318](https://github.com/prgrms-be-devcourse/NBE12-14-final-RESTLESS/issues/318)
- 범위: 한정 수량 판매의 쓰기 경로. 재고 점유와 입장 제어가 대상이다. PG 장애 복구 성능은 후속 과제다.
- 상태: 진행 중. 결과는 docs에 두지 않고 각자의 `.ai-output/perf/`에 둔다. 이 문서의 수치는 목표와 계획 입력이며 달성 결과나 운영 SLA가 아니다.
- 함께 보는 문서: [실행 절차](drop-performance-procedure.md)는 측정 한 번을 돌리는 방법, [측정 규약](drop-performance-measurement.md)은 집계와 판정 기준이다.

> 입장 제어는 SKU별 구매 입장 정책([policy.md 7-1절](../domains/drop/policy.md#7-1-sku별-구매-입장-제어-decided-2026-11-19-253), #253)을 따른다. #254에서 구현됐다. 2026-11-18 입장 제어 결과는 옛 동작(드롭 단위 입장, 재고를 보지 않는 입장)의 측정이라 근거로 쓰지 않는다. [열린 정책 질문](../product/open-questions.md)은 이 계획에서 정하지 않는다.

## 1. 목표

대표 시나리오는 재고 **1,000개**, 참여자 **10,000명**, 판매 시작 직후 최고 **1,000명/초**의 구매 시도다. 합성 경쟁 시나리오이며 실사용 예측이 아니다.

| 목표 | 기준 | 판정 |
|---|---|---|
| 정합성 | 초과 판매, 중복 주문, 이중 반환 0. 순판매 1,000 이하 | 실행마다 확인한다. 하나라도 어기면 그 개선은 채택하지 않는다 |
| 첫 응답 | 참여자별 첫 응답 p99 1초 이하, 예상 밖 오류율 0.1% 미만 | 첫 응답은 성공, 품절, 대기 안내 중 하나다. 타임아웃과 미전송을 숨기지 않는다 |
| 구매 경로 지연 | 점유 요청 p95 200ms 이하, p99 500ms 이하 | 성공과 품절을 따로 보고한다 |
| 지속 처리량 | 위 지연과 신규 성공률 99.9% 이상을 3분 지키는 C_final이 첫 C의 1.5배 이상. 도전 하한 300건/초 | 300은 모델로 아직 지지되지 않은 도전값이다. 지지되지 않으면 그 사실을 남긴다 |
| 입장 제어 비용 | 진입과 조회 p95 300ms 이하, p99 1초 이하 | 입장 제어를 개선 수단으로 쓸 때만 판정한다 |

목표는 정한 뒤 결과에 맞춰 낮추지 않는다. 미달도 결과로 남긴다. 지연, 정합성, 유입 달성, 부하 발생기 유효성을 모두 만족한 측정만 합격이다.

## 2. 진행 방식

병목 하나를 풀고 다음 병목으로 넘어가는 반복이다.

1. **측정해서 병목을 찾는다.** 3절의 용량 측정으로 지속 처리 용량 C와 먼저 포화한 자원을 본다.
2. **원인을 확인하고 고친다.** 4절 표로 병목을 판정하고, 그 병목 하나만 고친다. 한 번에 바꾸는 것은 하나다.
3. **같은 조건으로 다시 측정해 전후를 비교한다.** 고치기 전에 예측을 한 줄 적는다. 예측과 실측의 차이를 숨기지 않는다.
4. **다음 병목을 찾는다.** 목표에 닿으면 대표 판매 측정으로 최종 확인하고 멈춘다.

매 실행 뒤 정합성을 확인한다. 개선되지 않았으면 그 이유도 결과로 남긴다. 고칠 수단의 후보는 [성능 상위 계획 4절](performance.md#4-개선-후보)에 있다. 병목이 그 후보와 맞을 때 고른다.

## 3. 측정 두 가지

| 측정 | 묻는 것 | 조건 | 얻는 값 |
|---|---|---|---|
| 용량 측정 | 서버가 버티는 양과 병목 위치 | `capacity` 시드, 대기열 끔. 연속 증가 한 번으로 후보를 찾고, 고정 도착률 3분 유지로 확인한다 | C, 먼저 포화한 자원 |
| 대표 판매 측정 | 1절 목표 달성 여부 | `sale` 시드, 대표 시나리오. 대기열 끔과 켬을 같은 도착 시간표로 비교한다 | 첫 응답, 구매 지연, 품절 처리, 정합성 |

반복 중에는 용량 측정을 주로 쓴다. 대표 판매 측정은 큰 개선 뒤나 마지막 확인에 쓴다. 대기열 폴링 비용은 입장 제어가 개선 수단일 때만 따로 잰다 ([실행 절차 5절](drop-performance-procedure.md#5-대기열-폴링-측정)).

C는 연속 증가 중 순간 최대가 아니라 고정 도착률로 유지해 본 값이다. 연속 증가에서는 서버가 넘친 뒤에도 요청이 타임아웃 전까지 쌓였다가 늦게 성공해서 값이 높게 나온다.

입장 제어 on에서 참여자는 진입 때 SKU 하나를 고르고, 진입, 조회, 점유에 같은 SKU를 쓴다. 입장 수는 SKU마다 `min(max(0, available - 미사용 유효 ADMITTED 수), admit-per-run)`이다. 입장률은 C보다 낮게 둔다. SKU의 `available = 0`이면 신규 진입은 409 `DROP_SOLD_OUT`이고, 입장 허가 작업이 그 SKU의 `WAITING`과 미사용 `ADMITTED`를 `UNAVAILABLE`로 종료한다.

## 4. 병목 판정

먼저 포화한 자원을 찾는다. 한 지표만 보고 원인을 확정하지 않는다.

| 관측 조합 | 병목 후보 | 확인 방법 |
|---|---|---|
| Hikari 획득 대기와 대기 수 급증, DB와 앱은 여유 | 풀 또는 커넥션을 오래 쥐는 작업 | 커넥션 사용 시간, 트랜잭션 추적. 풀 상한 근사는 풀 크기 / 커넥션 사용 초 |
| SKU에 몰릴 때 잠금 대기 증가, 잠금 보유 구간이 김 | 핫 SKU 재고 행 | SKU 하나의 상한 근사는 1000 / 잠금 보유 ms, SKU k개면 k배. SKU 1개와 3개로 대조 |
| EC2 CPU 포화, runnable 스레드 증가, 지연 동반 | 앱 연산, GC | CPU, GC, 프로파일. 잠금 대기와 공존할 수 있다 |
| RDS CPU, IO 지연, 대기열 증가 | SQL, 저장장치 | SQL별 시간, 실행 계획, IO. 사양을 바꾸기 전에 쿼리 비용을 본다 |
| Tomcat 스레드 포화와 Hikari 대기 | 스레드 고갈의 상위 원인 | 커넥션 대기와 다른 대기를 구분한다. 스레드 수만 늘리지 않는다 |
| 클라이언트만 나빠지고 서버는 안정 | 부하 발생기, 네트워크 | 노트북 자원, 연결 지표. 근거가 없으면 미판정 |

## 5. 병목 기록

| 회차 | 병목 | 근거 | 개선 | 상태 |
|---|---|---|---|---|
| 1 | 핫 SKU 재고 행 잠금 | 2026-11-20 용량 측정. 잠금 모델이 SKU 1개와 3개 결과와 맞았다. 풀과 정상 상태 CPU는 먼저 포화하지 않았다 | TX1에서 재고 UPDATE를 마지막으로 옮겼다 (#322, PR #324). 잠금 보유는 9.64ms(11-20)에서 5.51ms(11-21)로 줄었다. SKU 1개 포화 처리량은 약 104건/초(11-20)에서 약 192건/초(11-21)로 올랐다 | 완료 |
| 2 | 같은 SKU 재고 행의 커밋 직렬화. 잠금 보유가 거의 전부 커밋이다 | 2026-11-21 커밋 구간 분리 측정. 잠금 보유 6.22ms 중 커밋 단계가 6.22ms였다. 앱에서 더 줄일 구간이 없었다 | SKU 재고를 버킷 K개로 나눴다 ([ADR-0005](../decisions/0005-drop-inventory-buckets.md), #330, PR #334). K=1은 약 159건/초에서 포화했다(11-22). K=4는 300건/초 도착까지 포화하지 않았다(11-23) | 완료 |
| 3 | EC2 앱 CPU | 2026-11-23 K=4 용량 측정. SKU 1개 포화 처리량은 약 345건/초다. 그때 EC2 CPU는 약 91%, RDS CPU는 약 86%였다. 같은 날 문장 캐시 측정에서는 EC2 CPU가 약 94%까지 올랐다. 핫 SKU 3개로 300건/초를 3분 유지하자 성공률은 99.97%였다. p95 336ms, p99 1,142ms로 지연 목표에 미달했다 | 두 가지를 시도했다. JDBC 문장 캐시로 SQL 파싱을 거의 없앴다. 세션 문장을 빼서 왕복을 20에서 17로 줄였다. 둘 다 요청당 CPU가 줄지 않아 채택하지 않았다 | 결정 대기 |

계획 입력값은 아래와 같다. 결과 자체는 `.ai-output/perf/`에 있다.

| 입력 | 값 | 쓰는 곳 |
|---|---|---|
| C (핫 SKU 3개, 고정 도착률 3분) | 200건/초. 220은 급진입 뒤 지연 목표를 깨서 200을 안전한 C로 둔다 | 1회차 개선 전 기준, 입장률 상한 |
| SKU 1개 포화 처리량 | K=4 약 345건/초(2026-11-23). 버킷 분할 전 값은 약 104건/초, 잠금 보유 평균 9.64ms(2026-11-20)다 | 잠금 모델 확인, SKU 하나의 입장률 상한 |
| 입장률 시작값 | 0.7 x C = 140건/초. 핫 SKU 3개, 주기 1초면 `admit-per-run` 약 47 | 대표 판매 측정의 대기열 켬 |

앱 CPU는 요청 처리 전반에 넓게 퍼져 있어 개별 최적화로 줄지 않았다. 남은 선택은 사람이 정한다. 입장 제어의 입장률 설정, 점유 때 주문을 만들지 않는 구조 변경(팀 결정), 사양 변경(예산 승인)이다. 위 값은 t3.small, RDS small, 로컬 k6 조건의 측정이다. 환경이나 이미지가 바뀌면 다시 잰다.

## 6. 결과 보고

결과는 `.ai-output/perf/<날짜>-<측정>/`에 둔다 (예: `2026-11-22-capacity-hold-200`). 원자료, 보고서, 개선 기록은 레포에 올리지 않는다.

회차마다 병목, 바꾼 것 하나, 변경 전 예측, 같은 조건 전후 비교, 정합성 결과, 남은 한계를 적는다. 전후 비교 표에는 C, p95와 p99, 잠금 보유, 먼저 포화한 자원을 나란히 둔다. 모델 예측 오차 (실측 - 예측) / 예측을 남긴다.

가짜 PG, 단일 앱, 공유 RDS, 로컬 k6, 측정 기간을 명시한다. 재고 점유를 PAID로, 품절 RPS를 성공 TPS로, 합성 용량을 실제 구매 완료 처리량으로 쓰지 않는다. PG 응답 유실 때의 돈과 재고 보호는 기존 정합성 테스트와 결제 정책으로 설명하고, 이 계획으로 입증했다고 쓰지 않는다.
