# 드롭 성능 실험: 한정 수량 판매와 과부하 제어

- 관련 이슈: [#130](https://github.com/prgrms-be-devcourse/NBE12-14-final-RESTLESS/issues/130), 기존 측정 추적 [#183](https://github.com/prgrms-be-devcourse/NBE12-14-final-RESTLESS/issues/183)
- 범위: 헤드라인 기준선 → 병목 연쇄(풀 → 잠금) → 입장 제어 켬/끔 → 폴링 비용. PG 장애 복구는 후속 과제.
- 상태: 계획. 2026-11-18에 1차 실행했다. 결과는 docs에 두지 않고 각자의 `.ai-output/perf/`에 둔다. 이 문서의 수치는 목표와 예산이며 달성 결과나 운영 SLA가 아니다. [실행 절차](drop-performance-procedure.md)와 [측정 규약](drop-performance-measurement.md)을 함께 적용한다.

> 입장 제어는 SKU별 구매 입장 정책([policy.md 7-1절](../domains/drop/policy.md#7-1-sku별-구매-입장-제어-decided-2026-11-19-253), #253)을 따른다. #254에서 구현됐다. 2026-11-18 H on 결과는 옛 동작(드롭 단위 입장, 재고를 보지 않는 입장)의 측정이라 이 계획의 근거로 쓰지 않는다.

## 1. 대표 시나리오와 질문

재고 **1,000개**, 참여자 **10,000명**, 판매 개시 직후 최고 **1,000명/초**로 구매를 시도한다. sale 시드(base와 같고 워밍업 드롭이 있다)와 10:1 경쟁 조건을 사용한다. 대표 실험 H에서는 품절을 피하려고 재고를 늘리지 않는다. [열린 정책 질문](../product/open-questions.md)을 임의로 결정하지 않는다.

입장 제어 on에서 참여자는 진입 때 SKU 하나를 고르고 그 SKU의 입장 순번을 받는다. 시나리오는 계정 순서대로 SKU를 돌아가며 배정하고 진입, 조회, 점유에 같은 SKU를 쓴다. off의 점유 배정과 같다. SKU의 `available = 0`이면 그 SKU는 현재 구매 불가가 된다. 신규 진입은 409 `DROP_SOLD_OUT`으로 거절되고, 입장 허가 작업이 그 SKU의 `WAITING`과 미사용 `ADMITTED`를 `UNAVAILABLE`로 종료한다. 따라서 품절 뒤 대기 인원은 0으로 수렴해야 한다. 측정 대상은 첫 `available = 0`부터 종료 완료까지 걸린 시간, 종료된 대기 수, 진입 거절 수다. 점유 만료나 결제 실패로 재고가 반환되면 새 진입부터 다시 받는다. 종료된 입장 순번은 복구하지 않는다. 반환 뒤 재진입은 관측하되 H의 판정 대상이 아니다.

결과는 다음 질문에 답해야 한다.

1. 목표 숫자를 어떤 시나리오·사용자 응답 예산·자원 모델에서 유도했는가?
2. 풀·행 잠금·CPU 중 어떤 병목이 먼저 나타나는가? 풀을 더 늘려도 도움이 되는가?
3. 잠금 보유 시간 축소의 효과 예측은 맞는가? 품절 롤백·마감 재검증·교착 비용은 무엇인가?
4. 같은 유입에서 입장 제어는 구매 경로를 보호하는가? 폴링 비용은 얼마인가?
5. 품절 후 요청은 어떤 DB 작업을 일으키는가? 입장 제어 on에서 대기가 종료되기까지 사용자는 얼마나 기다리는가?
6. 어떤 환경·대기 인원·시간 범위 밖에서는 이 결론을 적용할 수 없는가?

PG 응답 유실 시 돈·재고 보호는 기존 정합성 테스트와 결제 정책을 근거로 별도 설명하되, 이번 실험으로 복구 성능을 입증했다고 쓰지 않는다.

## 2. 가설과 변경 전 예측

| 가설 | 모델·확인 | 반증·비용 |
|---|---|---|
| 연결 획득 대기가 첫 병목 | 풀 상한 근사 C_pool=P/E[연결 사용 초]. 기존 run4의 P=20, 평균 23ms면 약 870건/초 | 현재 조건에서 재측정. 평균값·연결 다중 획득·작업 혼합 때문에 상한 증명이 아님. 풀 10/20/40과 CPU·DB 지표로 대조 |
| 핫 SKU 잠금이 다음 병목 | SKU별 C_lock≈1,000/E[잠금 보유 ms], 균등 k개면 k×C_lock. 잠금 획득 완료→커밋까지 먼저 측정 | SKU 1/3개에서 증가 방향·크기를 비교. 3배는 다른 병목이 없을 때만 기대. CPU·IO·공통 작업 포화면 잠금 단독 가설 기각/수정 |
| 잠금 구간 축소로 용량 확대 | 현재 holdOne 뒤 주문·품목·배송·점유 INSERT, 슬롯 UPDATE, 조회가 이어짐. 변경 전/후 예상 잠금 시간과 C_pred를 실행 전 기록 | 품절 시 선행 INSERT 롤백 비용, 종료 시각/입장 허가 재확인, 잠금 순서·교착을 평가. 정합성 조건은 유지 |
| 입장 제어가 구매 경로 보호 | 입장률을 실측 처리 용량 C보다 낮게 두고 같은 회원 도착 시간표로 on/off 비교. 입장 수는 SKU마다 `min(max(0, available - 미사용 유효 ADMITTED 수), admit-per-run)`이다. 재고가 남은 동안 드롭 전체 입장률은 SKU 수 x `admit-per-run` / 입장 허가 작업 한 주기로 근사한다 | 폴링은 heartbeat 쓰기와 입장 순번 COUNT를 발생시킴. 전체 비용과 대기 시간도 함께 비교. 재고가 적으면 `available`이 먼저 입장을 막으므로 `admit-per-run`만으로 입장률이 정해지지 않는다. 실제 입장률은 `drop.queue.admitted` 증가율로 확인 |

입장 제어 실험의 입력값은 아래와 같다. 2026-11-20 B2와 SKU 1개 대조에서 얻었다. 결과 자체는 `.ai-output/perf/`에 있고 여기에는 계획 입력만 둔다.

| 입력 | 값 | 쓰는 곳 |
|---|---|---|
| C (핫 SKU 3개, 고정 도착률 3분 유지) | 200건/초. 220은 30에서 바로 올렸을 때 약 90초 동안 지연 목표를 깼다. 그래서 200을 안전한 C로 둔다 | 입장률 상한 |
| 입장률 시작값 후보 | 0.7 x C = 140건/초. 핫 SKU 3개, 주기 1초면 `admit-per-run` 약 47에 해당한다. 주기에는 작업 실행 시간이 더해지므로 실측으로 맞춘다 | H on 첫 실행 |
| SKU 1개 포화 처리량 (capacity_single) | 약 104건/초, 잠금 보유 평균 9.64ms. 1,000 / 9.64와 맞는다 | SKU 하나에 몰리는 입장률의 상한. SKU별 입장률이 이 값을 넘지 않게 둔다 |

이 값은 t3.small, RDS small, 로컬 k6 조건의 측정이다. 다른 환경이나 이미지에서는 다시 잰다.

기존 풀 실험(2026-11-17)은 이미지, 워밍업, 만료 경합이 통제되지 않아 새 기준선으로 쓰지 않는다. 풀 10→20은 독립 성과 목표가 아니라 병목 연쇄 재현이다. run3 HTML 근사값은 정량 비교에서 제외한다.

## 3. 목표와 판정

헤드라인 H의 1,000개·10,000명·최고 1,000명/초는 합성 경쟁 시나리오이며 실사용 예측이 아니다. 첫 응답 1초는 대기 안내까지 포함한 피드백 예산, 구매 200/500ms는 짧은 DB 거래의 실험 예산이다. 아래 제안값은 통제 기준선과 모델을 측정한 뒤 **한 번 확정**해 날짜·근거·예측값을 기록한다. 이후 결과에 맞춰 낮추지 않으며 미달도 결과로 남긴다.

| 목표 | 실험 전 제안 기준 | 판정·보고 |
|---|---|---|
| 정합성 | 초과 판매·중복 주문·이중 반환 0, 순판매 ≤1,000 | 실제 실행한 검사와 대상 불변식 명시. 하나라도 위반하면 변경 채택 불가 |
| 대표 H 첫 응답 | 참여자별 최초 구매/대기 진입 응답 p99 ≤1초, 예상 밖 오류율 <0.1% | 성공·품절·대기 안내 중 하나. timeout·미전송을 숨기지 않음. 10,000명 유입 달성 여부 별도 판정 |
| H 구매 경로 | 허가된 점유 요청 평가 지연 p95 ≤200ms·p99 ≤500ms | 성공·품절 별도 보고. 버스트부터 잔존 대기 최고 부하와 배출 구간까지 평가 |
| 보조 B 지속 용량 | 지연 200/500ms·신규 성공률 ≥99.9%를 3분 지키는 C_final ≥1.5×C_base, 도전 하한 300건/초 | 300은 모델에서 아직 유도되지 않은 도전값. 잠금 시간 측정 후 예측으로 지지되는지 기록. 지지되지 않으면 근거 없는 수치를 확정하지 않음 |
| 품절 경로 | 품절 p95 ≤동일 조건 성공 p95를 개선 가설로 검증 | 입장 제어 off는 조건부 재고 UPDATE가 품절을 판정한다. 재고 행 잠금 없는 거절은 off 경로의 최적화 후보이고 현재 구현 사실이 아니다. on은 진입이 `available = 0`을 읽고 409로 거절한다. 남은 대기는 입장 허가 작업이 종료하며, 진입 직후 작업 한 주기만큼 지연을 허용한다. on과 off의 품절 응답은 경로가 달라 따로 보고한다 |
| 입장 제어 비용 | 확인된 인원 범위에서 진입/조회 p95 ≤300ms·p99 ≤1초, 예상 밖 오류율 <0.1% | 대기 1,000명당 DB 비용과 수용 가능한 최대 인원 보고. 생성기 한계와 서비스 한계 구분 |
| 사용자 지표 | 수치 판정 없이 모두 공개 | PAID TPS, 진입→PAID 및 대기 체류 p50/p95/p99, 미완료, 이탈 인원, 진입 거절과 `UNAVAILABLE` 종료 수, 첫 `available = 0`부터 종료 완료까지 시간 |

H on/off의 성공·품절·대기 응답 분포는 같지 않다. 경쟁률 10:1만으로 응답의 90%가 품절이라고 가정하지 않는다. G5 독립 복귀 목표는 두지 않는다. 구매 경로가 계속 보호됐는지 또는 얼마나 악화되고 회복됐는지를 H 결과로 함께 보고한다. 지연·정합성·유입 달성·생성기 유효성을 모두 만족한 조건만 합격이다. 보조 용량의 달성이 대표 판매 시나리오의 달성을 대신하지 않는다.

## 4. 결과 보고 형식

결과는 각자 PC의 `.ai-output/perf/<날짜>-<실험>/`에 둔다(예: `2026-11-19-h-off-1`). 원자료, 보고서, 성능 개선 기록은 레포에 올리지 않는다.

환경·초기 데이터 → 가설과 변경 전 예측 → 변경 하나 → 동일 조건 비교 → 정합성 검사 → 비용·반증·남은 한계 순서로 작성한다. 대표 그림은 H on/off의 같은 시간축에서 회원 유입·구매 p99·오류·실제 입장률·대기 인원·폴링 RPS·DB 대기를 나란히 놓는다. 품절 시각과 만료 처리도 표시한다.

측정 지연과 처리량의 실행별 원값·중앙값·범위를 공개하고, 모델 예측 오차=(실측-예측)/예측을 기록한다. 정합성 위반 0은 검사 범위를 붙이며 가짜 PG·단일 앱·공유 RDS·로컬 k6·측정 기간을 명시한다. 재고 점유를 PAID로, 품절 RPS를 성공 TPS로, 합성 용량을 실제 구매 완료 처리량으로 표현하지 않는다.
