# 드롭 성능 측정 규약

[목표·가설](drop-performance-plan.md) / [실행 절차](drop-performance-procedure.md)

> **정책 변경 표시 (2026-11-19, #253): 이 문서의 대기열 설명 일부가 새 정책과 충돌한다.**
> 대기열은 SKU별이 되고, 입장 수는 `max(0, available - 미사용 유효 ADMITTED 수)`로 제한된다. SKU의 `available = 0`이면 `reserved`와 무관하게 신규 진입과 발급을 중단하고 그 SKU의 `WAITING`과 미사용 `ADMITTED`를 종료한다(현재 구매 불가). 재고가 반환되면 새 진입으로 재개하고 종료된 순번은 복구하지 않는다 ([policy.md 7-1절](../domains/drop/policy.md#7-1-sku별-구매-입장-대기열-decided-2026-11-19-253)).
> 이 문서와 측정 결과는 새 구현 전의 현재 동작(드롭 단위, 재고를 보지 않는 입장, 판매 기간 종료 전에는 품절만으로 대기를 닫지 않음)을 기준으로 쓰였다. 2026-11-18 H on 결과도 그 동작의 측정이다. 구현 뒤 대기열 실험을 다시 하기 전에는 새 정책의 결과로 쓰지 않는다. 아래 충돌 항목은 본문을 고치지 않고 표시만 한다.

| 위치 | 충돌하는 현재 동작 설명 | 새 정책 |
|---|---|---|
| 3절 | 품절 뒤 남은 대기자 수와 추가 대기 시간을 첫 `available = 0`, 마지막 반환, 최종 순판매 1,000 기준으로 보고 | `available = 0`이면 대기가 종료된다. 첫 `available = 0`부터 종료 완료까지 걸린 시간, 종료된 대기 수, 반환 뒤 재진입 수를 보고해야 한다 |
| 3절 | WAITING 수와 실제 admitted/s | `admitted`가 재고로 제한된다. 진입 거절(409) 수와 `UNAVAILABLE` 종료 수를 별도 지표로 본다 |
| 5절 정합성 검사 | 검사 범위는 INV-01, 02, 03, 04, 05, 07, 08, 09 | INV-16(구매권이 `available`을 넘지 않음), INV-17(`available = 0` 뒤 대기 없음)이 추가된다. SQL 검사는 `variant_id` 구현 뒤 가능하다 |

## 1. 단위·분모·판정 구간

iteration은 새 회원의 거래 흐름, HTTP RPS는 폴링·결제를 포함한 API 요청 수다. 점유 성공 TPS와 PAID 커밋 TPS를 구분한다. H 첫 응답은 회원 도착 후 첫 구매 API(off) 또는 대기 진입 API(on) 응답이며 결제 완료가 아니다. H의 미전송 회원도 전체 참여자에서 제외하지 않는다.

계획 P, 실제 시작 S, 미전송 D, 완료 F, 시작했지만 미완료 I를 분리한다. iteration 첫 줄의 사용자 정의 started와 모든 종료 경로 finished를 기록한다. I=S-F이며 S에 다시 더하지 않는다. 정상 드레인 후 P=S+D, S=F+I를 대조한다. 예정이 10,000명인데 초과 skip이 생긴 경우 skip을 성공이나 참여자로 세지 않는다. H는 10,000명 모두의 예정 도착·실제 시작·결과를 대조한다. 집계 불일치는 원인 확인 전 미판정이다.

B 신규 성공률=신규 점유 성공/P. H는 품절/대기가 정상일 수 있어 구매 성공률 99.9%를 요구하지 않는다. H의 예상 밖 오류율은 해당 API의 실제 시작 요청을 분모로 계산하고, 예정 회원 대비 첫 응답 미획득률·미전송률도 별도 보고한다. API별로도 오류를 집계해 높은 폴링량이 구매 오류를 희석하지 않게 한다.

B 연속 증가는 30초 창별 탐색이며 최종 판정은 유지 3분 전체와 30초 창이다. H는 버스트부터 폴링 최고점·품절·잔존 대기 배출/최대 관측 종료까지 전체와 10초 창을 함께 공개한다. 표본 수를 표시하고 적은 표본의 p99를 확정적 값으로 해석하지 않는다. 구간 분위수를 평균해 전체 분위수라고 쓰지 않는다. 요청 시작 창에 귀속해 느린 완료가 뒤 창으로 밀리는 효과를 분리한다.

## 2. 오류와 지연

재고·대기열 HTTP timeout은 5초다. 결제는 가짜 PG 300ms·정상 모드에서 별도 timeout 설정을 기록한다. 5xx·연결 실패·timeout·예상 밖 4xx는 오류다. 정상 품절은 별도 결과이며 잘못된 구매권·판매 기간 설정을 정상 거절로 숨기지 않는다.

평가용 지연은 실제 응답(오류 포함)의 경과시간과 timeout 실패의 설정 한도(재고·대기열 5,000ms)를 포함한다. 이는 우측 절단 지연이며 실제 완료시간이 아니다. 즉시 전송 실패는 0ms로 넣지 않고 별도 실패 수·관측 경과시간으로 보고하며 첫 응답 미획득에 포함한다. 실제 응답만/신규 성공만/품절만 지연도 나란히 제시한다. H 첫 응답은 요청 시작까지의 생성기 스케줄 지연을 별도 보고하고, 사용자 관점 예정 도착→첫 응답 분포도 함께 공개한다.

합격은 클라이언트 평가 지연·오류·부하 달성으로 판정한다. 원인 분석은 http.server.requests와 drop.reservation.duration 서버 히스토그램을 사용한다. 서버 지연과 클라이언트 지연을 같은 구간에 병기하되 서로 다른 분위수의 차이를 정확한 네트워크 시간으로 해석하지 않는다. drop.reservation.duration의 결과 태그(성공/품절 분리)는 #217에서 추가한다. ID를 메트릭 태그에 넣지 않는다.

## 3. 사용자·품절·폴링 지표

- PAID TPS와 성공 점유 TPS, 최종 available/reserved/sold·순판매량.
- 입장 진입→ADMITTED 대기 체류, 최초 진입→PAID 전체 구매 시간 p50/p95/p99. 완료 수와 미완료·중도 이탈·관측 종료로 잘린 수를 항상 함께 표시한다.
- 품절/대기/실패로 종료한 사람의 최초 진입→최종 결과 시간도 별도 분포로 제시한다.
- 최초 가용 재고 0 시각, 마지막 재고 반환 시각, 최종 순판매 1,000 확정 시각을 구분한다. 각 기준 뒤에도 남은 대기자 수와 추가 대기 시간(관측 종료까지 미완료 포함)을 보고한다.
- 품절 응답 p95/p99와 품절 이후 요청당 SQL 시도 수·DML 실행/롤백·재고 UPDATE/잠금 시도. 롤백된 DML을 DB 쓰기 0이라고 하지 않는다. 스키마/세션별 계측을 준비하고 전체 RDS 수치를 요청당 비용으로 오인하지 않는다.
- WAITING 수·실제 admitted/s·폴링 RPS·404/이탈, 대기 1,000명당 SQL/s·검사 행/s·CPU/IO 변화. CPU 변화는 퍼센트포인트로 보고하며 선형 확장 가능성을 전제하지 않는다.

## 4. 수집·실행 유효성

k6 원자료에 UTC·scenario·phase·창·outcome·예정/실제 도착을 보존하고, Prometheus는 5초 간격 수집한다. k6 요약 JSON과 로그도 저장한다. before/after만으로 창별 원인을 주장하지 않는다. EC2/RDS의 CPU·메모리·IO·크레딧, Hikari acquire/usage/pending/timeout, Tomcat busy, JVM GC와 잠금 지표를 같은 시간축에 맞춘다.

RDS SHOW GLOBAL STATUS는 인스턴스 전체 값이다. 다른 DB 작업 부재를 확인하거나 schema/thread별 Performance Schema와 대조한다. 전역 lock wait/우리 요청 수를 요청별 잠금 확률이라고 표현하지 않는다. CPU 포화와 잠금 대기는 공존할 수 있어 먼저 포화된 자원과 반증 결과를 함께 해석한다.

생성기 장애가 독립 근거로 확인되면 실행 무효·재실행, 서버 기인 지연·미전송은 성능 실패, 원인 미상은 미판정이다. B 합격 구간은 dropped=0. H도 예정 10,000명을 만들지 못하면 원래 시나리오 달성으로 인정하지 않는다. 감소·skip으로 그래프를 매끈하게 만들지 않는다.

중단 기준은 30초 창 오류율 ≥5% 또는 p99 ≥3초가 두 창 지속, OOM/프로세스 종료, 정합성 위반이다. H는 짧아서 조건이 늦게 발동할 수 있으므로 오류·자원 고갈을 실시간 관찰하고 중단 시각·이유를 기록한다. 종료 시점 threshold나 창 태그만으로 실시간 중단이 구현됐다고 가정하지 않는다.

최종 H on/off·B 기준선/최종 유지는 각 3회. B 탐색·Q는 조건당 1회다. 반복 편차가 10%를 넘으면 워밍업·환경을 조사하고 불확실성을 남긴다. 실패 실행을 중앙값으로 숨기지 않고 목표는 각 실행별 평가한다. Q의 최대 인원은 1회 탐색 결과임을 명시한다.

## 5. 정합성과 변경 안전망

기존 SQL 검사 범위는 INV-01·02·03·04·05·07·08·09다. B는 queue.required=false라 INV-06 대상이 아니다. H on에는 유효 CONSUMED 구매권과 신규 점유의 대응·개수 검사를 추가한다. 각 실행의 신규 성공 수와 DB 신규 점유·주문 수, 승인·PAID·재고 수량을 초기값 대비 대조한다. 전체 불변식을 SQL 하나로 입증했다고 쓰지 않는다.

재시도·중복 confirm·중복/동시 환불·늦은 결과·이중 반환·판매 마감·이전 결제 시도 격리는 해당 통합·동시성 테스트의 실제 실행 결과로 제시한다. 변경한 경로에 맞는 모듈 경계·동시성·전체 빌드를 수행한다. 이번 문서 작성은 해당 테스트 실행이 아니다. PG I/O 중 TX 금지, 코어 상태 TX 내 커밋 등 기존 정책을 성능 때문에 바꾸지 않는다.
