# 드롭 성능 측정 규약

[계획과 진행 방식](drop-performance-plan.md) / [실행 절차](drop-performance-procedure.md)

측정 결과를 어떻게 세고 판정하는지 정한다. 입장 제어 설명은 SKU별 구매 입장 정책([policy.md 7-1절](../domains/drop/policy.md#7-1-sku별-구매-입장-제어-decided-2026-11-19-253), #253, #254)을 따른다.

## 1. 단위, 분모, 판정 구간

- iteration은 새 참여자의 거래 흐름이다. HTTP RPS는 폴링과 결제를 포함한 API 요청 수다. 점유 성공 TPS와 PAID 커밋 TPS를 구분한다.
- 대표 판매 측정의 첫 응답은 참여자 도착 뒤 첫 구매 API(대기열 끔) 또는 대기 진입 API(대기열 켬)의 응답이며 결제 완료가 아니다. 미전송 참여자도 전체 참여자에서 빼지 않는다.
- 계획 P, 실제 시작 S, 미전송 D, 완료 F, 시작했지만 미완료 I를 나눈다. I = S - F다. 정상 드레인 뒤 P = S + D, S = F + I를 대조한다. 초과 skip을 성공이나 참여자로 세지 않는다. 집계가 어긋나면 원인을 찾기 전까지 미판정이다.
- 용량 측정의 신규 성공률은 신규 점유 성공 / P다. 대표 판매 측정은 품절과 대기가 정상일 수 있어 구매 성공률 99.9%를 요구하지 않는다. 예상 밖 오류율은 해당 API의 실제 시작 요청을 분모로 하고, 첫 응답 미획득률과 미전송률을 따로 보고한다. 오류는 API별로도 세서 많은 폴링이 구매 오류를 희석하지 않게 한다.
- 용량 측정의 연속 증가는 30초 창별로 보고, 판정은 고정 도착률 3분 전체와 30초 창으로 한다. 대표 판매 측정은 버스트부터 관측 종료까지 전체와 10초 창을 함께 공개한다.
- 표본 수를 표시하고 적은 표본의 p99를 확정 값으로 해석하지 않는다. 구간 분위수를 평균해 전체 분위수라고 쓰지 않는다. 요청을 시작 창에 귀속해 느린 완료가 뒤 창으로 밀리는 효과를 나눈다.
- 매분 00 ~ 02초에 응답이 잠깐 멈추는 현상이 관측된 적이 있다. 크기와 원인 조사 결과는 [#391](https://github.com/prgrms-be-devcourse/NBE12-14-final-RESTLESS/issues/391)에 있다. 창별 p95는 그대로 보고하고, 매분 00 ~ 02초에 시작한 요청을 뺀 p95를 함께 적는다. 두 값이 다르면 그 영향이라고 표시한다.

## 2. 오류와 지연

- 재고와 입장 제어 HTTP 타임아웃은 5초다. 결제는 가짜 PG 300ms에서 따로 정한 타임아웃을 기록한다.
- 5xx, 연결 실패, 타임아웃, 예상 밖 4xx는 오류다. 정상 품절, 진입 409, `UNAVAILABLE` 종료는 별도 결과다. 잘못된 입장 허가나 판매 기간 설정을 정상 거절로 숨기지 않는다.
- 평가용 지연은 실제 응답(오류 포함)의 경과 시간과, 타임아웃 실패의 설정 한도 5,000ms를 넣는다. 실제 완료 시간이 아니다. 즉시 전송 실패는 0ms로 넣지 않고 따로 센다. 실제 응답만, 신규 성공만, 품절만의 지연도 나란히 둔다.
- 합격은 클라이언트 평가 지연, 오류, 부하 달성으로 판정한다. 원인 분석은 서버 히스토그램 `http.server.requests`, `drop.reservation.duration`으로 한다. 서로 다른 분위수의 차이를 정확한 네트워크 시간으로 해석하지 않는다. ID를 메트릭 태그에 넣지 않는다.

## 3. 사용자, 품절, 대기 지표

- PAID TPS와 성공 점유 TPS, 최종 available, reserved, sold, 순판매량
- 진입부터 ADMITTED까지 대기 시간, 첫 진입부터 PAID까지 전체 구매 시간의 p50, p95, p99. 완료 수와 미완료, 이탈, 관측 종료로 잘린 수를 항상 함께 적는다
- 품절, 대기 종료, 실패로 끝난 참여자의 첫 진입부터 최종 결과까지 시간
- 첫 `available = 0` 시각부터 대기 종료 완료까지 걸린 시간, 종료된 대기 수, 진입 거절 409 수, 반환 뒤 재진입 수, 최종 순판매 1,000 시각
- 품절 응답 p95와 p99, 품절 뒤 요청당 SQL 수와 재고 UPDATE 시도. 롤백된 DML을 DB 쓰기 0이라고 하지 않는다
- 대기 수, SKU별 실제 admitted/s, 폴링 RPS, 대기 1,000명당 SQL/s와 CPU, IO 변화. CPU 변화는 퍼센트포인트로 보고하고 선형 확장을 전제하지 않는다

## 4. 수집과 실행 유효성

- k6 원자료에 UTC, 시나리오, 단계, 창, 결과를 남기고 서버 지표는 5초 간격으로 수집한다. k6 요약과 로그도 저장한다. 실행 전후 스냅샷만으로 창별 원인을 주장하지 않는다.
- EC2와 RDS의 CPU, 메모리, IO, 크레딧, Hikari 획득, 사용, 대기, 타임아웃, Tomcat busy, JVM GC, 잠금 지표를 같은 시간축에 맞춘다.
- RDS `SHOW GLOBAL STATUS`는 인스턴스 전체 값이다. 다른 DB 작업이 없음을 확인하거나 schema와 thread별 Performance Schema와 대조한다. CPU 포화와 잠금 대기는 함께 나타날 수 있어 먼저 포화한 자원과 반증 결과를 같이 해석한다.
- 판정 회차의 k6는 앱 서버와 같은 리전, 같은 서브넷의 EC2에서 돌린다. 노트북 k6는 축소 시드 진단에만 쓰고 그 결과로 합격과 실패를 판정하지 않는다. 2026-11-27 오전 노트북 k6 회차에서 TCP 연결 시간이 1, 2, 3, 4초로 뛰는 SYN 재전송 모양이 나타났고 회차가 무너졌다. 같은 순간 ALB 노드 두 개와 ALB를 거치지 않는 EC2 SSH 대상까지 세 곳의 연결 프로브가 함께 느려져 원인은 서버가 아닌 노트북이나 집 네트워크였다. 같은 서브넷의 m7g.xlarge로 옮긴 뒤 연결 p95는 36ms에서 1ms로 줄었다. 참여자 10,000명에 k6 메모리 약 6.9GB, CPU 5 ~ 30%를 썼다.
- 판정 회차에는 앱 서버에서 vmstat(1초)만 돌린다. 서버 지표 수집은 부하 발생기에서 관리 포트를 읽는다. DB 통계(performance_schema digest, prepared_statements_instances, global_status)는 판매 직전 한 번, 판매 시작 약 20초 뒤 한 번 DB 호스트에서 읽고 차이를 본다. 잠금 대기 폴링, 0.2초 단위 문장 폴링, async-profiler나 JFR profile 같은 CPU 프로파일러는 별도 진단 회차에서만 쓴다. 진단 회차는 합격과 실패 판정에 쓰지 않는다. 2026-11-28 앱 서버 p3에서 0.2 ~ 1초마다 mysql 클라이언트를 띄우는 수집기가 돌았다. 모든 회차에서 p3만 점유와 승인이 2.5 ~ 3.5배 느렸다. CPU 크레딧은 충분했지만 부하가 없는 동안 p3의 CPU 사용률은 17 ~ 38%로 다른 서버의 0 ~ 4%보다 높았다. 서버 쪽 점유 p95는 p3가 716ms, 나머지가 201 ~ 224ms였고 전체 p95를 끌어올렸다. 수집기를 뺀 뒤 같은 코드가 실패로 보이던 기준을 통과했다.
- 회차마다 서버별 유효성을 검사한다. 서버별 점유(201) p95와 승인(200) p95는 각 서버의 `http_server_requests_seconds` 히스토그램에서 구한다. 점유는 `uri="/api/drops/{dropId}/reservations"`, `status="201"`이고 승인은 `uri="/api/payments/confirm"`, `status="200"`이다. 측정 전과 후 스냅샷의 `le`별 버킷 누적값 차이를 쓰고 `+Inf`는 뺀다. 마지막 버킷 누적값을 전체 수로 보고, 누적값이 처음 0.95 x 전체 이상이 되는 버킷 안에서 앞 버킷 경계와의 선형 보간으로 p95를 정한다. 판매 전 CPU는 서버마다 vmstat의 판매 시작 8초 전부터 1초 전까지 7행의 busy(100 - idle) 평균이다.
  - R1: 어느 서버의 점유 p95 또는 승인 p95가 나머지 서버 값의 중앙값의 1.5배를 넘으면 그 회차는 무효다.
  - R2: 어느 서버의 판매 전 CPU가 나머지 서버 값의 중앙값보다 10%p 넘게 높으면 그 회차는 무효다. 판매 전 vmstat 행이 5개보다 적으면 R2는 판정 불가로 적고 무효로 보지 않는다.
  - 무효 회차는 한 번 다시 돌린다. 전체 p95만으로 판정하지 않는다. 서버별 p95, 요청 수, 판매 전 CPU와 R1, R2 결과를 보고서에 남긴다.
- 노트북 진단 회차에서 macOS 부하 발생기의 임시 포트 범위는 32768 ~ 65535를 포함해야 하고 TCP MSL은 1000ms 이하여야 한다. 사전 검사 실패 시 실행하지 않는다. k6 로그에서 `can't assign requested address` 또는 dial 오류가 1건 이상이면 해당 회차는 부하 발생기 무효다. 두 오류 건수는 각각 세며 한 로그 줄이 양쪽에 포함될 수 있다. 검사 결과를 측정 보고서에 남긴다. 로그가 없거나 비어 있으면 부하 발생기 유효성을 판정할 수 없다.
- 부하 발생기 장애가 독립 근거로 확인되면 실행 무효와 재실행, 서버 탓의 지연과 미전송은 성능 실패, 원인 미상은 미판정이다. 용량 측정의 합격 구간은 dropped 0이다. 대표 판매 측정이 [계획 1절](drop-performance-plan.md#1-목표) 시나리오의 참여자 수를 만들지 못하면 원래 시나리오 달성으로 인정하지 않는다.
- 중단 기준은 30초 창 오류율 5% 이상 또는 p99 3초 이상이 두 창 이어짐, OOM이나 프로세스 종료, 정합성 위반이다. 중단 시각과 이유를 기록한다.

## 5. 반복 횟수

- 병목을 찾는 측정은 조건당 1회다.
- 개선 효과는 같은 조건 전후 1회씩으로 먼저 본다. 차이가 20% 미만이거나 결론을 바꿀 만큼 흔들리면 전후 각 3회로 확인한다.
- Drop perf의 기준선은 JFR `settings=default`로 잰다. 개선 전후는 같은 JFR 모드로 잰다. JFR을 켠 회차와 끈 회차, default 회차와 profile 회차의 성능 지표는 직접 비교하지 않는다.
- 반복 편차가 10%를 넘으면 워밍업과 환경을 조사하고 불확실성을 남긴다. 실패 실행을 중앙값으로 숨기지 않는다.

## 6. 정합성과 변경 안전망

- 실행마다 `verify`를 돌린다. 검사 범위는 드롭 INV-01 ~ 09, 금액, FK 고아 행이다. 대기열 켬에서는 INV-16(입장 허가가 `available`을 넘지 않음), INV-17(`available = 0` 뒤 남은 대기 없음)도 대상이다. 이 둘의 SQL 검사가 없으면 수용 테스트 결과로 대신하고 그 사실을 적는다.
- 각 실행의 신규 성공 수를 DB의 신규 점유, 주문, 승인, PAID, 재고 수량과 초기값 대비로 대조한다. 전체 불변식을 SQL 하나로 입증했다고 쓰지 않는다.
- 코드를 바꾼 회차는 바꾼 경로의 통합 테스트, 동시성 테스트, 모듈 경계 테스트, 전체 빌드를 돌린다. PG 호출 중 트랜잭션 금지, 코어 상태의 트랜잭션 안 커밋 같은 기존 정책을 성능 때문에 바꾸지 않는다.
