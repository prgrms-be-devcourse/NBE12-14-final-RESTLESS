# 티켓팅 주최자 정책

> 상태: DECIDED (2026-11-26 개정). 2026-11-24 MVP 축소안을 대체하는 정본이다. 구현 완료를 의미하지 않는다.
>
> 이 문서는 정책만 다룬다. 현재 구현, 정책과의 차이, 예정 스키마는 [구현 계약](organizer-implementation.md)에, 요청·응답은 [API 계약](../../contracts/api/ticketing.md)에 있다. 관리 화면은 프론트 담당 범위다.

## 1. 범위

공연 등록(공연장·배치 선택) → 공통 구역별 등급·가격 설정 → 회차 개별·일괄 등록과 판매 좌석 생성 → 공연 전체 공개 → 고객 예약.

공개 뒤에는 회차 추가, 비공개 전환·재공개, 주최 측 취소(전액 환불)와 삭제를 지원한다.

| 기능 | 범위 |
|---|---|
| 관리 조회 | 공연 목록·상세, 회차 목록·설정 현황, 등록 배치 조회. 검색·필터 제외 |
| 공연 초안 | 공연장·배치·제목·소개·기간·소요 시간·예매 오픈 시각 등록, 공통 구역별 등급·가격 설정 |
| 회차 | 개별·일괄(1~10개) 등록, 공개 전 개별 수정, 공개 뒤 추가 |
| 공개 | 공연 단위 공개·비공개·재공개. 회차별 공개는 없다 |
| 취소·삭제 | 주최 측 공연·회차 취소(100% 환불), 환불 완료 뒤 soft delete |

## 2. 권한

- ORGANIZER는 본인 공연·회차만 관리한다. ADMIN은 모든 공연·회차에 같은 주최자 기능을 수행한다.
- ADMIN도 이 문서의 모든 제한을 똑같이 따른다. 제한을 넘는 관리자 예외 수정·삭제는 없다.
- 다른 주최자 이름으로 공연을 대신 등록하지 않는다. 기존 공연의 소유자는 바꾸지 않는다.
- ORGANIZER가 다른 주최자의 공연에 접근하면 없는 공연과 같이 404다.

## 3. 공연 상태

| 개념 | 의미 |
|---|---|
| 공개 여부 | 공개 또는 비공개. 고객 노출과 새 선점 허용 여부를 정한다 |
| 공개 이력 | 한 번이라도 공개했는지. 비공개로 돌려도 남는다. 정책 전환 전 기존 공연은 이력이 있다 |
| 취소됨 | 주최 측 전체 취소를 요청한 공연. 되돌릴 수 없다 |
| 삭제됨 | soft delete. 모든 조회에서 없는 공연으로 다룬다. 거래·티켓 이력은 남는다 |

```
초안(비공개, 이력 없음) ──공개──▶ 공개 ──비공개 전환──▶ 비공개(이력 있음) ──전체 취소──▶ 취소됨
      │                            ◀──재공개──┘           │                             │
      └─삭제(회차 포함)─▶ 삭제됨          예약 없음: 삭제 ─┘          환불 모두 완료: 삭제 ─┘
```

## 4. 예매 시간

- 예매 오픈 시각은 공연에 하나만 둔다. 모든 회차가 같은 값을 쓰며 회차 등록·수정에서 따로 입력하지 않는다.
- 공연 예매 오픈 시각은 첫 공개 전에는 자유롭게 바꾼다. 공개 이력이 생긴 뒤에는 아직 오픈 전일 때 미래 시각으로만 바꿀 수 있고, 오픈한 뒤에는 바꿀 수 없다. 바꾸면 모든 회차에 같은 값을 적용한다.
- 회차 예매 마감의 기본값은 회차 시작 전날 오후 5시(공연장 시간대)다. 주최자가 회차별로 바꿀 수 있으며 `예매 오픈 < 예매 마감 ≤ 회차 시작`을 지켜야 한다. 기본값이 예매 오픈보다 이르면 등록을 거절하고 주최자가 마감을 지정한다.
- 예매 마감을 바꿀 수 있는 시점은 회차 일정 수정과 같다(6절).
- 고객 취소 기한은 회차 시작 전날 오후 5시로 고정한다. 주최자가 예매 마감을 바꿔도 취소 기한은 바뀌지 않는다(9절).

## 5. 공연 초안과 공통 설정

### 공연 정보

- 공연 초안은 소요 시간 없이 저장할 수 있다. 회차 등록 전에는 공연 기간과 양의 정수 분 단위 소요 시간이 필수다. 기존 공연에도 같다.
- 공연 기간·소요 시간은 공개 이력이 없고 선점·예약 이력(취소·만료 포함)이 없을 때 바꿀 수 있다. 새 기간은 공연장 시간대 기준 모든 회차 시작일을 포함해야 하고, 소요 시간을 바꾼 뒤에도 회차가 겹치지 않아야 한다. 회차가 있으면 기간·소요 시간을 지울 수 없다.
- 공연 제목·소개는 공개 여부·예매 시작·거래 이력과 관계없이 언제든 수정할 수 있다. 제목 필수·길이 검증은 유지한다.
- 공개 이력이 생긴 공연은 제목·소개, 4절의 예매 오픈 시각 변경, 6절의 회차 추가만 허용한다. 비공개로 돌려도 이 제한은 풀리지 않는다.

### 공연장·배치

- 공연 등록 시 기존 공연장과 그 공연장에 등록된 배치를 함께 선택한다. 공통 공연장·배치 등록 화면은 추가하지 않는다.
- 공연장·배치 변경은 공개 이력과 회차가 없는 공연만 가능하다. 공연장을 바꾸면 새 배치는 새 공연장 소속이어야 한다.
- 공연장·배치가 실제로 바뀌면 공통 등급·가격을 모두 초기화한다. 구역 이름이 같아도 승계하지 않는다. 다시 설정하기 전에는 회차 등록·공개를 허용하지 않는다.
- 같은 공연장·배치를 다시 제출하거나 다른 정보를 수정하면 가격을 초기화하지 않는다. 변경과 초기화는 함께 성공하거나 함께 취소한다.

### 공통 구역별 등급·가격

- 공연 등록 → 공통 등급·가격 설정 → 회차 등록 순서를 지킨다. 선택한 배치의 판매 가능한 모든 구역에 등급과 1원 이상 정수 가격이 있어야 회차를 등록할 수 있다.
- 모든 회차가 같은 공통 배치·등급·가격을 쓴다. 회차별·좌석별 가격은 없다. 판매 좌석·재고·소유권은 회차별로 독립이다.
- 공통 가격은 공개 이력과 회차가 없을 때만 바꿀 수 있다. 회차가 있으면 회차를 삭제한 뒤 바꾸고 다시 등록한다. 이미 만든 판매 좌석 가격을 일괄 갱신하지 않는다.
- 가격 변경과 회차 등록이 동시에 실행돼도 회차 존재 검증을 우회하거나 서로 다른 가격이 섞인 좌석을 남기지 않는다.

## 6. 회차

### 등록

- 회차별 입력은 시작 시각, 예매 마감(선택, 기본값은 4절), 구매 한도다. 일괄 등록은 구매 한도를 공통으로 받는다.
- 회차 시작일은 공연장 시간대 기준 공연 기간 안에 있어야 하고 구매 한도는 양수다.
- 같은 공연의 회차는 날짜 포함 시작 시점이 같을 수 없다. `[시작, 시작 + 소요 시간)` 구간도 겹치지 않아야 한다. 종료와 다음 시작이 같으면 허용한다. 일괄 요청 내부, 기존 회차, 시작 시각 수정에 모두 적용하며 삭제된 회차는 제외한다.
- 다른 공연 간 공연장 사용 중복은 검사하지 않는다.
- 회차 등록 시 공통 배치·가격으로 판매 좌석을 함께 만든다. 회차와 좌석은 함께 성공하거나 함께 취소한다.
- 일괄 등록은 요청당 1~10개이며 하나라도 실패하면 전체를 취소하고 실패한 항목과 이유를 알린다. 나눠 보낸 요청 사이의 원자성은 보장하지 않는다.

### 공개 이력이 생긴 뒤 회차 추가

- 공개 이력이 있는 공연에도 회차를 추가할 수 있다. 회차 시작과 예매 마감이 모두 현재보다 미래여야 하고, 나머지 등록 검증은 같다.
- 추가한 회차는 공연의 공개 여부를 따른다. 공개 중인 공연이면 바로 고객에게 보이고, 공연 예매 오픈이 지났으면 바로 예매할 수 있다.
- 추가한 회차는 수정할 수 없다. 잘못 추가했으면 삭제(8절)한 뒤 다시 등록한다.

### 수정

- 회차 일정·예매 마감·구매 한도는 공개 이력이 없는 공연에서 개별 수정만 지원한다. 선점·예약 이력이 있으면 바꿀 수 없다.
- 공개 이력이 없고 거래 이력이 없는 초안은 공연 예매 오픈이 지났어도 미래 시각으로 바꿔 다시 준비할 수 있다.
- 공개 이력이 생긴 공연의 회차는 기존 회차와 추가 회차 모두 수정할 수 없다.

## 7. 공개·비공개

### 첫 공개

- 최소 1개 회차가 있어야 하며 모든 회차를 함께 공개한다.
- 제목·공연장·기간·소요 시간·예매 오픈과 모든 회차의 일정·구매 한도·배치·판매 좌석·공통 등급·가격 설정이 완료돼야 한다.
- 공연 예매 오픈 시각이 공개 시점보다 엄격히 미래여야 한다. 공지 없이 판매가 바로 열리는 것을 막기 위해서다.
- 하나라도 조건을 충족하지 못하거나 저장에 실패하면 공개 전체를 취소한다. 공개와 설정 변경이 동시에 실행돼도 검증을 우회하지 않는다.
- 공개는 예매 시작과 별개다. 고객은 예매 기간·구매 조건에 따라 예약한다.

### 비공개 전환

- 주최자와 ADMIN은 공개 중인 공연을 언제든 비공개로 돌릴 수 있다. 예약이 있어도 된다.

| 대상 | 비공개 동안 |
|---|---|
| 고객 목록·상세·회차·좌석 조회 | 숨긴다 |
| 새 선점 | 막는다. 비공개가 커밋된 뒤 시작한 선점은 거절한다 |
| 진행 중인 선점·결제 | 끝까지 진행한다 |
| 확정 예약·본인 티켓 조회·고객 환불 | 유지한다 |
| 주최자 설정 변경 | 제한이 풀리지 않는다(5절) |

### 재공개

- 주최자와 ADMIN은 비공개 공연을 다시 공개할 수 있다. 예매 시각 조건은 없고 준비 조건(회차 일정·판매 좌석·공통 가격 일치)만 확인한다.
- 취소됨 공연은 재공개할 수 없다.
- 다시 공개해도 최초 공개 시각은 바꾸지 않는다.

## 8. 주최 측 취소와 삭제

### 취소

- 공연 전체 취소는 비공개 상태이고 모든 회차가 시작 전일 때만 요청할 수 있다. 이미 시작한 회차가 있으면 공연 전체 취소는 막고 남은 회차를 개별 취소한다.
- 회차 취소는 시작 전 회차에만 요청할 수 있으며 공연이 공개 중이어도 된다.
- 취소하면 그 범위의 확정 예약을 "주최 측 취소"로 표시하고 발급 티켓을 취소로 바꾼다. 고객은 본인 티켓 조회에서 취소 상태를 볼 수 있다.
- 환불은 시점과 상관없이 100%다. 취소 요청에서 PG를 직접 호출하지 않고, 배치가 공통 결제의 전액 환불 경로로 처리한다(드롭 삭제 환불과 같은 방식).
- 취소 직전에 시작돼 나중에 승인된 결제도 다음 배치에서 전액 환불한다. 결과가 불명확한 결제는 확정된 뒤 환불한다.
- 취소는 되돌릴 수 없다. 취소한 회차는 새 선점을 받지 않고, 취소됨 공연은 재공개할 수 없다.
- 고객 알림은 후순위다. 이번 범위에서는 티켓 조회의 취소 상태로만 알린다.

### 삭제

삭제는 soft delete다. 삭제된 공연·회차는 고객·주최자 조회와 드롭 생성의 공개 공연 확인에서 없는 것으로 다룬다. 예약·결제·티켓 이력과 참조는 남긴다.

| 대상 | 삭제 조건 |
|---|---|
| 초안 공연(공개 이력 없음) | 언제든. 회차가 있으면 함께 삭제한다. 공개한 적이 없어 선점·예약이 있을 수 없다 |
| 공개 이력이 있는 공연 | 비공개 상태이고 진행 중이거나 환불이 끝나지 않은 예약이 없을 때. 예약이 있었다면 전체 취소 뒤 모든 환불이 완료돼야 한다. 남은 회차도 함께 삭제한다 |
| 회차 | 선점·예약 이력(취소·만료 포함)이 없을 때. 예약이 있으면 회차 취소 뒤 모든 환불이 완료돼야 한다 |

- 공개 공연은 바로 삭제할 수 없다. 먼저 비공개로 돌린다.
- 환불이 처리 중·불명확·거절(FAILED)로 남아 있으면 삭제를 거절한다. 거절된 환불은 운영 확인 대상이다.
- 이력이 없는 회차를 삭제하는 것과 고객 선점이 동시에 일어나도, 둘 중 먼저 커밋된 쪽이 이긴다. 삭제가 먼저면 선점을 거절하고, 선점이 먼저면 삭제를 거절한다.
- 삭제와 종속 데이터 정리는 함께 성공하거나 함께 취소한다. 공통 배치·물리 좌석·다른 회차를 자동 삭제하지 않는다.

### 드롭·경매와의 관계

- 공연 삭제는 연결된 드롭·경매가 있어도 위 조건만 본다. soft delete라 드롭·경매의 참조가 깨지지 않으며 티켓팅은 드롭·경매 코드를 바꾸지 않는다.
- 이미 만든 드롭·경매는 각 도메인 규칙대로 진행한다. 삭제된 공연을 드롭·경매에서 어떻게 보여 줄지는 드롭·경매가 실제로 티켓팅 공연과 연결될 때 정한다.
- 드롭·경매는 공개된 공연에만 연결한다. 비공개 공연으로 드롭을 만들면 404다.

## 8-1. 티켓 보유자 전용 드롭·경매 (향후 연결)

드롭·경매가 티켓팅 공연과 연결되는 경우는 티켓 보유자 전용 드롭·경매뿐이다. 일반 드롭·경매는 공연과 연결하지 않는다. 드롭·경매 쪽 연결 기능은 아직 없으며, 아래 규칙은 연결 기능을 만들 때 각 도메인 담당자와 함께 적용한다. 티켓팅 구현은 이 연결이 생길 것을 전제로 한다.

| 항목 | 규칙 |
|---|---|
| 연결 단위 | 회차. 경매는 기존 `performance_id`·`required_performance_id`를 쓰고, 드롭은 회차 연결을 추가한다 |
| 시작 시점 | 드롭 판매·경매 입찰의 시작 시각이 연결 회차의 예매 마감과 취소 기한 이후여야 한다. 이때부터 새 예매와 고객 환불이 없어 보유자가 확정된다. 만드는 시각은 제한하지 않는다 |
| 끝 시점 | 제한하지 않는다. 회차가 끝난 뒤에도 열 수 있다 |
| 참가 자격 | 대기열 입장·입찰마다 그 회차의 유효 티켓 보유를 확인한다. 발급 상태이며 취소되지 않은 티켓이고, 입장 처리로 사용된 티켓도 보유로 인정한다 |
| 자격 확인 경로 | 티켓팅이 회원의 회차별 유효 티켓 보유 매수를 알려 주는 application 계약을 제공한다. 드롭·경매는 티켓 repository에 접근하지 않는다 |
| 구매·입찰 한도 | 드롭·경매 도메인이 정한다. 티켓팅은 보유 매수만 제공한다 |
| 주최 측 취소 | 막지 않는다. 고객 환불이 우선이다. 진행 중인 드롭·경매의 중단·환불은 각 도메인 정책으로 정한다 |

현재 드롭은 `concert_id`가 필수이고 일반 드롭도 공연에 연결한다. 이 정책과 다르며, 드롭과 공연 연결의 필수 여부는 [열린 결정](../../product/open-questions.md)의 팀 확인 항목이다. 티켓팅 정책으로 드롭 구현을 바꾸지 않는다.

## 9. 고객 환불

고객이 직접 취소하면 회차 시작일 기준(공연장 시간대, 각 날짜는 그날 23:59까지) 아래 비율로 환불한다.

| 구간 | 환불 |
|---|---|
| 공연 7일 전까지 | 100% |
| 6일 전 ~ 3일 전 | 80% |
| 2일 전 ~ 취소 기한(전날 오후 5시) | 70% |
| 취소 기한 이후 | 불가 |

- 예약(결제) 단위로 환불하며 1원 미만은 버린다.
- 주최 측 취소는 이 표와 상관없이 100%다(8절).
- 비율은 티켓팅이 정한다. 부분 환불의 실행 방식은 결제 담당자의 정책을 따른다.
- 공통 결제가 부분 환불을 지원하기 전에는 100% 구간만 환불을 받고 80%·70% 구간은 거절한다. 전액 환불 경로로 처리하면 과다 환불이 되기 때문이다.

## 10. 기존 데이터 전환

- 정책 전환 전 공연은 공개 상태와 공개 이력을 가진 것으로 본다. 실제 공개 시각은 모르므로 기록하지 않는다.
- 기존 선점·예약·주문·결제·환불·티켓과 가격 이력은 보존한다. 진행 중 결제 확인·복구를 중단하지 않는다.
- 기존 공연의 회차별 배치·등급·가격·예매 오픈이 서로 다르면 별도 확인 대상이다. 한 회차를 기준으로 통일하거나 판매 좌석·거래 가격을 자동 수정하지 않는다. 예매 오픈이 다른 공연은 공연 예매 오픈을 비워 두고 회차의 기존 값으로 판매한다.
- 운영 DB의 기존 데이터는 이 개정의 마이그레이션 PR 전에 확인한다. 확인 항목은 [구현 계약](organizer-implementation.md)에 있다.

재도입할 때 상세 정책과 계약을 다시 정한다. 현재 구현 요구사항이 아니다.

| 기능 | 내용 |
|---|---|
| 일괄 수정 | 여러 회차의 구매 한도·예매 마감 일괄 변경 |
| 일괄 삭제 | 여러 회차 선택 삭제 |

| 회차별 공개 | 공연 안에서 일부 회차만 공개·비공개 |

| 무료 공연 | 0원 좌석과 무료 예매 확정 |
| 관리 편의 | 제목 검색·상태 및 주최자 필터·대시보드 |

운영 정지·재개와 재개 요청·검토는 2026-11-26에 정책에서 뺐다. 판매를 멈추는 기능은 비공개 전환으로 대신한다.
