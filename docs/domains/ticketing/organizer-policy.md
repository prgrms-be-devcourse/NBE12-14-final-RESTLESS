# 티켓팅 주최자 MVP 정책

> 상태: DECIDED (2026-11-24, MVP 축소안 확정). 구현 완료를 의미하지 않는다.
>
> 이 문서는 이전의 확장 정책을 대체하는 정본이다. 고객 예약에 필요한 공연 준비·전체 공개에 집중한다.

## 1. MVP 범위

공연 등록(공연장·배치 선택) → 공연 공통 구역별 등급·가격 설정 → 회차 개별·일괄 등록 및 판매 좌석 생성 → 회차 일정·구매 한도 수정 → 준비 조건 검증 → 공연 전체 공개 → 고객 예약.

| 기능 | 범위 |
|---|---|
| 관리 조회 | 기본 공연 목록·상세, 회차 목록·설정 현황, 등록 배치 조회. 검색·필터 확장 제외 |
| 공연 초안 | 공연장·배치·제목·소개·기간·소요 시간 등록, 공통 구역별 등급·가격 별도 설정 |
| 회차 준비 | 개별·일괄 등록, 공연 공통 배치·등급·가격 사용, 회차별 일정·구매 한도 설정·수정 |
| 공개 | 공연과 모든 등록 회차를 한 번에 공개 |
| 공개 후 | 제목·소개만 수정 가능. 회차 추가·설정 변경·삭제·비공개 전환 불가 |
| 삭제 | 미공개 초안 공연·회차의 조건부 개별 삭제 |

## 2. 권한

- ORGANIZER는 본인 공연·회차만 관리한다. ADMIN은 모든 공연·회차에 동일한 주최자 기능을 수행할 수 있다.
- ADMIN도 공개 후 변경·삭제 제한과 모든 사업 검증을 동일하게 준수한다. 제한을 넘어서는 예외 수정·삭제는 DEFERRED다.
- 기존 기본 목록·페이지 조회를 유지하며 검색·필터 및 별도 관리자 운영 대시보드는 추가하지 않는다. ADMIN의 타인 공연 접근에 필요한 기본 조회 범위만 제공한다.
- 타 주최자 명의의 신규 공연 대행 등록 기능은 추가하지 않는다. 기존 공연 소유자는 수정·회차 등록으로 변경하지 않는다.

## 3. 공연 초안과 개별 수정·삭제

- 등록한 공연과 회차는 비공개 초안이다. 일반 사용자용 공연·회차·좌석 조회에 노출하지 않고 선점·예약도 허용하지 않는다.
- 공연 초안은 소요 시간 없이 저장할 수 있지만 회차 등록 전에는 공연 기간과 양의 정수 분 단위 소요 시간이 필수다. 기존 공연에도 동일 적용한다.
- 공연 등록 시 기존 공연장과 해당 공연장에 등록된 배치를 함께 선택한다. 배치가 하나면 자동 선택할 수 있다. 공연장·배치 변경은 공개 이력이 없고 회차가 없는 공연만 가능하다. 공통 공연장·배치 등록 화면은 추가하지 않는다.
- 공연 기간·소요 시간은 공개 전, 모든 회차가 예매 시작 전이고 선점·예약 이력(취소·만료 포함)이 없을 때 변경할 수 있다. 새 기간은 공연장 시간대 기준 모든 회차 시작일을 포함하고 소요 시간 변경 후에도 회차 간 겹침이 없어야 한다. 회차가 있으면 기간·소요 시간을 지울 수 없다.
- 회차 일정·구매 한도는 공개 전 개별 수정만 지원한다. 배치·구역별 등급·가격은 공연 공통 설정이며 회차별 입력·변경을 지원하지 않는다. 기존 항목별 예매 시각·선점 및 예약 이력 제한과 입력 검증도 적용한다.
- 한 번도 공개하지 않았고 선점·예약 이력이 없는 초안은 기존 예매 시작 시각이 지났어도 미래 시각으로 일정을 변경할 수 있다. 기간·소요 시간 변경이 필요하면 먼저 회차 일정을 미래로 수정한다. 이 예외로 배치·가격의 다른 변경 제한을 자동 해제하지 않는다.
- 공연 제목·소개는 공개 여부·예매 시작·선점 및 예약 이력과 관계없이 수정 가능하다. 제목 필수·길이 등 기존 입력 검증은 유지한다.
- 공연 삭제는 공개 이력이 없고 등록된 회차가 없는 경우만 가능하다. 회차가 있으면 허용 조건에 따라 개별 삭제한 뒤 공연을 삭제한다.
- 연결된 드롭·경매가 하나라도 있으면 공연 삭제를 거절한다(DECIDED, 2026-11-24). 공개 전이고 회차가 없어도 동일하며 ADMIN도 예외가 없다. 다른 도메인 데이터를 자동 삭제하거나 연결을 임의 해제하지 않는다. 연결 데이터는 해당 도메인의 허용된 절차로 정리한 뒤 재시도한다.
- 드롭·경매 참조 여부 확인은 해당 도메인의 application 서비스·계약을 통해 수행하고 다른 도메인 repository에 직접 접근하지 않는다. 확인과 삭제 사이의 동시 연결 요청에서도 참조 정합성을 유지한다.
- 공연 삭제는 연결된 드롭 또는 경매가 있으면 거절한다. ADMIN도 동일하게 적용하며 타 도메인 데이터나 연결을 자동 삭제·해제하지 않는다. 각 도메인의 서비스 계약으로 참조를 확인한다.
- 회차 삭제는 공개 이력과 선점·예약 이력(취소·만료 포함)이 모두 없는 경우만 가능하다. 예매 시작 예정 시각 경과와 무관하며 종속 판매 좌석도 함께 정리한다. 공통 배치·물리 좌석·다른 회차 및 공연 자체는 자동 삭제하지 않는다.
- 삭제와 종속 데이터 정리는 함께 성공하거나 함께 취소한다. 거래 데이터와 다른 도메인 참조 정합성을 보존한다.

## 4. 회차 등록과 필수 검증

- 개별 등록과 같은 공연의 여러 회차 일괄 등록을 지원한다. 일괄 등록은 요청당 1~10개, 공연 전체 회차 수는 제한하지 않는다. ADMIN도 동일하다.
- 회차별 입력: 날짜·시작 시각·예매 마감 시각.
- 일괄 등록의 공통 입력: 예매 시작 시각·구매 한도. 배치·구역별 등급·가격은 공연에 저장된 공통 설정을 사용하며 회차 등록 요청에서 다시 입력하지 않는다.
- 회차별 일정·구매 한도와 판매 좌석·재고·예약은 독립적이다. 배치·구역별 등급·가격은 모든 회차가 같은 공연 공통 설정을 사용하며 회차별로 달리 지정할 수 없다.
- 일괄 등록은 하나라도 검증·저장·판매 좌석 생성에 실패하면 전체 취소한다. 부분 회차·좌석을 남기지 않고 등록 불가 대상과 이유를 권한 범위 안에서 안내한다. 나눠 보낸 여러 요청 사이에는 원자성을 보장하지 않는다.
- 별도 요청 식별자를 통한 최초 결과 재반환 기능은 DEFERRED다. 재시도라도 아래 중복·겹침 검증으로 중복 회차 생성은 방지한다. 응답 유실 시 기본 관리 조회에서 결과를 확인한다.
- 회차 시작일은 공연장 시간대 기준 공연 기간 안에 있어야 하며 예매 시작 < 예매 마감 ≤ 회차 시작, 구매 한도 양수를 준수한다.
- 같은 공연의 모든 회차는 공연 등록 시 선택한 배치를 사용한다. 공연장은 장소, 배치는 해당 공연장의 무대·좌석 구성이다. 회차 등록 화면에서는 배치를 다시 선택하지 않는다.
- 구역별 등급·가격은 공연 등록의 필수 동시 입력이 아니다. 초안 준비 중 별도 단계에서 공연 공통으로 한 번 설정하고 모든 회차에 동일하게 적용한다(DECIDED, 2026-11-24). 이전 회차별 가격 독립 설정·수정 정책을 대체한다.
- 선택한 배치의 판매 가능한 모든 구역에 등급·가격을 설정한다. 구역 내 동일 가격이며 개별 좌석 예외 가격은 지원하지 않는다. 회차별 판매 좌석·재고·소유권은 계속 독립적으로 관리한다.
- 공연 등록 → 공통 구역별 등급·가격 설정 → 회차 등록 순서를 필수로 한다(DECIDED, 2026-11-24). 선택한 배치의 모든 판매 가능 구역에 유효한 등급·1원 이상 가격 설정이 완료돼야 개별·일괄 회차 등록을 허용한다. 미완료면 회차·판매 좌석을 생성하지 않는다.
- 회차 등록 시 공연 공통 배치·등급·가격으로 해당 회차의 판매 좌석을 함께 생성한다. 회차와 판매 좌석 생성은 함께 성공하거나 함께 취소하며, 일괄 등록에서는 요청 전체 회차와 판매 좌석에 이 원칙을 적용한다.
- 공통 가격 설정과 회차 등록이 동시에 실행돼도 동일한 유효 공통 설정을 기준으로 검증·생성하고 일부 구역이나 다른 가격 버전이 섞인 좌석을 남기지 않는다. 구체적인 잠금 계약은 후속 구현에서 정한다.
- 공연 공통 구역별 등급·가격은 공개 전이고 등록된 회차가 없을 때만 변경할 수 있다(DECIDED, 2026-11-24). 회차가 하나라도 있으면 공개 전이어도 변경할 수 없으며 ADMIN에게도 동일하게 적용한다.
- 가격을 잘못 설정한 경우 삭제 조건을 충족하는 미공개 회차를 개별 삭제한 뒤 공통 등급·가격을 수정하고 회차를 다시 등록한다. 회차를 자동 삭제하거나 이미 생성된 판매 좌석 가격을 일괄 갱신하지 않는다.
- 공통 등급·가격 수정과 회차 등록이 동시에 실행돼도 회차 존재 여부 검증을 우회하지 않아야 한다. 최초 가격 설정·변경은 선택한 배치의 모든 판매 가능 구역을 검증하며 1원 이상 등 기존 입력 조건을 유지한다.
- 공개 전이고 회차가 없는 공연에서 공연장 또는 배치가 실제로 변경되면 기존 공통 구역별 등급·가격을 모두 초기화한다(DECIDED, 2026-11-24). 구역 이름이 같더라도 자동 승계하지 않는다.
- 변경된 배치의 모든 판매 가능 구역에 등급·가격을 다시 설정해야 한다. 완료 전에는 개별·일괄 회차 등록과 공개를 허용하지 않는다.
- 공연장·배치 변경과 공통 가격 초기화는 함께 성공하거나 함께 취소한다. ADMIN도 같은 조건을 적용하며, 공연장 변경 시 새 배치는 새 공연장 소속이어야 한다.
- 기존과 같은 공연장·배치를 다시 제출한 경우에는 실제 변경이 아니므로 가격을 초기화하지 않는다. 공연 제목·소개 등 다른 정보 수정도 가격을 초기화하지 않는다.
- 모든 판매 구역 가격은 원 단위 1원 이상 정수다. 무료 공연·무료 좌석·무료 예매 확정은 DEFERRED다.
- 같은 공연의 공개·비공개 회차 전체에서 날짜 포함 실제 시작 시점이 중복될 수 없다. 일괄 요청 내부와 기존 회차 모두 검사하며 개별 등록·시작 시각 수정에도 적용한다.
- 소요 시간 기준 `[시작, 시작 + 소요 시간)` 구간이 겹치지 않아야 한다. 종료와 다음 시작이 같으면 허용하고 준비·정리 간격은 강제하지 않는다. 자정을 넘는 회차도 실제 시점으로 비교한다. 소요 시간 변경에도 재검증한다.
- 다른 공연 간 공연장 사용 중복 검사는 이번 정책 범위에 포함하지 않는다.

## 5. 공연 전체 공개

- 최소 1개 회차가 있어야 하며 모든 등록 회차를 함께 공개한다. 최초 공개만 지원하고 회차 선택 공개·재공개는 지원하지 않는다.
- 제목·공연장·공연 기간·소요 시간 및 모든 회차의 일정·구매 한도·배치·판매 좌석·구역별 등급·1원 이상 가격 설정이 완료돼야 한다.
- 공개 처리 시 모든 회차의 예매 시작 시각이 현재보다 엄격히 미래여야 한다. 최소 사전 공지 시간은 두지 않는다.
- 하나라도 조건을 충족하지 못하거나 저장 중 실패하면 전체 공개를 취소한다. 공연과 모든 회차의 공개는 함께 확정하고 공개와 설정 변경이 동시에 실행돼도 검증을 우회하지 않는다.
- 공개는 예매 시작과 별개다. 공개 이후 고객은 기존 예매 기간·구매 조건에 따라 예약한다.
- 공개 후에는 제목·소개 외 설정 변경, 회차 추가·삭제, 공연 삭제, 비공개 전환을 허용하지 않는다. ADMIN도 동일하다. 기존 좌석 소유권·예약·결제·환불 보호 규칙은 유지한다.

## 6. 기존 데이터 전환 (DECIDED, 2026-11-24)

- 정책 전환 전에 존재하던 공연은 공개 상태로 유지한다. 전환 적용 후 새로 등록하는 공연부터 비공개 초안으로 생성한다. 기존 공연에 신규 공개 준비 검증을 소급 적용해 일괄 비공개로 만들지 않는다.
- 기존 선점·예약·주문·결제·환불·티켓과 가격 이력 및 참조 관계를 보존한다. 공개 상태 도입으로 기존 거래 결과를 변경하거나 진행 중 결제 확인·복구를 중단하지 않는다.
- 기존 공연의 회차별 배치·구역별 등급·가격이 서로 다르면 별도 확인 대상으로 분류한다. 한 회차를 임의의 기준으로 삼아 통일하거나 기존 판매 좌석·거래 가격을 자동 수정하지 않는다.
- 회차별 설정이 다른 기존 공연을 공통 배치·가격 구조에 어떻게 표현·이관할지는 데이터 확인 후 결정한다. 단일 공통 설정이 있다고 허위로 표시하지 않으며 기존 고객 조회·예약 흐름과 참조 정합성을 유지하도록 전환한다.
- 기존 공개 공연에는 공개 후 제목·소개 외 변경 금지 정책을 적용한다. 예외 수정·삭제를 허용하는 전환은 아니다.
- 신규·기존 구분의 기준점, 공개 표식의 초기값·이관 시각 의미, 배치·가격 불일치와 0원·소요 시간 누락 점검은 마이그레이션 설계에서 구체화한다. 과거 실제 공개 시각을 모르면 임의로 사실처럼 기록하지 않는다.

## 8. 스키마·API 설계 초안

이 절은 확정 정책을 구현 가능한 형태로 옮긴 초안이다. 실제 기존 데이터 상태를 읽기 전에는 이관 UPDATE를 만들거나 과거 공개 시각을 추정하지 않는다.

### 저장 모델

- `concerts.status`는 기존 공연 진행 상태로 유지한다. 공개 여부와 같은 필드로 쓰지 않는다.
- `concerts`에 `is_published BOOLEAN NOT NULL`, `published_at DATETIME(6) NULL`을 추가하는 방안을 사용한다. DB 기본값은 공개(TRUE)다(2026-11-25 결정, V20261125_1000). 공개 여부를 지정하지 않은 직접 INSERT(타 도메인 fixture 등)는 공개로 저장되고, 주최자 API는 엔티티가 FALSE를 명시해 초안으로 만든다. 비공개 기본값으로의 전환은 후속 결정이다. 공개 판정은 `is_published`로 한다. 기존 공연은 이관 시 `is_published = TRUE`, 실제 공개 시각을 알 수 없으므로 `published_at = NULL`로 보존한다. 신규 공연은 FALSE/NULL로 생성하고 공개 성공 시 TRUE/서버 시각을 함께 저장한다. 생성 시각을 실제 공개 시각으로 추정하지 않는다. 기존 진행 상태와 회차 상태는 변경하지 않는다.
- `concerts`에 초안의 공통 `layout_id`를 저장하고 `concert_section_prices(concert_id, section_label, grade, price)` 테이블로 구역별 공통 가격을 저장하는 방안을 제안한다. `concert_section_prices`는 `(concert_id, section_label)` 유일, 양수 가격 CHECK, 공연 FK를 둔다. 구역 표시는 선택 배치의 판매 가능 구역과 정확히 일치해야 한다.
- 신규·정합성이 확인된 공연은 모든 회차의 `layout_id`가 공연의 배치와 같아야 한다. 기존 불일치 공연은 개별 확인 전 공통 설정으로 자동 변환하지 않는다. 가격 테이블의 관계와 CHECK만으로 공연-회차의 배치 일치를 강제하기 어려우므로 회차 생성 서비스에서 잠금·검증하고, 데이터 모델 계약을 필요하면 복합 FK로 보강한다.
- `performance_seats`는 계속 회차별 판매 재고와 소유권의 기준이다. 회차 등록 트랜잭션이 공통 배치·가격으로 좌석을 생성하고, 기존 `seat_holds.price_amount`·`tickets.price_amount`의 스냅샷은 수정하지 않는다. 신규 판매 좌석은 `price > 0`이어야 한다. 기존 0원 좌석은 기존 공개 공연에서 보존한다.
- 삭제는 거래 없는 초안만 가능하다. 드롭·경매 참조 존재 여부를 각 도메인의 명시적 application 계약으로 확인한다. 교차 도메인 repository 직접 호출이나 cascade 삭제를 사용하지 않는다. 검사와 삭제 사이 새 참조 연결을 막는 방법은 해당 서비스·DB FK와 함께 설계한다.

### API 제안

| 작업 | 제안 API | 동작 |
|---|---|---|
| 공연 초안 생성 | `POST /api/organizer/concerts` | 기존 본문에 `layoutId` 필수 추가. 사용자에게 미노출 |
| 공연 공통 가격 | `PUT /api/organizer/concerts/{id}/section-prices` | 배치의 판매 가능 구역 전체를 한 번에 설정. 공개 전·회차 없음만 허용 |
| 공연 관리 상세/목록 | 기존 `/api/organizer/concerts...` | ADMIN은 전체, ORGANIZER는 본인 소유 데이터. 기본 페이지 조회 유지 |
| 회차 개별 등록 | 기존 `POST /api/organizer/concerts/{id}/performances` | 요청에서 `layoutId` 제거. 가격 완료 후 공통 배치로 좌석까지 생성 |
| 회차 일괄 등록 | `POST /api/organizer/concerts/{id}/performances/batch` | 1~10개. 공통 `bookingOpensAt`, `maxTicketsPerUser`; 항목별 공연 시작·예매 마감. 전체 원자성 |
| 공연 전체 공개 | `POST /api/organizer/concerts/{id}/publish` | 공연 잠금 후 모든 회차·가격·좌석·미래 예매 시각 검증, 전체를 한 번에 공개 |
| 공연장·배치 변경 | `PUT /api/organizer/concerts/{id}` 확장 | 공개 전·회차 없음만. 실제 변경 시 가격 전부 삭제. 동일 값은 유지 |
| 회차/공연 초안 삭제 | `DELETE /api/organizer/performances/{id}`, `DELETE /api/organizer/concerts/{id}` | 공개·거래 이력 및 타 도메인 참조 검사 후 원자 삭제 |

관리자 타인 공연 접근은 각 서비스가 `ADMIN || ownerId == actorId`를 확인한다. 인증 역할 검사는 기존 `/api/organizer/**`를 쓴다. 고객 공개 조회와 신규 선점은 `is_published = TRUE`를 확인한다. 결제 복구·티켓 조회는 공개 표식으로 차단하지 않는다.

### 구현 순서 갱신

1. **데이터 현황 및 마이그레이션 기준 확인:** 읽기 전용으로 회차 배치·가격 불일치, 0원, 소요 시간 NULL, 드롭·경매 참조 현황을 점검한다. 기존 공연은 공개로 유지하고 거래 스냅샷을 보존한다. 불일치 데이터 보정은 별도 검토 전 실행하지 않는다.
2. **공개·공통 설정 스키마와 접근 경계:** `is_published`·`published_at`, 공연 배치, 구역별 공통 가격을 추가하고 과거 레코드를 공개로 표시한다. 기존 구매 API·응답 호환을 유지하며 공개 조회·선점에서 초안을 막는다.
3. **초안 생성·조회·수정:** 등록 때 공연장·배치 선택, ADMIN 소유권 예외, 공통 가격 입력과 1원 검증, 기간·소요 시간 및 배치 변경 규칙을 구현한다.
4. **회차 생성·편집:** 공통 가격 선행 조건, 회차+판매 좌석 원자 생성, 최대 10개 전체 취소 일괄 등록, 기간·소요 시간·중복·겹침 검증을 구현한다. 가격·배치는 공연 공통이며 회차별 API에서 제거한다.
5. **전체 공개 및 공개 후 제한:** 공개 서비스와 전체 회차 검증, 공개 후 제목·소개 외 변경 차단, 고객 조회·좌석·선점 경로 검증을 완성한다.
6. **조건부 삭제:** 회차/공연의 공개·선점·예약 확인, 판매 좌석의 안전한 제거, 드롭·경매 참조 계약 및 동시 연결 방지를 구현한다.
7. **최소 관리 화면:** 기본 목록·상세, 공통 가격 설정, 개별/일괄 회차 준비, 공개, 조건부 삭제를 연결한다. 검색·필터와 DEFERRED 기능은 범위에서 뺀다.

### 아직 데이터 확인이 필요한 점

- 기존 공연 회차에서 `layout_id`가 공연 간 또는 같은 공연 안에서 일치하는지
- `performance_seats` 가격이 0인 레코드와 이미 저장된 결제·티켓 가격 스냅샷 여부
- 공연 `duration_minutes` NULL인데 회차가 존재하는지
- 드롭·경매가 참조하는 공연에 대한 삭제 거절이 FK만으로 충분한지, 참조 생성과 삭제 경합을 막는 기존 계약이 있는지

이 확인은 기존 데이터의 안전한 이관에 한정한다. 신규 MVP 정책 결정을 다시 여는 사유로 삼지 않는다.

## 9. 현재 구현과의 차이 및 후속 계약

- 현재 코드는 공연·회차를 등록 직후 공개 조회한다. 초안·전체 공개·공개 후 잠금은 미구현이다.
- 개별 공연·회차 등록·일정 및 가격 설정·관리 조회는 일부 구현돼 있다. ADMIN 일부 기능은 본인 공연만 허용해 권한 정책과 차이가 있다.
- 일괄 등록·공연장 변경·공연 공통 배치·등급·가격 관리·개별 삭제, 1원 이상 가격 검증, 소요 시간 필수·중복 및 겹침 검증은 구현 확인·변경이 필요하다. 문서만으로 구현 완료나 테스트 통과를 주장하지 않는다.
- 현재 API의 공개 후 수정 허용·0원 저장 등은 구현 기록이며 위 의도한 정책과 다르다. [API 문서](../../contracts/api/ticketing.md)의 현재 동작과 구분한다.
- 기존 공개 유지 전환의 구현과 회차별 설정 불일치·0원·소요 시간 누락 점검, 공개 상태 저장 방식, 동시성·에러·삭제 참조 처리와 새 API 경로·요청·응답은 구현 전에 구체화한다. 공개된 기존 거래 가격·이력을 소급 변경하지 않는다.

### 구현 전 정책 검토 결과 (2026-11-24)

- 신규 공연 MVP의 기능·권한·준비 순서·공통 배치 및 가격·공개·수정·삭제 정책은 확정됐다. 추가 편의 기능에 대한 정책 결정을 늘리지 않는다.
- 공개 표식·공통 설정 스키마, API·오류, 잠금·원자성, 시간 표현, 삭제 참조 처리의 구현 방식은 기존 규약과 위 정책을 준수해 설계한다. 별도의 사업 정책 승인 항목으로 취급하지 않는다.
- 기존 회차별 설정 불일치·0원·소요 시간 누락 데이터는 실제 데이터를 확인한 뒤 이관 방식을 정한다. 발견 시 기존 공개·거래 보존 결정에 따라 자동 보정하지 않고 필요한 사항만 추가 협의한다. 이 조건부 이관 확인은 신규 공연 기능의 정책 미결과 구분한다.
