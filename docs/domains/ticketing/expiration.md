# 예약 만료와 좌석 반환

- 상태: DECIDED (2026-11-12, 담당자 합의).
- 구현 상태: 문서 설계. 애플리케이션·승인 시도 스키마는 후속 구현 대상이다.

## 1. 판단 기준

PAYMENT_PENDING은 결제 단계 진입을 의미한다. 실제 PG 승인 시도 여부는 공통 결제의 영속 승인 시도 기록으로 구분한다.
티켓팅이 결제 Repository를 직접 조회하지 않고, Coordinator가 공통 결제 서비스의 결과와 예약 상태를 함께 검증한다.
시도 상태의 실제 enum·컬럼과 전체 잠금 순서는 공통 계약에서 정한다.

| 예약·승인 상황 | 만료 판단 |
|---|---|
| HELD, 결제 진입 전 | 현재 시각 >= hold_expires_at이면 반환 |
| PAYMENT_PENDING, 승인 시도 없음 | 현재 시각 >= payment_expires_at이면 반환 |
| PAYMENT_PENDING, 모든 시도가 최종 실패 | 결제 기한 전에는 재시도 대기, 현재 시각 >= payment_expires_at이면 반환 |
| 유효 승인 시도가 진행 중이거나 결과 불명확 | 기한 경과만으로 반환하지 않음 |
| 승인 성공이 확인됨 | 결제 기한 이후라도 유효 시도라면 예매 확정 |
| CONFIRMED 또는 환불 진행·결과 확인 중 | 선점 만료 대상이 아님. 환불 확정 후 반환 |
| RELEASED 또는 CANCELLED | 만료 재처리로 상태·수량을 다시 변경하지 않음 |

최초 결제 진입 후에는 별도로 부여한 payment_expires_at으로 판단한다. 최초 hold_expires_at만 보고 반환하지 않는다.
과거 실패 기록이 있어도 진행 중·불명확 시도가 하나라도 남으면 반환하지 않는다.
승인 시도 기록 직후 서버가 종료돼 실제 전송 여부를 모르는 경우도 보호·복구 대상이다.
PG 조회 미존재만으로 최종 실패라고 단정하지 않는다.

예: 12:00 선점 → hold_expires_at=12:05 → 12:04 결제 진입 → payment_expires_at=12:09.
승인 시도가 없으면 12:09부터 반환할 수 있다. 12:08:59에 유효 시도를 기록·커밋했다면 12:09가 지나도 결과 확인 전까지 유지한다.

## 2. 승인 준비·checkout과 만료의 경합

구매 관리 행 → 예약 행 → 좌석 행(ID 오름차순) 순으로 잠그고 상태·기한을 재검증한다.
승인 준비와 만료는 같은 예약 잠금으로 직렬화한다. 공통 결제 기록도 이 경계에서 일관되게 확인한다.

- 기한 내 승인 준비가 먼저 유효 시도를 기록·커밋하면 만료 작업은 좌석을 유지한다.
- 기한 이후 만료가 먼저 좌석을 반환하면 승인 준비는 RELEASED 예약을 보고 거절하며 PG를 호출하지 않는다.
- 승인 요청이 기한 전에 도착했어도 잠금 획득 후 기록 시점이 기한 이상이면 신규 승인을 거절한다.
- checkout과 최초 선점 만료도 같은 방식으로 재검증한다. 이미 해제된 예약은 checkout할 수 없다.

## 3. 반환 트랜잭션

예약 한 건과 그 좌석 전체를 단위로 처리한다.

1. 공통 순서로 잠근 뒤 예약의 반환 가능 상태, 서버/DB 기준 현재 기한과 미완료 승인 시도 유무를 검증한다.
2. 각 좌석의 current_hold_id가 반환 대상 선점과 일치하는지 확인한다. 불일치하면 해당 좌석을 덮어쓰거나 예약 전체를 반환 완료로 처리하지 않고, 롤백하여 불일치 복구 대상으로 남긴다.
3. 예약 RELEASED, 선점 RELEASED, 좌석 AVAILABLE/current_hold_id=NULL, reserved_count 감소를 한 트랜잭션에서 커밋한다.
4. 다중 좌석은 모두 함께 반환한다. 중복 만료 실행은 상태를 재검증하여 카운터를 한 번만 감소시킨다.

5초 스케줄러와 요청 시 만료 검증은 같은 반환 규칙을 사용한다.
기한 도달은 반환 가능한 시점이며 스케줄러 실행 지연으로 실제 정리가 늦을 수 있다.
불명확 상태 5분 후 운영 전환은 반환 조건이 아니다. 자동 조회와 좌석 보호를 계속한다.
복구 정책은 [결제 트랜잭션 설계](transactions.md)를 따른다.

## 4. 검증 계획 (미실행)

- HELD 최초 기한, 승인 미시도 결제 기한 각각의 직전·정각·직후 판정.
- checkout 후 최초 선점 기한 경과: 별도 결제 기한까지 유지.
- 승인 미시도·모든 시도 최종 실패: 결제 기한에 전체 좌석 반환.
- 과거 실패와 현재 진행 중 시도 공존: 반환하지 않음.
- 승인 준비와 만료 경합, 잠금 대기 중 기한 종료: 유효 시도와 좌석 해제가 동시에 성립하지 않음.
- 준비 커밋 직후 서버 종료: 최초 기한·결제 기한 경과에도 보호 및 복구 대상 유지.
- 중복 Worker 실행: 카운터 한 번만 감소, 다중 좌석 전체 반환.
- 좌석 포인터 불일치: 새 소유자의 좌석·카운터를 변경하지 않고 복구 대상으로 남김.
