# 티켓팅 결제 트랜잭션 경계

- 상태: DECIDED (2026-11-12, 담당자 합의).
- 구현 상태: checkout과 내부 대상 조회·승인 시작·성공 확정/티켓 발급을 구현했다. 실제 결제 시도 연결·Handler 빈 등록·실패/불명확·결제 후 만료·보상 취소는 다음 단계다. 실행 범위는 아래 단계별 검증 기록을 따른다.
- 공통 승인·대사·손님 환불 계약은 ADR-0003과 [장애 처리 문서](../../operations/failure-handling.md)를 따른다. OPEN: 티켓팅 Handler·시도 저장 연결, 결제 이후 만료, 운영 확인 등록·알림의 담당과 세부 규칙.

## 1. 책임과 연결

티켓팅은 예약·좌석 소유권·구매 카운터·티켓을 소유한다.
공통 주문은 구매자·내역·최종 금액을, 공통 결제는 PG 요청과 결과를 소유한다.
checkout 주문 준비는 티켓팅 TicketCheckoutService가 공통 주문 Application Service를 통해 조정한다. 실제 승인·대사는 공통 결제가 동기 Handler로 티켓팅을 호출하는 후속 연결 범위다.
다른 도메인의 Repository를 직접 접근하지 않는다.
예약은 ticket_reservations.order_id로 공통 주문과 연결한다. 결제 대상은 payable_type/payable_id로 식별하며 payments.order_id는 전제하지 않는다.
checkout은 TicketCheckoutService가 OrderService.create(CreateOrderCommand)를 호출한다. OrderService의 MANDATORY 계약으로 주문·항목과 예약 변경이 호출자 트랜잭션에 참여한다.
OrderType.TICKET, shipping=null이며 좌석별 수량은 1, 단가는 SeatHold.priceAmount다. 항목은 TICKET/판매 좌석 ID, 이름은 서버 회차 ID, 옵션은 서버 좌석 등급·ID로 구성한다. 클라이언트의 가격·이름은 받지 않는다.

## 2. 결제 진입과 승인 시도 준비

결제 화면 진입과 실제 PG 승인 요청은 구분한다.

결제 진입 트랜잭션:

- @LoginMember의 본인 예약인지 확인하고 구매 관리 행 → 예약 → 좌석 ID 오름차순으로 잠근다. 없는 예약과 타인 예약은 동일한 NOT_FOUND다.
- 기존 order_id가 있으면 상태·기한과 무관하게 기존 주문·최초 결제 기한을 반환한다. 이후 결제 가능 여부는 별도 승인 준비에서 검사한다.
- 최초 진입은 결제 관련 필드가 없는 HELD만 허용한다. 모든 좌석 잠금 후 DB UTC_TIMESTAMP(6)으로 now < hold_expires_at을 재검증하고 선점 HELD·동일 회차·current_hold_id 일치를 확인한다.
- checkout_started_at=now, payment_expires_at=now+5분이다. 최초 hold_expires_at과 SeatHold.expires_at은 변경하지 않으며 좌석 HELD와 구매 카운터를 유지한다.
- 최초 진입 시 공통 주문을 생성·연결하고 PAYMENT_PENDING 및 최초 결제 진입 시각·별도 결제 기한을 저장한다.
- 중복 진입은 기존 주문·기한을 반환한다. 주문 중복 생성과 기한 연장을 허용하지 않는다.
- 주문 생성·연결과 예약 변경은 READ_COMMITTED 새 트랜잭션에서 함께 커밋하거나 함께 롤백한다. 교착·잠금 대기 실패는 전체 롤백 후 최대 3회 시도하고 SEAT_LOCK_TIMEOUT으로 반환한다. PG 호출과 결제 시도 생성은 이 트랜잭션에 없다.

실제 PG 승인 직전의 별도 준비 트랜잭션:

- 주문·예약·금액과 승인 요청 자격을 검증하고 승인 시도를 영속적으로 기록한다.
- 동시에 여러 승인 요청이 나가지 않도록 진행 중 시도를 식별한다.
- 승인 시도가 진행 중이거나 결과 불명확하면 단순 시간 경과로 좌석을 반환하지 않는다.
- 이 기록을 커밋한 뒤에만 외부 PG를 호출한다.
- 기한 판정은 8절을 따른다. 공통 시도 문맥은 ADR-0003의 PaymentAttemptContext/RefundContext를 따른다. 티켓팅의 시도 저장·검증 연결은 후속 구현이다.

## 3. PG 호출 구간: DB 트랜잭션 없음

준비 트랜잭션은 이미 커밋됐으며 좌석 행 잠금도 해제됐다. PG 호출을 감싸는 외부 DB 트랜잭션을 두지 않는다.
공통 Coordinator 전체를 하나의 @Transactional로 감싸지 않고, 준비와 결과 반영을 각각 별도 트랜잭션으로 실행한다.
외부 응답을 기다리는 동안 DB 연결과 행 잠금을 계속 보유하지 않는다.

DB 잠금이 풀려도 좌석의 HELD/current_hold_id와 결제 진행 기록은 남아 있다.
다른 선점 요청은 좌석을 잠근 뒤 이 상태를 확인하고 거절한다. 만료 처리도 결제 진행·불명확 상태를 검증한다.
즉, 잠금은 짧은 변경 작업을 직렬화하고, 실제 좌석 점유는 저장된 상태로 유지한다.

## 4. 결과 반영 트랜잭션

Coordinator는 검증된 PG 결과를 직접 전달하여 다음을 동일 DB 트랜잭션에서 확정한다.

| 소유 모듈 | 성공 시 반영 |
|---|---|
| 결제 | 승인 결과와 결제 완료 |
| 주문 | 결제 완료 |
| 티켓팅 | 예약 CONFIRMED, 선점 CONFIRMED, 좌석 SOLD, reserved_count 감소·confirmed_count 증가, 좌석별 티켓 발급 |

소유권 변경은 [좌석 잠금 순서](seat-ownership.md)를 준수한다. 승인 결과는 결제 행 → 구매 관리 행 → 예약 → 좌석 ID 오름차순 → 주문 순으로 처리한다. 저장된 환불의 결과 반영은 결제 행 → 환불 행 → Handler 순서이며, 티켓팅 환불 연결은 후속 구현이다.
중복 성공 결과는 동일 결제인지 확인하고 기존 확정 결과를 반환한다. 티켓 재발급이나 카운터 재변경을 하지 않는다.
실패 확정은 기존 상태 머신과 남은 기한에 따라 재시도 또는 해제로 반영한다.
결과 불명확은 RECONCILING으로 기록하고 좌석을 보호한다. DB 기록 자체가 실패해도 승인 시도 기록으로 복구 후보를 찾을 수 있어야 한다.

## 5. 장애와 복구

PG와 우리 DB를 하나의 원자적 트랜잭션으로 묶을 수는 없다.
PG 성공 후 DB 확정 실패는 PG 결제 실패가 아니다. DB 변경은 전체 롤백하고, 좌석을 보호한 상태로 PG 결과를 재조회하여 확정 트랜잭션을 재실행한다.

준비 커밋 후 PG 호출 전 서버 종료, PG 요청 타임아웃, 승인 성공 후 응답 유실·서버 종료도 영속 승인 시도로 복구한다.
준비 기록만으로 요청이 실제 전송됐다고 단정하지 않는다. 결과 조회의 미존재·처리 중 응답만으로 즉시 실패 처리하거나 새 승인 시도를 만들지 않는다.
공통 대사의 후보·주기·PG 결과별 분기와 최종 실패 기준은 [공통 대사 운영 계약](../../operations/failure-handling.md#공통-결제-대사-46)에 구현돼 있다. 티켓팅 Handler 연결과 결제 이후 만료는 후속이다. checkout만 완료된 주문·예약에는 결제 시도 행이 없어 공통 대사가 예약 기한 만료를 대신 처리하지 않는다.
진행 중·불명확 결과를 실패로 추정하여 좌석을 반환하지 않는다.

## 6. 이벤트 경계

PaymentSucceeded 등의 기존 명칭은 결과 의미를 설명하는 원본 초안이다.
AFTER_COMMIT 리스너가 결제 성공을 받아 핵심 예매 상태를 확정하는 방식으로 구현하지 않는다.
핵심 상태는 위 결과 반영 트랜잭션에서 직접 조정한다.
커밋 이후 TicketReservationConfirmed 등으로 알림 같은 후속 작업을 처리한다.
리스너 실패는 로그·메트릭에 남긴다. Outbox/Kafka는 ADR-0001의 재검토 조건을 따른다.

## 7. 검증 계획

아래는 실행 결과가 아니다. Fake PG와 MySQL Testcontainers를 사용한다.

- 주문 생성 실패: 결제 진입의 예약 변경도 롤백.
- 중복 checkout: 주문 한 건, 최초 기한 유지.
- PG 응답 대기 중 DB 트랜잭션·행 잠금이 유지되지 않으며 좌석 재선점은 거절.
- 승인 시도 준비 커밋 후 서버 종료: 재기동 후 복구 후보 발견.
- PG 성공 후 DB 확정 중 실패: 결제·주문·티켓팅 변경 전체 롤백, 재조회 후 한 번만 확정.
- PG 성공 응답 유실·중복 결과: 좌석 보호, 기존 결과 반환, 티켓·카운터 중복 반영 없음.

## 8. 결제 기한 인정 기준 (DECIDED, 2026-11-12)

유효한 승인 시도를 서버가 결제 기한 안에 기록했고 그 기록이 커밋됐다면, 해당 시도의 성공이 기한 이후에 확인돼도 예매를 확정한다.
브라우저 버튼 클릭 시각, HTTP 요청 도착 시각, PG 승인 완료 시각이나 응답 수신 시각을 기한 판정 기준으로 삼지 않는다.

- 주문·예약·금액·좌석 소유권과 다른 진행 중 승인 시도가 없음을 검증한 뒤 승인 시도를 기록한다.
- 기한 판정 시각은 티켓팅의 구매 관리·예약·좌석 잠금을 획득하고 업무 검증을 마친 뒤 승인 시도를 기록할 때 DB 기준 UTC로 읽는다. 트랜잭션 시작 시각이나 티켓팅 잠금 대기 전 시각을 재사용하지 않는다.
- 경계는 기록 시각 < payment_expires_at이다. 기한과 정확히 같거나 이후이면 새 승인 시도를 허용하지 않는다.
- 기한 내 수락한 시도 기록과 주문 상태 변경을 포함한 준비 트랜잭션이 성공적으로 커밋돼야 유효하다. 기록 이후 changeStatus의 주문 잠금 대기로 기한이 지나도 성공적으로 커밋되면 유효하다. 롤백된 기록은 자격이 없다.
- PG 호출은 이 커밋 후에 수행한다. 기록 시각은 PG에 실제 요청이 전송됐다는 증거가 아니다.
- 기한 내 유효한 시도의 처리 중·결과 불명확 상태에서는 좌석과 구매 제한 수량을 유지한다.
- 같은 시도의 결과 조회·복구는 기한 이후에도 허용한다. 승인 재전송이 필요한 경우 동일 시도의 안전한 재실행 조건을 공통 결제 계약에서 확인해야 한다. 새 시도를 만드는 것과 구분한다.
- 기존 시도가 실패로 확정된 경우 새 시도는 남은 결제 기한 안에서만 허용한다. 기한이 지났으면 해제한다.
- 유효한 시도 없이 들어온 성공 결과는 이 규칙으로 자동 확정하지 않는다. 좌석 소유권과 PG 사실을 조사하고 보상·운영 처리를 결정한다.

예: 기한 12:05:00, 유효 시도 기록 12:04:59, 성공 확인 12:05:02 → 예매 확정.
기한 12:05:00, 신규 시도 기록 시점 12:05:00 → 요청 거절, PG 호출 없음.
티켓팅 잠금 대기 중 기한이 끝난 요청도 대기 전 접수 시각만으로 허용하지 않는다. 기한 내 기록을 마친 후의 주문 잠금 대기는 이 경우와 구분한다.

추가 검증 계획:

- 기한 직전 유효 시도 기록 후 늦은 성공: 한 번만 확정.
- 기한과 같거나 이후인 신규 시도, 티켓팅 잠금 대기 중 기한 종료: PG 호출 없이 거절.
- 티켓팅 잠금 아래 기한 내 기록 후 주문 잠금 대기로 기한 종료: 준비 트랜잭션이 커밋되면 유효한 시도로 인정.
- 기한 전 준비 기록 롤백: 유효한 시도로 인정하지 않음.
- 기한 이후 기존 시도 실패 확정: 새 시도 없이 좌석·카운터 해제.
- 기한 이후 불명확 상태 유지: 신규 승인 금지, 기존 시도 재확인만 수행.

## 9. 불명확 결과의 운영 확인 전환 (DECIDED, 2026-11-12)

- 결제 결과가 불명확한 상태로 5분 지속되면 운영 확인 대상으로 등록하고 운영 알림을 발생시킨다.
- 5분은 결제 기한과 별개이며, 해당 승인 시도의 최초 불명확 상태 진입 시각부터 계산한다. 반복 조회 실패와 서버 재시작으로 기준 시각을 갱신하지 않는다.
- 운영 확인 전환은 실패 확정이나 예약 취소가 아니다. RECONCILING과 좌석 소유권·구매 제한 수량을 유지한다.
- 운영 확인 중에도 최종 결과가 확인될 때까지 자동 PG 결과 조회를 계속한다. 조회 횟수나 경과 시간만으로 실패 처리하거나 좌석을 반환하지 않는다.
- 자동 조회에서 성공이 확인되면 동일 결과 반영 트랜잭션으로 확정한다. 최종 실패가 확인되면 남은 결제 기한에 따라 재시도 또는 해제한다.
- 운영 확인 등록·알림은 동일 승인 시도에 대해 중복 처리하지 않는다. 자동 복구와 운영 처리가 겹쳐도 같은 멱등 결과 반영 절차를 사용한다.
- 공통 payments.unknown_since_at에 최초 UNKNOWN 진입 시각을 보존하고 UNKNOWN 수·최대 나이 메트릭을 제공한다. 운영 확인 등록 여부의 저장과 중복 없는 알림은 아직 후속 구현이며 상세는 [공통 대사 운영 계약](../../operations/failure-handling.md)을 따른다.
- 운영자는 PG 사실을 확인해 처리한다. 근거 없는 강제 해제를 허용하지 않는다.

미확정 사항:

- 공통 대사 조회 간격은 운영 계약의 설정을 따른다. 실제 운영 알림 채널·수신 담당자는 미확정이다.
- 공통 대사는 오래된 PROCESSING도 조회하고 최초 UNKNOWN 시각을 기록한다. 이를 티켓팅의 운영 확인 등록·알림으로 연결하는 작업은 후속이다.
- 공통 최종 실패 분기는 운영 계약을 따른다. 동일 승인 재전송 허용 범위와 공연 시작까지 미해결된 경우의 고객·입장·보상 절차는 별도 확인이 필요하다.

검증 계획 (미실행):

- 최초 불명확 진입 후 5분 경과: 운영 확인 등록·알림 1회, 좌석 유지.
- 반복 조회 실패·서버 재시작: 최초 시각 유지, 운영 전환 타이머가 연장되지 않음.
- 운영 확인 전환 후 자동 조회 지속, 늦은 성공 시 한 번만 확정.
- 운영 처리와 자동 복구 경합: 상태·티켓·카운터 중복 변경 없음.

## 10. 만료 계약

승인 시도 유무와 최종 결과에 따른 좌석 반환, 승인 준비와의 경합은 [만료 설계](expiration.md)를 따른다. PAYMENT_PENDING이라는 예약 상태만으로 보호·반환을 판단하지 않는다.

## 구현 현황: 예약 엔티티 매핑

- TicketReservation을 ticket_reservations에 매핑했다. 사용자·회차·주문은 Long 스칼라 참조, 시각은 UTC Instant, 상태는 TicketReservationStatus의 VARCHAR 문자열이다.
- createHeld는 신규 HELD 예약을 생성한다. orderId/checkoutStartedAt/paymentExpiresAt은 최초 생성 시 NULL이다.
- 요청 키는 VARCHAR(100), holdRequestHash는 BINARY(32)에 맞춘다. 신규 생성은 32바이트 비교값을 요구하고 입력·반환 배열을 복사하여 외부 변형을 막는다. 기존 행의 NULL 해시는 조회 가능하다.
- 선점 기한·생성 시각은 호출자가 전달한다. 5분 기한 계산·현재 시각 검증·요청 정규화/해시 계산은 후속 application 구현 범위다.
- 사용자별 키와 order_id의 UNIQUE, 사용자·회차·주문 FK는 기존 Flyway를 그대로 사용한다. 새 마이그레이션은 없다.
- TicketReservationMappingTest는 MySQL Testcontainers/Flyway/ddl-auto=validate로 실제 저장 후 영속성 컨텍스트를 비워 조회한다.
- 결제 진입 필드·후속 상태는 SQL fixture로 준비해 매핑만 검증한다. 실제 checkout·승인·환불 전이와 활성 예약 1건 잠금 검증을 구현한 것은 아니다.
- Repository·Controller·서비스·공통 결제 계약은 이번 단계에서 변경하지 않는다.
- ./gradlew build 실행으로 예약 매핑 테스트 13개를 포함해 전체 192개 테스트가 통과했다. UTC 시각·해시·NULL 필드·저장된 결제 상태 조회, 사용자별 키/주문 중복 및 미존재 참조 거절을 확인했다.
