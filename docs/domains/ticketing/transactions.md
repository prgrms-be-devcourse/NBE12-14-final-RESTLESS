# 티켓팅 결제 트랜잭션 경계

- 상태: DECIDED (2026-11-12, 담당자 합의).
- 구현 상태: 설계만 반영. 애플리케이션과 결제 시도 저장 구조는 후속 구현 대상이다.
- OPEN: 공통 결제 전체 잠금 순서, 복구 작업 주기·담당, 재시도 세부 규칙.

## 1. 책임과 연결

티켓팅은 예약·좌석 소유권·구매 카운터·티켓을 소유한다.
공통 주문은 구매자·내역·최종 금액을, 공통 결제는 PG 요청과 결과를 소유한다.
checkout의 공통 Application Coordinator가 각 모듈의 Application Service를 통해 흐름을 조정한다.
다른 도메인의 Repository를 직접 접근하지 않는다.
예약은 ticket_reservations.order_id로 주문과 연결하고, 결제는 그 주문과 연결한다.
주문 유형·항목 스냅샷·결제 시도 컬럼과 API 상세는 공통 담당자와 후속 계약으로 정한다.

## 2. 결제 진입과 승인 시도 준비

결제 화면 진입과 실제 PG 승인 요청은 구분한다.

결제 진입 트랜잭션:

- 본인 예약, 좌석 소유권, 선점 기한을 검증한다.
- 최초 진입 시 공통 주문을 생성·연결하고 PAYMENT_PENDING 및 최초 결제 진입 시각·별도 결제 기한을 저장한다.
- 중복 진입은 기존 주문·기한을 반환한다. 주문 중복 생성과 기한 연장을 허용하지 않는다.
- 주문 생성·연결과 예약 변경은 함께 커밋하거나 함께 롤백한다.

실제 PG 승인 직전의 별도 준비 트랜잭션:

- 주문·예약·금액과 승인 요청 자격을 검증하고 승인 시도를 영속적으로 기록한다.
- 동시에 여러 승인 요청이 나가지 않도록 진행 중 시도를 식별한다.
- 승인 시도가 진행 중이거나 결과 불명확하면 단순 시간 경과로 좌석을 반환하지 않는다.
- 이 기록을 커밋한 뒤에만 외부 PG를 호출한다.
- 기한 판정은 8절을 따른다. 승인 시도 식별자·상태·컬럼의 구체적인 형태는 후속 공통 결제 계약에서 정한다.

## 3. PG 호출 구간: DB 트랜잭션 없음

준비 트랜잭션은 이미 커밋됐으며 좌석 행 잠금도 해제됐다. PG 호출을 감싸는 외부 DB 트랜잭션을 두지 않는다.
공통 Coordinator 전체를 하나의 @Transactional로 감싸지 않고, 준비와 결과 반영을 각각 별도 트랜잭션으로 실행한다.
외부 응답을 기다리는 동안 DB 연결과 행 잠금을 계속 보유하지 않는다.

DB 잠금이 풀려도 좌석의 HELD/current_hold_id와 결제 진행 기록은 남아 있다.
다른 선점 요청은 좌석을 잠근 뒤 이 상태를 확인하고 거절한다. 만료 처리도 결제 진행·불명확 상태를 검증한다.
즉, 잠금은 짧은 변경 작업을 직렬화하고, 실제 좌석 점유는 저장된 상태로 유지한다.

## 4. 결과 반영 트랜잭션

Coordinator는 검증된 PG 결과를 직접 전달하여 다음을 동일 DB 트랜잭션에서 확정한다.

| 소유 모듈 | 성공 시 반영 |
|---|---|
| 결제 | 승인 결과와 결제 완료 |
| 주문 | 결제 완료 |
| 티켓팅 | 예약 CONFIRMED, 선점 CONFIRMED, 좌석 SOLD, reserved_count 감소·confirmed_count 증가, 좌석별 티켓 발급 |

소유권 변경은 [좌석 잠금 순서](seat-ownership.md)를 준수한다. 공통 주문·결제 잠금까지 포함한 전체 순서는 후속 설계에서 정한다.
중복 성공 결과는 동일 결제인지 확인하고 기존 확정 결과를 반환한다. 티켓 재발급이나 카운터 재변경을 하지 않는다.
실패 확정은 기존 상태 머신과 남은 기한에 따라 재시도 또는 해제로 반영한다.
결과 불명확은 RECONCILING으로 기록하고 좌석을 보호한다. DB 기록 자체가 실패해도 승인 시도 기록으로 복구 후보를 찾을 수 있어야 한다.

## 5. 장애와 복구

PG와 우리 DB를 하나의 원자적 트랜잭션으로 묶을 수는 없다.
PG 성공 후 DB 확정 실패는 PG 결제 실패가 아니다. DB 변경은 전체 롤백하고, 좌석을 보호한 상태로 PG 결과를 재조회하여 확정 트랜잭션을 재실행한다.

준비 커밋 후 PG 호출 전 서버 종료, PG 요청 타임아웃, 승인 성공 후 응답 유실·서버 종료도 영속 승인 시도로 복구한다.
준비 기록만으로 요청이 실제 전송됐다고 단정하지 않는다. 결과 조회의 미존재·처리 중 응답만으로 즉시 실패 처리하거나 새 승인 시도를 만들지 않는다.
안전한 동일 시도 재실행·최종 실패 판단 조건과 복구 담당·주기는 후속 공통 결제 계약에서 정한다.
진행 중·불명확 결과를 실패로 추정하여 좌석을 반환하지 않는다.

## 6. 이벤트 경계

PaymentSucceeded 등의 기존 명칭은 결과 의미를 설명하는 원본 초안이다.
AFTER_COMMIT 리스너가 결제 성공을 받아 핵심 예매 상태를 확정하는 방식으로 구현하지 않는다.
핵심 상태는 위 결과 반영 트랜잭션에서 직접 조정한다.
커밋 이후 TicketReservationConfirmed 등으로 알림 같은 후속 작업을 처리한다.
리스너 실패는 로그·메트릭에 남긴다. Outbox/Kafka는 ADR-0001의 재검토 조건을 따른다.

## 7. 검증 계획

아래는 실행 결과가 아니다. Fake PG와 MySQL Testcontainers를 사용한다.

- 주문 생성 실패: 결제 진입의 예약 변경도 롤백.
- 중복 checkout: 주문 한 건, 최초 기한 유지.
- PG 응답 대기 중 DB 트랜잭션·행 잠금이 유지되지 않으며 좌석 재선점은 거절.
- 승인 시도 준비 커밋 후 서버 종료: 재기동 후 복구 후보 발견.
- PG 성공 후 DB 확정 중 실패: 결제·주문·티켓팅 변경 전체 롤백, 재조회 후 한 번만 확정.
- PG 성공 응답 유실·중복 결과: 좌석 보호, 기존 결과 반환, 티켓·카운터 중복 반영 없음.

## 8. 결제 기한 인정 기준 (DECIDED, 2026-11-12)

유효한 승인 시도를 서버가 결제 기한 안에 기록했고 그 기록이 커밋됐다면, 해당 시도의 성공이 기한 이후에 확인돼도 예매를 확정한다.
브라우저 버튼 클릭 시각, HTTP 요청 도착 시각, PG 승인 완료 시각이나 응답 수신 시각을 기한 판정 기준으로 삼지 않는다.

- 주문·예약·금액·좌석 소유권과 다른 진행 중 승인 시도가 없음을 검증한 뒤 승인 시도를 기록한다.
- 기한 판정 시각은 필요한 잠금을 획득한 뒤 기록 시점에 DB 기준 UTC 현재 시각으로 정한다. 트랜잭션 시작 시각이나 잠금 대기 전 시각을 재사용하지 않는다.
- 경계는 기록 시각 < payment_expires_at이다. 기한과 정확히 같거나 이후이면 새 승인 시도를 허용하지 않는다.
- 기록 시각과 검증 결과를 포함한 준비 트랜잭션이 성공적으로 커밋돼야 유효하다. 롤백된 기록은 자격이 없다.
- PG 호출은 이 커밋 후에 수행한다. 기록 시각은 PG에 실제 요청이 전송됐다는 증거가 아니다.
- 기한 내 유효한 시도의 처리 중·결과 불명확 상태에서는 좌석과 구매 제한 수량을 유지한다.
- 같은 시도의 결과 조회·복구는 기한 이후에도 허용한다. 승인 재전송이 필요한 경우 동일 시도의 안전한 재실행 조건을 공통 결제 계약에서 확인해야 한다. 새 시도를 만드는 것과 구분한다.
- 기존 시도가 실패로 확정된 경우 새 시도는 남은 결제 기한 안에서만 허용한다. 기한이 지났으면 해제한다.
- 유효한 시도 없이 들어온 성공 결과는 이 규칙으로 자동 확정하지 않는다. 좌석 소유권과 PG 사실을 조사하고 보상·운영 처리를 결정한다.

예: 기한 12:05:00, 유효 시도 기록 12:04:59, 성공 확인 12:05:02 → 예매 확정.
기한 12:05:00, 신규 시도 기록 시점 12:05:00 → 요청 거절, PG 호출 없음.
잠금 대기 중 기한이 끝난 요청도 대기 전 접수 시각만으로 허용하지 않는다.

추가 검증 계획:

- 기한 직전 유효 시도 기록 후 늦은 성공: 한 번만 확정.
- 기한과 같거나 이후인 신규 시도, 잠금 대기 중 기한 종료: PG 호출 없이 거절.
- 기한 전 준비 기록 롤백: 유효한 시도로 인정하지 않음.
- 기한 이후 기존 시도 실패 확정: 새 시도 없이 좌석·카운터 해제.
- 기한 이후 불명확 상태 유지: 신규 승인 금지, 기존 시도 재확인만 수행.

## 9. 불명확 결과의 운영 확인 전환 (DECIDED, 2026-11-12)

- 결제 결과가 불명확한 상태로 5분 지속되면 운영 확인 대상으로 등록하고 운영 알림을 발생시킨다.
- 5분은 결제 기한과 별개이며, 해당 승인 시도의 최초 불명확 상태 진입 시각부터 계산한다. 반복 조회 실패와 서버 재시작으로 기준 시각을 갱신하지 않는다.
- 운영 확인 전환은 실패 확정이나 예약 취소가 아니다. RECONCILING과 좌석 소유권·구매 제한 수량을 유지한다.
- 운영 확인 중에도 최종 결과가 확인될 때까지 자동 PG 결과 조회를 계속한다. 조회 횟수나 경과 시간만으로 실패 처리하거나 좌석을 반환하지 않는다.
- 자동 조회에서 성공이 확인되면 동일 결과 반영 트랜잭션으로 확정한다. 최종 실패가 확인되면 남은 결제 기한에 따라 재시도 또는 해제한다.
- 운영 확인 등록·알림은 동일 승인 시도에 대해 중복 처리하지 않는다. 자동 복구와 운영 처리가 겹쳐도 같은 멱등 결과 반영 절차를 사용한다.
- 최초 불명확 시각과 운영 확인 등록 여부는 DB에 보존해야 한다. 컬럼·작업 소유권 방식은 후속 공통 결제 스키마 설계 대상이다.
- 운영자는 PG 사실을 확인해 처리한다. 근거 없는 강제 해제를 허용하지 않는다.

미확정 사항:

- 자동 조회의 세부 간격·백오프와 실제 운영 알림 채널·수신 담당자.
- 준비 커밋 후 서버 종료 등 불명확 상태를 명시적으로 기록하지 못한 미완료 시도의 탐지·기준 시각 규칙.
- 안전한 동일 승인 재전송과 최종 실패 판정 조건, 공연 시작까지 미해결된 경우의 고객·입장·보상 절차.

검증 계획 (미실행):

- 최초 불명확 진입 후 5분 경과: 운영 확인 등록·알림 1회, 좌석 유지.
- 반복 조회 실패·서버 재시작: 최초 시각 유지, 운영 전환 타이머가 연장되지 않음.
- 운영 확인 전환 후 자동 조회 지속, 늦은 성공 시 한 번만 확정.
- 운영 처리와 자동 복구 경합: 상태·티켓·카운터 중복 변경 없음.

## 10. 만료 계약

승인 시도 유무와 최종 결과에 따른 좌석 반환, 승인 준비와의 경합은 [만료 설계](expiration.md)를 따른다. PAYMENT_PENDING이라는 예약 상태만으로 보호·반환을 판단하지 않는다.
