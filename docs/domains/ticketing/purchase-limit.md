# 구매 제한과 사용자·회차별 활성 예약

- 상태: DECIDED (2026-11-12, 담당자 합의).
- 구현 상태: TicketPurchaseLimit 엔티티 매핑 구현. 비관적 락·한도 검증·수량 변경 애플리케이션은 후속 구현 대상이다.

## 범위와 불변식

- 사용자·회차별 활성 예약은 최대 1건이다. 서로 다른 회차는 각각 진행할 수 있다.
- 활성 예약 상태는 HELD, PAYMENT_PENDING, RECONCILING이다.
- 확정 수량 + 선점 수량은 회차 max_tickets_per_user 이하이며 각 수량은 0 이상이다.
- 예약 한 건에는 여러 좌석이 포함될 수 있다. 활성 예약 1건 제한과 좌석 수 제한은 별개다.
- 확정·환불 진행/불명확 상태는 활성 예약 집합에는 포함하지 않지만, 환불 확정 전까지 confirmed_count에 포함한다.

## 공통 잠금 지점

선점·결제 확정·만료·취소·환불 등 수량이나 활성 예약 여부를 바꾸는 모든 경로가
사용자·회차의 ticket_purchase_limits 행을 잠그고 최신 상태를 재검증한다.
티켓팅 내부 순서는 구매 관리 행 → 예약 행 → 좌석 ID 오름차순이다.
결제 Handler 경로는 ADR-0003에 따라 결제 행을 먼저 잠근 뒤 티켓팅 내부 순서를 따른다.
다른 결제 행까지 추가로 잠그는 흐름의 전체 순서는 공통 결제와 후속 조율한다.

1. UNIQUE(user_id, performance_id)로 구매 관리 행 하나를 확보한다.
2. 행이 없으면 생성한다. 생성 경쟁의 UNIQUE 충돌 시 실패한 트랜잭션을 종료하고 새 트랜잭션에서 기존 행을 잠근다.
3. 잠금 획득 후 활성 예약과 현재 reserved_count/confirmed_count를 다시 확인한다. 잠금 대기 전 조회 결과를 사용하지 않는다.
4. 활성 예약이 이미 있으면 새 예약은 ACTIVE_RESERVATION_EXISTS로 거절한다. 클라이언트는 본인 활성 예약 조회로 이어갈 수 있다.
5. 활성 예약이 없고 confirmed_count + reserved_count + 요청 좌석 수 <= max_tickets_per_user이면 좌석 잠금·검증 후 선점한다.
6. 예약·선점·좌석·카운터 변경을 함께 커밋하거나 함께 롤백한다.

여러 탭에서 서로 다른 좌석을 요청해도 같은 사용자·회차 구매 관리 행에서 직렬화된다.
먼저 성공한 요청이 활성 예약을 생성하면 다음 요청은 이를 확인하고 거절한다.
같은 멱등성 키의 재전송은 기존 예약에 연결하고 새 예약을 만들지 않는다. 새 키여도 활성 예약·구매 한도 제한은 적용된다.
만료된 기존 예약은 [만료 규칙](expiration.md)에 따라 정리한 뒤 활성 여부와 수량을 재검증한다. 진행 중·불명확 결제를 만료로 간주하지 않는다.

## 수량 변경표

| 처리 | reserved_count | confirmed_count |
|---|---|---|
| N좌석 최초 선점 | +N | 유지 |
| 결제 진입·승인 시작·결과 불명확 | 유지 | 유지 |
| N좌석 결제 확정 | -N | +N |
| 선점 취소·만료·최종 실패 후 반환 | -N | 유지 |
| 결제 실패 후 기한 내 재시도 대기 | 유지 | 유지 |
| 환불 요청·환불 결과 불명확·환불 실패 | 유지 | 유지 |
| 확정된 N좌석 환불 완료 | 유지 | -N |

상태 전이가 실제로 일어났을 때만 수량을 바꾼다. 반복 결과·중복 Worker로 두 번 증감하지 않는다.
예매 확정 전 보상 취소는 확정 구매 환불과 구분하며 confirmed_count를 감소시키지 않는다.
구매 관리 카운터와 예약·좌석·티켓 상태가 불일치하면 임의로 보정하지 않고 복구 대상으로 식별한다.

## DB와 서비스의 역할

현재 DB의 사용자·회차 UNIQUE는 관리 행 하나를 보장하며, CHECK는 카운터 음수를 방지한다.
이 제약만으로 활성 예약 1건이나 회차별 최대 수량을 보장하지는 않는다.
모든 쓰기 경로가 공통 관리 행 잠금과 위 검증을 거쳐야 한다. 별도 활성 예약 UNIQUE/포인터 제약은 이번 결정에 추가하지 않는다.
정책에 필요한 DB 제약은 기존 Flyway를 유지한다. 엔티티 매핑 구현 현황은 아래에 기록한다.

## 검증 계획 (미실행)

- 같은 사용자·회차에서 서로 다른 좌석 동시 요청: 활성 예약 최대 1건.
- 최초 구매 관리 행 동시 생성: 행 1건, 예약과 카운터 일관성.
- 다른 사용자 또는 다른 회차: 독립적인 관리 행 사용, 좌석 자체의 경쟁은 별도 잠금으로 처리.
- 확정 구매 후 남은 한도 내 분할 구매 허용, 한도 초과 거절.
- RECONCILING 중 새 키·다른 탭 요청 거절, 수량 유지.
- 중복 확정·만료·환불 처리: 카운터 정확히 한 번 변경.
- 환불 요청 중 수량 유지, 환불 확정 후 구매 가능 수량 복원.
- 카운터 변경 중 실패: 예약·좌석 변경까지 전체 롤백.

## 구현 현황: 구매 관리 엔티티

- TicketPurchaseLimit을 ticket_purchase_limits에 매핑했다. id는 BIGINT IDENTITY, userId/performanceId는 NOT NULL 스칼라 ID 참조다.
- reservedCount/confirmedCount는 NOT NULL INT에 맞춰 int로 매핑한다. create(userId, performanceId)는 두 카운터가 0인 행을 생성한다.
- 이번 단계는 저장·조회 매핑만 구현한다. 임의 setter·수량 증감 메서드, 구매 한도·활성 예약 검사와 Repository 잠금 메서드는 추가하지 않는다.
- 기존 UNIQUE(user_id, performance_id), FK, 음수 방지 CHECK를 그대로 사용한다. 새 마이그레이션은 없다.
- TicketPurchaseLimitMappingTest는 MySQL Testcontainers/Flyway/ddl-auto=validate를 사용하고 영속성 컨텍스트를 비운 뒤 조회한다.
- 비영 카운터의 읽기와 음수 거절은 SQL fixture로 저장 상태를 준비하여 확인한다. 실제 수량 변경·경합 로직의 구현/검증을 의미하지 않는다.
- ./gradlew build 실행으로 전용 매핑 테스트 7개를 포함해 전체 179개 테스트가 통과했다. 사용자·회차 범위별 저장·조회, 중복 조합·음수 카운터·미존재 참조 거절을 확인했다.
