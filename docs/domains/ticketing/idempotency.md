# 티켓팅 멱등성 계약

## 현재 구현 범위 (DECIDED, 2026-11-12)

이 절이 아래 상세 설계의 구현 시점보다 우선한다. 설계 결정을 폐기하지 않고 구현을 단계적으로 나눈다.

후속 구현(DEFERRED):

- 전용 idempotency_requests 테이블과 상태 5개·완료 응답 저장·실행 입력 JSON.
- owner_token/lease_until 기반 실행권, 30초 점유·10초 연장·5초 복구 탐색과 자동 인계.
- 자원 생성 전 작업 조회 API와 접수만 된 요청의 자동 재실행.
- 미실행 요청의 자동 실행 60초 제한은 제안만 있었으며 미확정이다.

MVP 필수:

- 좌석 행 비관적 락·소유권 검증, 구매 관리 행 잠금·활성 예약 1건·구매 수량 제한.
- 선점 요청 키를 예약에 연결하고 성공한 동일 요청은 기존 예약에 연결한다. 키가 같고 내용이 다르면 충돌, 기존 예약이 만료돼도 기한 연장·재생성 금지.
- checkout은 예약 잠금 후 기존 order_id를 확인하여 주문을 한 번만 생성하고 최초 결제 기한을 유지한다.
- 결제·환불은 기존 공통 결제의 영속 시도·중복 방지 제약을 활용한다. 결과 불명확 중 새 승인·환불 금지.
- 결제 확정·좌석 반환·환불은 허용된 상태 전이와 DB 제약으로 한 번만 반영하며 카운터를 이중 변경하지 않는다.
- 동일 예약·좌석 티켓 UNIQUE와 UUID 번호 UNIQUE를 유지한다.

전용 테이블이 없으므로 자원 생성 전 모든 거절 응답의 영구 재현·범용 처리 중 작업 조회를 MVP에서 보장한다고 문서나 API에 표시하지 않는다.
예약·주문·결제 등 이미 생성된 자원의 조회·중복 변경 방지는 유지한다. 범용 202/statusUrl 계약은 전용 저장 구조와 함께 후속 구현한다.
사용자+작업+키는 목표 계약이다. 선점은 아래 사용자별 키 계약을 적용하고, checkout은 예약 기준 중복 방지로 범위를 제한한다. 공통 결제의 대상별 키 계약은 별도 조율 대상이며 전체 작업이 목표 범위를 만족한다고 표시하지 않는다.

중요: 여기서 미루는 자동 복구는 멱등성 접수 작업의 자동 실행·인계다.
PG 승인·환불 결과 불명확에 대한 자원 보호·결과 재확인·서버 종료 후 미완료 시도 발견·운영 확인은 거래 정합성 필수이며 제외하지 않는다.
불명확 상태 5분 후 운영 확인, 자동 PG 조회 지속 정책도 유지한다. PG 조회 간격과 공통 구현은 별도 조율한다.

권장 구현 순서:

1. 기존 정합성 마이그레이션 검증, 핵심 엔티티·상태 변경 메서드 구성.
2. 구매 관리 행·좌석 비관적 락으로 선점과 성공 요청 재전송 처리.
3. 취소·만료와 카운터의 한 번만 반환 처리.
4. 예약 잠금으로 checkout 주문 생성·기한 설정 한 번만 수행.
5. 공통 결제 준비 완료 후 Handler 성공·실패·불명확 처리와 티켓 중복 발급 방지 연결.
6. 환불 중복 방지·확정 후 한 번만 좌석 반환, PG 미완료 시도 재확인 경로 연결.
7. 각 단계에서 실제 MySQL 동시성·중복 결과·실패 롤백을 검증. 실행권 전용 기능은 후속 구현.

## 확정: 키 범위

- 상태: DECIDED (2026-11-12, 담당자 합의).
- 식별 범위: 인증된 사용자 + 작업 종류 + 요청 키.
- 작업 종류는 서버가 구분하는 선점, checkout, 승인 요청, 환불 요청 등이다. 클라이언트가 임의로 정하는 값이 아니다.
- 사용자 식별자는 인증 정보에서 가져온다.
- 회차·예약·주문 ID는 범위에 추가하지 않고 요청 내용에 포함하여 비교한다. URL 경로의 대상 ID도 비교 대상이다.
- 같은 범위·키로 같은 의미의 요청이 오면 기존 작업으로 연결한다. 다른 요청이면 IDEMPOTENCY_KEY_CONFLICT로 거절한다.
- 따라서 같은 사용자가 같은 선점 키를 다른 회차·좌석에 재사용하면 충돌한다. 같은 사용자의 같은 checkout 키를 다른 예약에 사용해도 충돌한다.
- 다른 사용자 또는 다른 작업 종류는 같은 키 문자열을 사용해도 서로 다른 작업이다.
- 새 키로도 활성 예약·좌석 소유권·주문 및 티켓 유일성·진행 중 승인 제한을 우회할 수 없다.

## 현재 구현과의 차이

기존 V20261111_1000의 UNIQUE(user_id, performance_id, request_key)는 V20261112_1020에서 사용자별 UNIQUE로 대체한다.
기존 제약은 다른 회차의 키 재사용을 막지 못했다. 변경 후에도 예약 생성 전 거절·범용 처리 중 상태·다른 작업의 키는 별도 전용 테이블이 필요하다.
별도 idempotency_requests 테이블과 UNIQUE(user_id, operation_type, request_key)를 사용하기로 확정했다. 아래 저장 계약의 실제 DDL·공통 모듈 소유권은 후속 설계 대상이다.
애플리케이션과 기존 마이그레이션은 유지한다. MVP 선점 키 제약은 새 V20261112_1020에 정의한다.

## 확정: 보관 기간

- 상태: DECIDED (2026-11-12, 담당자 합의).
- MVP에서는 멱등성 키를 삭제·재사용하지 않는다. 키·요청 내용 비교값·결과 자원 ID와 결과 분류를 보존한다.
- 진행 중·결과 불명확 작업은 경과 시간만으로 삭제하지 않는다.
- 상세 응답 데이터의 정리·보관 기간은 별도 정책으로 결정한다. 키 이력을 정리하려면 늦은 요청의 중복 실행 방지 대안을 먼저 합의한다.
- 만료·취소된 예약에 대한 같은 키 재전송도 기존 자원에 연결한다. 선점이나 결제 기한을 연장하지 않는다. 현재 상태는 자원 조회로 확인한다.

## 확정: 처리 중 응답

- 같은 키·같은 요청이 처리 중이면 202 Accepted와 REQUEST_PROCESSING, 기존 작업의 statusUrl을 반환한다.
- 자원이 이미 생성됐다면 reservationId 등 식별자를 함께 제공할 수 있다. 아직 자원이 없다면 멱등성 작업 자체를 조회할 수 있는 주소를 제공해야 한다.
- statusUrl은 인증된 본인의 작업만 조회할 수 있어야 한다. 실제 조회 경로와 DTO는 후속 API 설계 대상이다.
- 같은 범위·키에 다른 내용이면 처리 중이어도 409 IDEMPOTENCY_KEY_CONFLICT로 거절한다.
- 202는 접수·처리 중이라는 의미이며, 결제 성공이나 새로운 작업 생성을 뜻하지 않는다.

## 확정: 실패 후 재전송

| 결과 분류 | 동일 키 재전송 |
|---|---|
| 좌석 불가·구매 한도 초과 등 확정된 비즈니스 거절 | 같은 거절을 반환한다. 새 구매 의도는 새 키로 요청한다. |
| 교착·잠금 시간 초과 등 전체 롤백과 외부 부작용 없음이 확인된 내부 오류 | 같은 키로 재시도할 수 있다. 실행 시 상태·기한을 다시 검증한다. |
| 응답 유실·PG 타임아웃 등 결과 불명확 | 기존 작업 확인·복구로 연결한다. 새 승인·환불을 실행하지 않는다. |
| PG 승인 최종 실패 | 기존 시도의 실패 결과를 반환한다. 기한 내 새 승인 시도는 새 키를 사용한다. |

HTTP 500만으로 롤백 여부를 판단하지 않는다. DB 커밋 여부와 저장된 작업·PG 시도 기록을 확인한다.
재시도 가능한 오류는 최초 키와 요청 내용의 연결을 유지한다. 같은 키를 다른 요청에 재사용할 수 없다.
같은 키로 동시에 재전송돼도 실행 주체는 하나로 제한해야 한다. 작업 소유권과 재시도 가능 상태는 영속적으로 관리한다.
기존 성공 작업은 같은 결과 자원에 연결하며 중복 부작용을 만들지 않는다.
저장된 결과 응답과 현재 자원 상태의 표현 방식은 후속 DTO 설계에서 구체화한다.

## 검증 계획 (미실행)

- 같은 사용자·작업·키·요청: 같은 자원, 중복 부작용 없음.
- 같은 선점 키에 다른 회차·좌석, 같은 checkout 키에 다른 예약: 충돌.
- 다른 사용자 또는 작업 종류에 같은 문자열 키: 독립 처리.
- 다른 키의 동시 요청: 기존 도메인 불변식 유지.

- 완료·거절 후 동일 키 재전송: 기존 결과에 연결, 신규 부작용 없음.
- 처리 중 중복 요청: 202와 본인 작업 조회 주소, 실행 주체 하나.
- 전체 롤백 확인 후 같은 키 재시도: 최초 요청 내용 유지, 새 시점 상태·기한 재검증.
- PG 결과 불명확·커밋 후 응답 유실: 실패로 오인하거나 새 승인을 만들지 않음.
- 예약 만료 후 같은 키: 기존 예약에 연결, 좌석 재선점·기한 연장 없음.

## 확정: 별도 멱등성 테이블 (DECIDED, 2026-11-12)

예약·주문·결제의 업무 상태와 별도로 요청 접수·처리 결과를 idempotency_requests에 보존한다.
예약 생성 전 거절·처리 중 상태도 표현하며 선점·checkout·승인·환불 작업을 구분한다.
이번 변경은 문서만 반영한다. 기존 공통 결제의 멱등성 제약을 제거하거나 변경하지 않으며 연결 방식은 담당자와 조율한다.

| 논리 필드 | 의미 |
|---|---|
| id | 처리 중 작업 조회에 사용할 내부 식별자 |
| user_id, operation_type, request_key | 인증 사용자·서버 정의 작업·요청 키, 복합 UNIQUE |
| request_hash | 정규화한 의미상 요청 내용의 비교값 |
| status | 처리 중·성공·확정 거절·재시도 가능·결과 불명확 등의 분류, 실제 enum은 후속 정의 |
| result_type, result_id | 예약·주문·paymentId 등 기존 결과 자원 연결 |
| http_status, response_body | 완료 결과 응답 재현용 데이터 |
| created_at, updated_at | 최초 접수·갱신 시각 |

작업 소유자·점유 기한 등 실행권 필드는 후속 실행·복구 계약에서 구체화한다.
결과가 아직 없으면 자원 참조·완료 응답은 없을 수 있다. 기본 타입·길이는 아래 확정 스키마를 따른다. 실제 DDL과 CHECK 상세는 후속 작업이다.
요청 키는 대소문자까지 동일한 값으로 비교할 수 있도록 저장·인덱스 비교 규칙을 정해야 한다.

요청 내용에는 본문뿐 아니라 작업 대상인 URL 경로 ID를 포함한다.
JSON 공백·필드 순서 차이는 무시하고, 좌석 배열은 중복 ID를 거절한 뒤 순서가 의미 없으면 정렬해 비교한다.
인증 토큰·결제 민감정보나 원본 요청 전체를 그대로 저장하지 않는다. 완료 응답에도 민감정보가 포함되지 않도록 구성한다.
해시는 승인 자격 검증이나 금액 검증을 대체하지 않는다.

같은 복합 키의 INSERT는 UNIQUE로 한 건만 허용한다. 충돌 시 기존 request_hash를 비교한다.
다르면 409, 같으면 기존 상태에 따라 202·완료 결과·복구 또는 재시도 경로로 연결한다.
접수 기록 UNIQUE만으로 실행자 하나가 보장되지는 않으며 실행권과 상태 변경 절차가 별도로 필요하다.

DB 내부 작업의 업무 변경과 멱등성 완료 결과는 동일 트랜잭션으로 커밋한다.
접수 기록 자체는 업무 수행 전에 영속화할 수 있지만 업무 커밋과 완료 결과 기록은 분리하지 않는다.
PG가 있는 작업은 외부 호출 전에 영속 승인 시도 paymentId와 연결한다. 재전송은 해당 시도 확인·복구로 연결한다.
오래된 처리 중 기록만으로 실패·롤백을 추정하여 새 작업을 실행하지 않는다.

## 확정: 비관적 락 기반 실행권 (DECIDED, 2026-11-12)

실행권 획득·변경은 멱등성 행의 SELECT ... FOR UPDATE로 직렬화한다.
조건부 UPDATE 방식은 초기 구현에 사용하지 않으며 추후 비교 실험 대상으로 남긴다.

1. 사용자·작업·키 UNIQUE로 접수 기록을 한 건 확보한다. 생성 충돌은 실패한 트랜잭션을 정리한 뒤 기존 행을 조회한다.
2. 짧은 트랜잭션에서 멱등성 행을 잠그고 요청 내용과 처리 상태를 재검증한다.
3. 완료면 기존 결과를 반환하고, 유효한 실행자가 처리 중이면 202를 반환한다.
4. 최초 실행 가능 상태이거나 안전한 인계 조건이 충족되면 새로운 owner_token과 lease_until을 저장하고 커밋한다.
5. DB 업무 실행 시에도 멱등성 행을 먼저 잠근 뒤 담당표를 검증한다. 다른 실행자에게 넘어간 작업은 수행하지 않는다.
6. 담당표 검증 후 업무 변경과 멱등성 완료 결과를 같은 트랜잭션에서 커밋한다. 잠금을 유지하는 동안 다른 실행자의 인계는 허용되지 않는다.

owner_token은 실행권을 획득할 때마다 바꾸는 담당표이며 서버 식별자만으로 재사용하지 않는다.
PG 호출 중에는 멱등성 행을 포함한 DB 잠금을 유지하지 않는다.
외부 호출 이후 결과 기록에도 현재 담당표를 검증하고, 권한을 잃은 실행자가 멱등성 상태를 덮어쓰지 않도록 한다.
관측한 PG 결과는 공통 결제의 동일 paymentId 복구 경로로 연결하며 오래된 담당표의 독자적인 도메인 변경을 허용하지 않는다.

전체 멱등성·결제·도메인 잠금 순서는 후속 공동 설계 대상이다. ADR-0003의 결제 행 → 도메인 행 순서를 역전하지 않는다.
점유 만료는 인계 검토 조건이며 PG 실패·좌석 반환·신규 승인 재전송의 근거가 아니다.
점유·연장·인계 규칙은 아래 확정 사항을 따른다. 코드·마이그레이션은 변경하지 않는다.

추가 검증 계획 (미실행):

- 같은 키 동시 실행권 요청: 한 담당표만 획득, 다른 요청은 202 또는 완료 결과.
- 이전 담당표로 업무 시작·완료 기록 시도: 거절, 부작용 없음.
- DB 업무 중 인계 요청: 행 잠금 해제 후 최신 상태를 재검증.
- PG 호출 대기 동안 DB 잠금 미유지, 점유 만료만으로 새 승인 실행 없음.

## 확정: 실행권 시간과 서버 종료 후 인계 (DECIDED, 2026-11-12)

- 실행권 점유 시간은 30초다. 최초 획득·인계 시 새 owner_token과 DB 기준 UTC 현재 시각 + 30초의 lease_until을 저장한다.
- 작업이 계속되는 동안 10초마다 연장을 시도한다. 짧은 트랜잭션에서 멱등성 행을 SELECT ... FOR UPDATE 하고 담당표·상태·기한을 다시 검증한다.
- 담당표가 같고 미완료이며 DB 현재 시각 < lease_until인 경우에만 현재 시각 + 30초로 연장한다. 이전 기한에 30초를 누적하지 않는다.
- DB 현재 시각 >= lease_until이면 이전 담당표로 연장하거나 새 업무를 시작할 수 없다. 담당표 변경·연장 실패 후 독자적으로 작업을 계속하지 않는다.
- 이미 담당표를 검증하고 멱등성 행을 잠근 DB 업무 트랜잭션은 완료 결과까지 함께 커밋/롤백한다. 그 잠금이 유지되는 동안 다른 실행자가 인계하지 못한다. 점유 시간은 DB 트랜잭션 강제 중단 시간이 아니다.
- 연장 작업이 본인의 DB 업무 잠금에 막힐 수 있으므로 업무 트랜잭션을 짧게 유지한다. 트랜잭션·락 대기 제한은 후속 구현에서 정한다.
- PG 대기 중 연장은 별도 짧은 트랜잭션으로 수행하며 외부 호출을 감싸는 DB 잠금을 유지하지 않는다.

복구 탐색은 5초마다 수행한다. 이는 확인 주기이며 정확히 만료 순간에 복구된다는 보장은 아니다.

1. 점유 기한이 지난 미완료 기록을 후보로 찾는다. 후보 조회만으로 실행 권한을 얻지 않는다.
2. 해당 행을 잠그고 최신 상태·기한을 재검증한다. 완료됐거나 다른 실행자의 유효 점유가 있으면 인계하지 않는다.
3. 인계 가능하면 새 담당표와 30초 점유를 기록한다. 여러 복구 작업이 겹쳐도 같은 행 잠금으로 직렬화한다.
4. DB 내부 작업은 기존 업무·완료 기록을 확인하고 재시도 가능한 경우에만 상태·비즈니스 기한을 다시 검증하여 실행한다.
5. paymentId가 연결된 작업은 기존 결제 시도의 결과 조회·복구로 연결한다. 점유 만료는 PG 실패나 새 승인/환불 재전송의 근거가 아니다.
6. 이전 실행자의 늦은 결과는 이전 담당표로 멱등성 상태를 덮어쓰지 않는다. 관측된 PG 결과는 동일 paymentId의 공통 멱등 결과 반영 경로에서 확인한다.

복구 작업은 잠긴 후보 하나 때문에 전체 탐색이 장시간 막히지 않도록 해야 한다. 실제 후보 선택·락 대기 제어는 구현 설계 대상이다.
이 5초 복구 탐색은 불명확 결제의 PG 조회 간격과 다르며, PG 재조회 간격은 공통 담당자와 별도 조율한다.

추가 검증 계획 (미실행):

- 최초/인계 점유 30초, 유효 담당자의 10초 주기 연장, 현재 시각 기준 기한 재설정.
- 만료 정각·이후 연장 거절, 다른 담당표의 연장·완료 기록 거절.
- 연장과 인계 경합: 잠금 획득 후 최신 기한 재검증, 유효 담당표 하나 유지.
- 서버 종료 후 5초 주기 탐색으로 후보 발견, 완료 기록 재실행 없음.
- DB 트랜잭션 중 후보 발견: 잠금 해제 후 커밋/롤백 결과에 따라 처리.
- PG 호출 중 점유 만료·인계: 새 승인 없이 동일 paymentId 재확인.

## 확정: 상태 5개와 기본 스키마 (DECIDED, 2026-11-12)

| 상태 | 의미 | 동일 요청 재전송 |
|---|---|---|
| PROCESSING | 접수·실행 대기 또는 실행 중 | 202 및 작업 조회 |
| SUCCEEDED | 해당 요청 성공 완료 | 저장된 성공 결과 |
| REJECTED | 확정된 업무 거절·실패 | 저장된 실패 결과 |
| RETRYABLE | 전체 롤백·외부 부작용 없음이 확인됨 | 실행권 획득 후 같은 요청 재시도 |
| RECONCILING | 외부 결과 확인 중 | 202 및 기존 시도 복구 |

PROCESSING → SUCCEEDED/REJECTED/RETRYABLE/RECONCILING,
RETRYABLE → PROCESSING, RECONCILING → SUCCEEDED/REJECTED를 기본 흐름으로 한다.
checkout 성공은 결제 성공이 아니라 해당 요청의 주문·결제 진입 준비 완료를 의미한다.
PG 최종 실패는 그 승인 요청의 REJECTED다. 예약은 남은 기한에 따라 재시도 대기 또는 반환한다.
PROCESSING이어도 아직 실행자가 없을 수 있다. 상태만으로 실행권을 판단하지 않는다.

## 확정: 자동 복구용 최소 실행 입력 (DECIDED, 2026-11-12)

## MVP 선점·checkout 계약 (DECIDED, 2026-11-12)

### 선점 키

- ticket_reservations.request_key에 선점 키를 보존하고 UNIQUE(user_id, request_key)를 적용한다. 작업 종류는 선점 전용 저장 위치로 구분한다.
- V20261112_1020 마이그레이션으로 기존 회차 포함 UNIQUE를 대체한다. 키는 최대 100자이며 대소문자와 후행 공백을 구분하는 utf8mb4_0900_bin을 사용한다.
- hold_request_hash BINARY(32)에 회차 ID와 중복 검증 후 정렬한 판매 좌석 ID의 정규화 요청 SHA-256을 저장한다. 신규 예약에는 서비스가 반드시 기록한다.
- 같은 사용자·키·요청이면 기존 예약에 연결한다. 다른 회차 또는 다른 좌석이면 IDEMPOTENCY_KEY_CONFLICT다. 만료·취소돼도 키 재사용·기한 연장·재선점하지 않는다.
- 구매 관리 행 잠금 후 기존 사용자·키를 다시 조회한다. 없으면 한도·활성 예약·좌석 가용성을 검증해 생성한다.
- 다른 회차는 서로 다른 구매 관리 행을 잠그므로 사용자·키 UNIQUE가 마지막 방어선이다. 해당 제약 충돌이면 전체 롤백 후 새 트랜잭션에서 기존 예약과 내용을 비교한다. 모든 무결성 오류를 키 충돌로 취급하지 않는다.
- 예약·선점·좌석·카운터·키·해시는 한 트랜잭션으로 반영한다. 예약 생성 전 거절은 영구 재현하지 않는다.

기존 데이터 호환:

- 과거 예약에는 최초 해시가 없으므로 컬럼은 NULL 허용으로 추가한다. 실제 저장 데이터에 없는 최초 요청을 추측해 백필하지 않는다.
- 기존 NULL 해시 재요청은 보존된 예약의 회차·원본 선점 좌석 집합으로 최초 요청이 확실히 재구성될 때만 비교한다. 재구성 불가이면 자동 재실행하지 않고 운영 확인 대상으로 남긴다.
- 기존 동일 사용자·키 중복은 아래 조회로 사전 확인한다. 충돌 키를 자동 변경하거나 예약을 삭제하지 않는다.

```sql
SELECT user_id, request_key COLLATE utf8mb4_0900_bin AS comparison_key, COUNT(*) AS request_count
FROM ticket_reservations
GROUP BY user_id, request_key COLLATE utf8mb4_0900_bin
HAVING COUNT(*) > 1;
```

현재 MVP의 정규화 형식은 UTF-8 문자열 `v1\n<performanceId>\n<오름차순 판매 좌석 ID를 쉼표로 연결>`이며 마지막 줄 끝에는 개행이 없다.
예를 들어 회차 100의 좌석 [11, 10]은 `v1\n100\n10,11`의 SHA-256으로 저장한다.
빈 목록·중복·NULL·0 이하 ID는 정규화 전에 거절한다. 키는 공백만 있는 값과 100자 초과를 거절하며 trim/소문자 변환을 하지 않는다.
향후 형식을 바꾸더라도 기존 해시의 재요청 호환성을 유지해야 한다. TicketReservationServiceTest에 동일 키의 동시·순차 재요청, 좌석 순서 정규화, 다른 회차·좌석 충돌 검증을 작성했으며 아직 실행하지 않았다.

### checkout

- MVP checkout은 범용 요청 키 계약 대신 예약 기준으로 중복 생성·변경을 막는다.
- 본인 예약을 잠그고 기존 order_id와 checkout_started_at/payment_expires_at을 확인한다.
- 최초 진입만 주문 생성·연결 및 최초 결제 기한을 설정한다. 재요청은 기존 주문·최초 기한을 반환한다. 기존 order_id가 있으면 결제 기한 경과·후속 상태와 무관하게 새 주문·기한을 만들지 않는다. 주문 누락·최초 기한 누락은 데이터 오류로 처리하며 새 주문으로 대체하지 않는다.
- 같은 요청 키를 다른 예약에 재사용한 충돌까지 MVP checkout에서 보장하지 않는다.
- 주문 생성과 예약 연결은 동일 트랜잭션으로 수행한다. 주문 모듈의 application 서비스를 사용한다.

### 구현 시작 조건

핵심 선점 정책·DB 제약·구매 제한·재요청 처리 방향은 확정되어 좌석 선점 구현을 시작할 수 있다.
엔티티 매핑과 좌석 조회, 최초 선점 POST·결제 전 HELD 만료·본인 선점 취소 DELETE를 구현했다. 취소는 별도 요청 키 없이 예약 잠금과 RELEASED 상태로 중복 반환을 막는다. 본인 활성 예약·예약 상세 GET도 구현했다. checkout 주문 준비도 구현했다. 티켓팅의 결제 시도 연결·PG 승인 결과 반영·결제 이후 취소·환불 API는 후속 범위다.
회차 조회는 concert 모듈의 application 계약으로 제공하여 ticketing이 concert Repository를 직접 참조하지 않게 한다.
좌석 배열 검증·정규화는 위 MVP 계약, HTTP 오류 매핑은 [API 계약](../../contracts/api/ticketing.md)을 따른다.
선점·만료는 각각 READ_COMMITTED의 새 트랜잭션으로 실행하며, 구매 관리 행 생성과 사용자별 키 UNIQUE 충돌·교착·잠금 대기 실패는 전체 롤백 후 최대 3회 시도한다.
재시도 가능한 UNIQUE는 uk_ticket_purchase_limits_user_performance와 uk_ticket_reservations_user_request_key로 제한한다. 그 외 무결성 오류는 키 충돌로 오인하지 않는다.
잠금 대기 시간은 환경의 MySQL innodb_lock_wait_timeout을 사용하며 이번 구현에서 DB·세션 값을 변경하지 않는다. 시도 소진은 SEAT_LOCK_TIMEOUT이다.
만료 예약 발견 시 기존 선점 트랜잭션을 롤백한 뒤 해당 예약의 전체 반환을 별도 트랜잭션에서 수행하고 최초 입력으로 재시도한다.
첫 범위는 지정석 선점과 기존 예약 반환까지로 두고, 결제 Handler 변경·전용 멱등성 테이블은 포함하지 않는다.

checkout은 READ_COMMITTED 새 트랜잭션에서 구매 관리 행 → 예약 → 좌석 ID 오름차순으로 잠근다. 잠금 경합은 전체 롤백 후 최대 3회 시도한다. 본문·Idempotency-Key는 요구하지 않으며 응답은 200이다. TicketCheckoutServiceTest 13개가 통과했다. 반복 요청·기한 경과 후 재요청·8개 동시 요청에서 주문 한 건과 저장된 최초 기한을 보존하고, 취소·만료 경합과 오류 시 전체 롤백을 확인했다.
