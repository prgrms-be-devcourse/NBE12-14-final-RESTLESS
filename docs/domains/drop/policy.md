# Drop 정책

> 관련 코드: `backend/src/main/java/com/restless/drop/`
>
> 마지막 확인: 2026-11-13 (#79에서 코드와 대조)

상태 표기: `DECIDED` 결정됨, `PROPOSED` 제안, `OPEN` 미확정, `DEFERRED` 보류

## 1. 도메인 정의 (DECIDED)

- Drop 1개 = 기간 한정으로 판매하는 대표 상품 1개
- Drop 1개는 SKU를 1개 이상 가진다
- SKU는 독립적인 재고 관리 단위이며, SKU마다 가격과 재고를 따로 관리할 수 있다
- 일반 굿즈는 `FREE` SKU, 의류는 `S`, `M`, `L` 등 옵션별 SKU를 쓴다

| 상품 | SKU | 재고 |
|---|---|---:|
| 포토카드 | FREE | 1,000 |
| 후드티 | S | 200 |
| 후드티 | M | 400 |
| 후드티 | L | 300 |

SKU 한 개는 재고 한 개라는 뜻이 아니다.

## 2. 구매 수량 (DECIDED)

- 주문당 SKU 한 종류, 수량 1개
- 같은 사용자의 누적 재구매 허용
- 같은 드롭에서 동시에 진행 중인 구매 거래는 사용자당 최대 1건

동시 활성 구매 제한은 누적 구매 횟수 제한이 아니다. 진행 중인 거래가 확정되거나 끝나서 슬롯이 해제되면 다시 살 수 있다.

## 4. 구매 흐름 (DECIDED)

상품 상세 → 옵션 선택 → 구매하기 → 배송·결제 페이지 → 결제하기 → MySQL 대기열 → 입장 허가 → 재고 예약 + 주문 생성 → 토스 PG 인증과 승인 → 내부 구매 확정 → 주문 상세

1. 사용자가 드롭 목록에서 상품을 조회한다.
2. 상품 상세에서 SKU를 고른다.
3. `구매하기`를 누르면 배송·결제 페이지로 간다.
4. 회원 기본 배송지를 불러오고, 사용자는 이 주문의 배송지를 수정할 수 있다.
5. 상품, SKU, 수량 1개, 서버가 계산한 금액을 확인한다.
6. `결제하기`를 누르면 MySQL 구매 대기열에 들어간다.
7. 서버가 대기 순서와 입장 허가율을 관리한다.
8. 입장이 허가되면 구매권을 확인한다.
9. MySQL에서 SKU 재고 1개를 원자적으로 예약한다.
10. 같은 DB 트랜잭션에서 공통 Order와 스냅샷을 만든다.
11. 예약에 성공한 뒤에만 토스 결제 인증을 시작한다.
12. 서버가 승인 가능 상태를 확인하고 PG 최종 승인을 요청한다.
13. PG 승인과 내부 DB 구매 확정이 모두 성공하면 주문을 `PAID`로 표시한다.
14. 구매자는 주문 상세에서 확정된 결과를 본다.

### 시점별 변화

| 시점 | 재고 | 주문 |
|---|---|---|
| 상품 조회, 옵션 선택, 배송·결제 페이지 진입 | 없음 | 없음 |
| 결제하기 클릭 | 없음 (대기열 진입만) | 없음 |
| 대기열 입장 허가 | 없음 | 없음 |
| 재고 예약 성공 | available -1, reserved +1 | PENDING_PAYMENT 생성 |
| PG 승인, 구매 확정 | reserved -1, sold +1 | PAID |
| 결제 실패 확정, 예약 기한 전 | 없음 (재결제 대기) | PENDING_PAYMENT |
| 예약 만료, 기한 뒤 결제 실패 확정 | reserved -1, available +1 | CANCELLED |
| 전액 환불 확정 | sold -1, available +1 | REFUNDED |

가용 재고는 PG 승인 후가 아니라 PG 승인 전 예약 단계에서 차감한다. 마지막 재고를 두고 여러 사용자가 결제할 때 중복 판매를 막기 위해서다.

### 대기열 진입 시점 (DECIDED)

대기열은 상품 상세의 `구매하기`가 아니라 배송·결제 페이지의 `결제하기` 클릭 때 들어간다.

- 주소 입력까지 마친, 구매 의사가 있는 사용자 위주로 부하를 제어한다
- 재고 예약 API로 들어오는 비율을 직접 제어한다
- 대기열 등록과 재고 예약을 나눠서 측정한다
- 재고 예약 전까지 재고를 점유하지 않는다

대기열은 구매를 보장하지 않는다. 구매권 발급과 재고 예약 성공은 별개다.

## 5. 화면

Drop 전용: 드롭 목록, 드롭 상세, 배송·결제 페이지, 결제 대기 상태 UI, 운영자 드롭 목록과 등록, 운영자 상품·SKU·재고 설정

공통: 서비스 메인, 주문·결제 상세, 내 주문 내역, 회원 정보와 기본 배송지

대기 상태는 배송·결제 페이지 안의 UI나 독립 경로로 구현할 수 있다. 독립 대기실 페이지는 필수가 아니다.

토스 결제 성공, 실패 리다이렉트를 처리해야 하며, 성공 URL에 도착했다는 것만으로 `PAID`를 표시하지 않는다.

## 6. 판매 정책

- 드롭은 시작 시각과 종료 시각을 가진다.
- 판매 가능 여부는 서버 시각과 판매 상태를 함께 확인한다.
- 판매 시작 전과 종료 후에는 신규 예약을 만들지 않는다.
- 판매 종료 후에도 기존 결제의 확인, 복구, 환불은 가능하다.
- 판매 기간 종료와 품절은 다른 개념이다.

판매 판정 (DECIDED, 2026-11-13): 게시된 드롭(`SCHEDULED`/`OPEN`)이고 서버 시각이 `opensAt <= now < closesAt`이면 판매 중이다.
상태 전환 스케줄러 없이 시각으로 판정한다. `OPEN`/`CLOSED` 전환은 표시용이다. 시작 시각이 이미 지난 드롭도 등록할 수 있다. 등록은 항상 `DRAFT`라서 게시하는 순간 판매가 시작된다.

## 7. 구매권 정책 (DECIDED, 2026-11-13)

- 구매권은 사용자와 드롭에 귀속된다.
- 구매권 없이 신규 재고 예약을 만들 수 없다.
- 입장이 허가되어도 재고 확보는 보장되지 않는다.
- 만료된 구매권, 다른 사용자의 구매권은 쓸 수 없다.
- 중복 요청으로 새 예약을 만들지 않는다.
- 초기 구매권의 기준 저장소는 MySQL이다.

- 구매권 TTL은 입장 허가부터 5분이다.
- WAITING 상태 조회가 30초보다 오래 끊기면 이탈로 닫는다. 다시 들어오면 새 순번을 받는다.
- 진입 순 정렬과 `SKIP LOCKED` 배치 허가를 사용한다. 정확한 선착순보다 처리 속도를 우선한다.
- 대기 상태는 배송·결제 페이지 안에 표시한다. 별도 대기실 페이지는 만들지 않는다.
- 구매권 소비는 재고 점유 성공과 같은 트랜잭션에서 반영한다. 품절이나 주문 생성 실패 시 소비하지 않는다.
- `restless.drop.queue.required=false`는 EXP-02 대기열 유무 비교와 D2 검증에 사용한다.

경계값 (DECIDED, 2026-11-13):

- heartbeat가 끊긴 시간이 정확히 30초면 대기를 유지하고, 30초보다 길면 이탈로 닫는다.
- 구매권은 `admittedUntil`과 같은 시각부터 만료다.
- 화면에 있다는 신호는 상태 조회(`GET .../queue/me`)뿐이다. 진입 재요청(`POST .../queue/entries`)은 heartbeat를 늘리지 않는다.
- 상태 조회는 회원의 최신 대기 기록으로 답한다. `EXPIRED`·`CONSUMED`는 그대로 보여 주고, 최신 기록이 `CLOSED`면 404다. 다시 들어오면 새 기록을 만든다.
- 판매가 끝나면 `WAITING`은 조회·입장 작업에서 `CLOSED`로 닫는다. `ADMITTED`는 TTL로 만료되고, 신규 재고 점유는 판매 기간 검증이 막는다.
- 순번과 대기 인원 메트릭에서 heartbeat가 끊긴 `WAITING`은 뺀다.

## 8. 재고 예약 정책

- SKU별로 재고를 독립적으로 관리한다.
- 결제 인증 전에 재고를 예약한다.
- 재고 예약과 주문 생성은 하나의 MySQL 트랜잭션이다.
- 예약 만료는 PG 최종 승인 시작과의 경합을 제어해야 한다.
- PG 최종 승인 여부가 불확실한 동안 재고를 반환하지 않는다.
- PG 취소가 확인되기 전에는 환불을 이유로 재고를 복원하지 않는다.

예약 TTL 5분은 초기 제안값이다. PG 결제창의 실제 인증 시간을 보고 확정한다.

만료 작업 (DECIDED, 2026-11-13):

- 만료 대상은 `RESERVED`이고 기한이 지난 예약뿐이다. 기한과 같은 시각도 만료로 본다. `CONFIRMING`, `RECONCILING`, `COMPENSATING`은 건드리지 않는다.
- 한 번에 기한이 오래된 순으로 최대 100건을 가져와, 건마다 새 트랜잭션에서 예약 행을 잠그고 상태와 현재 시각을 다시 확인한다.
- 한 건이 실패해도 로그와 메트릭을 남기고 다음 건을 처리한다.

### 결제 실패와 재결제 (DECIDED, 2026-11-12)

카드 한도 초과처럼 흔한 실패 한 번으로 한정 재고를 잃지 않게 한다. 재고 점유의 상한은 예약 기한(`expires_at`)이 그대로 정한다.

- 결제 실패가 확정된 시각이 예약 기한 전이면 재고를 유지하고 예약을 `RESERVED`로 돌린다. 사용자는 기한 안에 다시 결제할 수 있다.
- 기한과 같거나 뒤에 실패가 확정되면 재고를 반환한다.
- 기한 안에 다시 결제하지 않으면 일반 만료 작업이 예약을 `EXPIRED`로 닫고 재고를 반환한다.
- 다시 결제하면 새 결제 시도(새 `payments` 행, 새 `paymentId`)가 생긴다. 시도마다 새 멱등성 키를 쓴다.
- 결과가 불명확한 시도가 있는 동안에는 다시 결제할 수 없다 (공통 결제의 "대상당 진행 중인 시도 1건" UNIQUE). 이중 결제를 막는다.
- 승인 시작 판정: 예약 행을 잠근 뒤 읽은 현재 시각이 기한 전이어야 한다. 받아들인 시도는 승인이 기한 뒤에 확인되어도 확정한다.
  PG 승인 시각(`approvedAt`)으로 기한을 다시 판정하지 않는다 ([ADR-0003 4절](../../decisions/0003-payment-module-boundary.md#4-개정-시도-문맥과-환불-종류-2026-11-12)).
- 예약은 승인 시작을 받아들인 시도의 `paymentId`를 기록한다. 그 시도가 아닌 결제 결과로는 예약과 재고를 바꾸지 않는다 (INV-15).
  승인 결과를 거절해 보상 취소(`COMPENSATING`)로 보내는 것도 현재 시도가 승인 진행 중일 때만이다. 오래된 시도의 승인은 예약을 바꾸지 않고 거절한다.
- 재결제 중에도 구매 슬롯은 같은 예약이 계속 점유한다 (INV-05).

## 9. 배송지 정책

- 회원은 기본 배송지를 가질 수 있다 (Nullable).
- 배송·결제 페이지에서 기본값을 불러오고, 주문마다 수정할 수 있다.
- 구매 당시 배송지는 Order의 불변 스냅샷으로 저장한다.
- 회원 주소가 바뀌어도 기존 주문 스냅샷은 바뀌지 않는다.

## 10. 환불 정책

- 전액 환불을 지원한다.
- 실제 배송이 없으므로 배송 완료 상태는 필수가 아니다.
- PG 취소가 확정된 뒤 재고를 복원한다.
- 같은 결제의 중복 환불을 막는다.
- 재고 복원은 정확히 한 번만 한다.
- 환불 확인 중에는 순판매 수량을 유지한다.

환불 종류에 따라 되돌리는 재고가 다르다 ([ADR-0003 4절](../../decisions/0003-payment-module-boundary.md#4-개정-시도-문맥과-환불-종류-2026-11-12)).

| 종류 | 예약 | 재고 | 주문 |
|---|---|---|---|
| 손님 환불 (`CUSTOMER_REFUND`) | CONFIRMED → RESTORED | sold -1, available +1 | REFUNDED |
| 보상 취소 (`COMPENSATION`, 승인 거절 후 PG 취소) | COMPENSATING → RELEASED | reserved -1, available +1 | CANCELLED |

종류와 예약 상태가 맞지 않으면 재고를 바꾸지 않고 오류 로그와 메트릭을 남긴다 (운영 확인 대상).
현재 시도가 아닌 결제의 보상 취소 완료도 같은 경로(`drop.payment.result{result=anomaly}`)로 기록한다. 오래된 시도의 승인을 거절해 보상 취소가 정상으로 끝난 경우도 여기에 포함되므로, 이 메트릭은 "확인 필요"이지 "오류 확정"이 아니다.

PG가 손님 환불을 최종 거절하면 주문은 `REFUND_REVIEW`가 되고 판매 재고는 그대로다. 손님은 다시 환불을 요청할 수 있다 (`REFUND_REVIEW` → `PAID` → `REFUND_PENDING`, 한 트랜잭션, DECIDED 2026-11-13).

## 11. 탈퇴 제한 (PROPOSED, 2026-11-14 계약 반영, #41)

`WithdrawalGuard` 드롭 구현(`hasActiveParticipation(userId)`)으로 진행 중인 거래가 있는 회원의 탈퇴를 막는다 (`member/application/WithdrawalGuard.java`).
등록된 Guard가 없으면 결제 진행 중인 회원도 탈퇴할 수 있으므로 드롭 구매 흐름 구현 때 함께 넣는다 (#41).

막는다 (`true`):

- 재고 점유 `RESERVED`, `CONFIRMING`, `RECONCILING`, `COMPENSATING` (재고를 점유하거나 결제 결과를 기다림)
- 주문 `PAYMENT_REVIEW`, `REFUND_PENDING`, `REFUND_REVIEW` (돈의 행방을 확정하지 않음)

막지 않는다: 실제 배송이 없으므로 `PAID` 주문(점유 `CONFIRMED`)은 탈퇴를 막지 않는다. 끝난 점유(`EXPIRED`, `RELEASED`, `RESTORED`)와 주문(`CANCELLED`, `REFUNDED`)도 막지 않는다. 기준: [API 계약](../../contracts/api/drop.md) "회원 탈퇴 제한".
