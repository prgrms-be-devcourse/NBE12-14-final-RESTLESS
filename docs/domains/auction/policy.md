# Auction 정책

> 관련 코드: `backend/src/main/java/com/restless/auction/`, `backend/src/main/java/com/restless/credit/`
>
> 마지막 확인: 2026-11-26 (#316 크레딧 충전, #484 11/26 부하 측정 결과 반영)

담당자: 천종원. 원본은 [design.md](design.md)이고, 이 문서는 원본에 1차 구현 결정을 더한 구현 기준이다.

## 1. 개요

주최자(판매자)가 물품을 경매에 등록하고, 회원은 현재 최고가를 보면서 더 높은 금액으로 입찰한다. 경매 한 건에는 물품 하나가 있고, 종료 시점의 최고 입찰자 한 명이 자기 입찰 금액으로 낙찰받는다. 대금은 미리 받은 크레딧에서 차감한다.

| 항목 | 결정 |
|---|---|
| 경매 방식 | 최고가를 공개하는 가격 상승형 경쟁 경매 |
| 낙찰 금액 | 낙찰자가 직접 낸 최종 입찰 금액 |
| 운영 | 여러 경매를 동시에 운영한다 |
| 동시 참여 | 사용 가능 크레딧 범위에서 여러 경매에 입찰할 수 있다 |
| 결제 | 크레딧을 입찰 때 확보하고 낙찰 때 차감한다 |
| 개발 순서 | 기능 구현 → 병목 측정 → 고도화 |

## 2. 1차 구현 범위

1차 목표는 **다른 도메인과 연동하지 않고 경매만** 완성하는 것이다.

| 포함 | 제외 (DEFERRED) |
|---|---|
| 경매 등록, 시작 전 수정·삭제 | 티켓 소유자 입장 조건 (`access_policy`는 `ALL`만 받는다) |
| 목록, 상세, 결과, 내 입찰 조회 | 공연 연결 (`performance_id`, `required_performance_id`는 받지 않고 NULL) |
| 입찰, 크레딧 확보·해제, 종료 시각 연장 | 경매 이미지 (`auction_images` 테이블은 쓰지 않는다) |
| 시작·종료 스케줄러, 낙찰 확정, 크레딧 차감 | 충전 크레딧 환불 |
| 테스트용 크레딧 지급, PG 결제로 크레딧 충전 (#316) | 입찰 전체 내역 화면, 서버 여러 대 사이 실시간 전달 |
| SSE 실시간 전달 | |

## 3. 역할과 권한

| 역할 | 뜻 | 경매에서 할 수 있는 일 |
|---|---|---|
| `USER` | 일반 회원 | 조회, 입찰, 크레딧 |
| `ORGANIZER` | 주최자(판매자) | USER 권한 + 경매 등록, 자기 경매 수정·삭제 |
| `ADMIN` | 시스템 관리자 | 모든 권한. 다른 주최자의 경매도 수정·삭제할 수 있다 |

- `ORGANIZER` 역할은 회원 모듈에 있다. 가입하면 `USER`이고, `ORGANIZER`와 `ADMIN`은 DB에서 직접 지정한다.
- 등록, 수정, 삭제는 같은 `/api/auctions` 경로를 쓰고 Spring Security에서 역할로 막는다. 프론트가 버튼을 숨기는 것과 별개로 서버가 막는다.
- 자기 경매인지(`seller_user_id`)는 Security가 아니라 서비스 코드에서 확인한다.
- **경매 API는 조회와 실시간 스트림을 포함해 모두 로그인이 필요하다.** 비로그인 사용자는 경매 화면에 들어올 수 없다.
- 현재 `SecurityConfig.PUBLIC_GET_PATHS`에는 경매 조회 경로(`/api/auctions`, `/api/auctions/*`, `/api/auctions/*/bids`, `/api/auctions/*/result`)가 공개로 들어 있다. 이 경로를 공개 목록에서 빼는 작업은 인증 담당(홍승연)이 한다. 반영되기 전까지는 API를 직접 호출하면 로그인 없이 조회된다 (9절).

## 4. 경매 등록, 수정, 삭제

| 항목 | 규칙 |
|---|---|
| 입력 | 제목, 물품 이름, 물품 설명, 시작가, 최소 인상액, 시작 시각, 종료 시각, 연장 시간 |
| 시작가 | 1 이상 |
| 최소 인상액 | 1 이상 |
| 일정 | 등록 시점보다 뒤에 시작하고, 시작 시각 < 종료 시각 |
| 연장 시간 | 기본 60초. 판매자가 30초 ~ 300초 사이로 정할 수 있다 |
| 입장 조건 | 1차는 전체 회원(`ALL`)만 |
| 수정 | 시작 전(`지금 < starts_at`)에만, 본인 또는 ADMIN. 등록 때 받은 항목을 모두 바꿀 수 있다 |
| 삭제 | 시작 전에만, 본인 또는 ADMIN. 시작 전에는 입찰과 크레딧 확보가 있을 수 없으므로 행을 실제로 지운다 |

등록하면 `base_ends_at`과 `ends_at`은 둘 다 입력한 종료 시각이다. `base_ends_at`은 바뀌지 않고, `ends_at`만 연장으로 늘어난다.

## 5. 입찰

| 항목 | 규칙 |
|---|---|
| 입찰 가능 시각 | `starts_at <= 지금 < ends_at`. 상태 컬럼이 아니라 시각으로 판단한다 (6절) |
| 첫 입찰 | 시작가 이상 |
| 다음 입찰 | 현재 최고가 + 최소 인상액 이상 |
| 금액 입력 | 사용자가 직접 입력한다. 서버가 금액을 자동으로 올리지 않는다 |
| 판매자 | 자기 경매에 입찰할 수 없다 |
| 현재 최고 입찰자 | 같은 경매에 다시 입찰할 수 없다 |
| 크레딧 | 사용 가능 크레딧이 입찰 금액 이상이어야 한다 |
| 취소 | 수락된 입찰은 취소할 수 없다 |
| 화면 이탈, 연결 끊김 | 입찰 효력과 크레딧 확보에 영향이 없다 |
| 추월 | 추월된 입찰 기록은 남기고, 확보한 크레딧만 해제한다 |
| 중복 요청 | 같은 회원이 같은 `Idempotency-Key`로 다시 보내면 처음 결과를 그대로 돌려준다. 입찰, 확보, 연장을 다시 하지 않는다. 키는 회원별로 유일하다 |
| 키 재사용 | 같은 키로 다른 경매나 다른 금액을 보내면 `IDEMPOTENCY_KEY_CONFLICT`로 거절한다 |
| 거절된 요청의 재시도 | 거절된 입찰은 저장하지 않으므로, 같은 키로 다시 보내면 새 요청으로 다시 판단한다 (예: 크레딧 부족으로 거절된 뒤 크레딧을 받고 재시도하면 수락될 수 있다) |
| 거절 응답 | 금액 부족으로 거절하면 그 시점의 최소 입찰 가능 금액을 함께 돌려준다 |

동시에 같은 금액이 여러 건 오면 경매 행 잠금 순서상 먼저 처리된 한 건만 수락된다. 앞사람보다 충분히 높은 금액은 같이 몰려 와도 차례대로 수락된다.

수락된 입찰은 모두 `auction_bids`에 저장한다. 거절된 입찰은 저장하지 않는다.

## 6. 시작, 종료, 연장

**연장:** 종료 전에 수락된 입찰마다 종료 시각을 다시 계산한다. 횟수와 총 연장 시간에는 상한이 없다.

```text
새 종료 시각 = max(현재 종료 시각, 입찰 수락 시각 + 연장 시간)
```

예시 (연장 시간 1분):

| 입찰 수락 시각 | 기존 종료 시각 | 새 종료 시각 |
|---|---|---|
| 05:00 | 10:00 | 10:00 |
| 09:30 | 10:00 | 10:30 |
| 10:20 | 10:30 | 11:20 |

거절된 입찰과 중복 요청은 연장하지 않는다.

**상태 갱신:** 스케줄러가 1초마다 다음을 처리한다.

- `starts_at`이 지난 경매를 `SCHEDULED → OPEN`으로 바꾼다.
- `ends_at`이 지난 경매를 종료한다.

입찰 수락 여부는 시각으로 판단하므로, 스케줄러가 늦어도 종료 시각 이후의 입찰은 거절된다. 상태 컬럼은 목록 표시와 종료 처리 여부를 기록하는 데 쓴다.

**종료:**

- 입찰이 없으면 유찰(`UNSOLD`) 결과를 남긴다.
- 입찰이 있으면 최고 입찰자의 낙찰(`SOLD`)로 확정하고, 그 입찰의 확보 크레딧을 차감한다.
- 실시간 전달이나 알림에 실패해도 이미 확정된 낙찰은 취소하지 않는다.

## 7. 크레딧

```text
사용 가능 크레딧 = 보유 크레딧(balance) − 묶인 크레딧(reserved)
```

| 사건 | 보유 | 묶인 금액 |
|---|---|---|
| 지급 (테스트 지급, 충전 승인) | + 금액 | 변화 없음 |
| 입찰 수락 | 변화 없음 | + 입찰 금액 |
| 추월당함 | 변화 없음 | − 그 입찰 금액 |
| 낙찰 확정 | − 낙찰 금액 | − 낙찰 금액 |

예시:

| 상황 | 보유 | 묶인 금액 | 사용 가능 |
|---|---|---|---|
| 최초 | 100,000 | 0 | 100,000 |
| A 경매에 60,000 입찰 | 100,000 | 60,000 | 40,000 |
| B 경매에 30,000 입찰 | 100,000 | 90,000 | 10,000 |
| A 경매에서 다른 사람이 최고가 갱신 | 100,000 | 30,000 | 70,000 |
| B 경매에서 30,000에 낙찰 | 70,000 | 0 | 70,000 |

- 크레딧은 1차에서 경매에서만 쓴다.
- 지갑은 회원당 하나다. 지갑이 없는 회원의 사용 가능 크레딧은 0으로 본다.
- **테스트용 지급:** 로그인 회원이 버튼 한 번에 10,000을 받는다. 횟수 제한과 중복 방지는 없다 (누를 때마다 지급). 운영(prod) 프로필에서는 이 API를 등록하지 않으므로 404가 된다.
- 모든 변동은 `credit_transactions`에 한 번씩 기록한다.

### 7.1 충전 (PG 결제, #316)

회원이 공통 결제 모듈로 결제하면 그 금액만큼 크레딧을 받는다. 결제 대상 종류는 `CREDIT_CHARGE`이고, 결제 대상은 충전 주문(`credit_charges`)이다.

| 항목 | 결정 |
|---|---|
| 환산 | 1원 = 1크레딧 |
| 금액 | 1,000 이상 1,000,000 이하, 1,000 단위. 서버는 금액만 받는다 |
| 고정 상품 | 10,000 / 50,000 / 100,000. 프론트의 금액 바로가기일 뿐 서버에 상품표는 없다 |
| 결제 기한 | 충전 주문 생성 후 30분. 지나면 결제 준비가 `PAYMENT_WINDOW_EXPIRED`이고, 새 충전 주문을 만든다 |
| 승인 | 승인된 결제는 기한과 상관없이 **항상** 지급한다. 받을 자원이 한정돼 있지 않으므로 돈을 받고 거절하지 않는다 |
| 실패, 결과 불명확 | 지급하지 않고 충전 주문은 `READY`로 둔다. 불명확한 결제가 나중에 승인으로 확인되면 그때 지급한다 (결과를 모르는 것을 실패로 보지 않는다) |
| 중복 | 같은 회원·같은 `Idempotency-Key`는 충전 주문 하나다. 충전 주문 하나는 한 번만 지급된다 (INV-AU-12, INV-AU-16) |
| 환불 | 불가. 손님 환불 요청은 결제 모듈 기본값 `REFUND_NOT_SUPPORTED`로 거절된다 |
| 테스트 지급 | 그대로 둔다 (위 "테스트용 지급") |

```text
충전 주문 READY ──(결제 승인 확인, 지급)──▶ PAID
```

흐름: `POST /api/me/credit-charges`로 충전 주문 생성 → `POST /api/payments`(`payableType = CREDIT_CHARGE`)로 결제 준비 → 결제창 → `POST /api/payments/confirm` → 승인되면 결제 모듈이 크레딧 모듈의 결제 결과 처리기를 불러 지갑에 지급한다. 계약은 [auction.md](../../contracts/api/auction.md) "크레딧 충전"과 [payment.md](../../contracts/api/payment.md).

## 8. 실시간 전달

| 항목 | 결정 |
|---|---|
| 방식 | SSE (`GET /api/auctions/{auctionId}/stream`). 입찰은 일반 `POST`로 받는다 |
| 인증 | 로그인 필요. 브라우저 기본 `EventSource`는 `Authorization` 헤더를 붙일 수 없으므로, 프론트는 헤더를 붙일 수 있는 fetch 기반 SSE 클라이언트(예: `@microsoft/fetch-event-source`)를 쓴다. 토큰을 URL에 넣지 않는다 (서버·프록시 로그에 남음) |
| 공개 범위 | 최고 입찰자의 닉네임, 금액, 시각은 로그인한 회원 모두에게 보인다 |
| 보내는 내용 | 최신 상태 하나: 상태, 현재 최고 입찰(닉네임, 금액, 시각), 최소 입찰 가능 금액, 종료 시각, 종료 결과, `revision` |
| 보내는 간격 | 경매별로 변경을 모아 0.2초마다 최신 상태를 보낸다. 간격은 설정값이다 |
| 순서 | `revision`이 작거나 같은 메시지는 클라이언트가 무시한다 |
| 재접속 | 상세 API로 최신 상태를 받은 뒤 스트림을 다시 연다 |
| 실패 | 전달 실패는 로그와 메트릭으로 남긴다. 입찰과 낙찰 결과에는 영향이 없다 |
| 연결 상한 (#244) | 서버 전체 6,000개. 넘으면 새 연결만 503 `AUCTION_STREAM_BUSY`와 `Retry-After` 5초로 거절하고 기존 연결은 유지한다. 근거: 연결당 힙 약 120KB(2026-11-18 측정), 힙 한도 약 1,200MB에서 입찰 몰림용 약 300MB를 남긴다. 상한이 없을 때는 약 9,400 연결에서 앱 전체가 메모리 부족으로 종료됐다. 값은 `AUCTION_STREAM_MAX_CONNECTIONS`로 바꾼다. 2026-11-26 측정(서버 1대)으로 유지를 확인했다: 관전 6,000에 입찰 8,000이 겹쳐도 재시작·메모리 부족이 없고 GC 직후 힙 바닥이 약 840MB로 한도까지 약 300MB가 남았다. 연결당 메모리는 121KiB이고 그중 약 72%가 Tomcat 버퍼다 |
| 연결 유지 신호 (#447) | 15초마다 모든 연결에 주석 줄을 보낸다. 서버는 써 봐야 떠난 클라이언트를 알 수 있어, 입찰이 없는 경매에서도 떠난 연결을 약 15~30초 안에 정리한다 (2026-11-26: 끊은 연결 2,000개가 24.5초 만에 0). 네트워크가 갑자기 끊겨 종료 신호가 없는 연결은 운영체제 재전송 한도나 30분 연결 유지 시간까지 남을 수 있다 |

화면에는 현재 최고 입찰 하나만 보여 준다.

## 9. 미결정 (OPEN)

| 항목 | 상태 |
|---|---|
| 경매 조회 경로를 `SecurityConfig.PUBLIC_GET_PATHS`에서 제외 | 인증 담당(홍승연) 작업. 아직 반영되지 않아 목록·상세·결과 조회는 토큰 없이도 응답한다 (`/api/auctions/*/bids` GET은 API가 없다). 공통 계약 `auth.md`(인증 규칙)의 공개 경로 설명도 함께 고쳐야 한다 |
| 탈퇴 회원 처리 | 일부 정함. 탈퇴한 회원의 쓰기 요청(입찰, 경매 등록·수정·삭제 등)은 공통 필터가 404 `MEMBER_NOT_FOUND`로 막는다 (#380, perf 프로필에서는 끔). 경매용 `WithdrawalGuard`가 없어 크레딧이 묶인 최고 입찰자나 진행 중 경매의 판매자도 탈퇴할 수 있다. 탈퇴 회원 닉네임 표시도 정하지 않았다 |
| 주최자 API 경로 | 공통 계약은 주최자 기능을 `/api/organizer/**` 아래에 두라고 하지만, 경매 등록·수정·삭제는 `/api/auctions`에서 메서드와 역할로 막는다 (3절). 옮길지 팀과 정한다 |
| 티켓 소유자 입장 조건, 입장 후 티켓 취소 시 처리 | 2차, 티켓팅 담당과 합의 |
| 공연 취소 시 연결된 경매 처리 | 2차 |
| 낙찰 후 거래 처리 (배송, 판매자 정산, 환불) | 1차에 없음. 범위 미정 (design.md 12절) |
| 서버 여러 대일 때 실시간 전달과 스케줄러 중복 실행 | 방향만 정함 (2026-11-26, 구현 전). 입찰과 낙찰의 정확성은 지금도 DB 행 잠금이 지킨다. 다른 서버에서 받은 입찰은 SSE 전송 스레드가 관전 중인 경매의 `revision`을 DB에서 0.5초(설정값)마다 확인해 전달하고, 이 확인 결과로 그 서버의 조회 캐시도 갱신한다. 방식은 ADR로 남긴다. 스케줄러 후보 조회는 `FOR UPDATE SKIP LOCKED`로 다른 서버가 잡은 경매를 건너뛴다. 여러 대 측정으로 확인한다 |
| 경매 행 잠금에 요청이 몰릴 때의 대기 상한, DB 연결 풀 크기 | 보류. 측정함 (2026-11-18, 2026-11-20, 2026-11-26). 조회 캐시(#241)와 잠금 전 금액 확인(#242) 뒤 DB 연결 대기는 대부분 사라졌다. 2026-11-26 AU-4는 두 판 합계 사전 확인 통과 60, 금액 부족 거절 17,633으로 잠금 줄에 선 입찰은 60건뿐이었고, DB 연결을 얻는 데 최대 0.19초, 시간 초과 0이었다. 2026-11-20 10,000건 판의 대기 160은 몰림 순간 표본 하나였고 이번에는 그 순간 표본이 비어 같은 순간을 다시 보지 못했다. 금액 부족 거절도 요청 키 중복 확인으로 DB를 한 번 조회한다. 입찰만 몰릴 때 응답 p95는 8,000건 판 1.6초, 10,000건 판 3.3초다. 관전 6,000이 겹치면(AU-7) 노트북이 본 p95가 9.6초였으나 서버 처리 시간은 최대 1.05초로, 대부분 연결을 맺는 단계의 시간이었다. 대기 상한은 여러 대 측정 뒤 정한다 |
| 연결당 메모리 줄이기 | 당장 하지 않음 (2026-11-26). 상한 6,000은 실측으로 확인했다 (8절). 연결당 121KiB 중 약 72%가 Tomcat 버퍼다. 여러 대로 가면 서버당 연결이 줄어 급하지 않다. 줄인다면 전역 Tomcat 설정이 아니라 경매 SSE 응답의 버퍼만 줄인다 (다른 도메인 API에 영향이 가지 않게) |
