# Auction 정책

담당자: 천종원. 원본은 [design.md](design.md)이고, 이 문서는 원본에 1차 구현 결정을 더한 구현 기준이다.

## 1. 개요

주최자(판매자)가 물품을 경매에 등록하고, 회원은 현재 최고가를 보면서 더 높은 금액으로 입찰한다. 경매 한 건에는 물품 하나가 있고, 종료 시점의 최고 입찰자 한 명이 자기 입찰 금액으로 낙찰받는다. 대금은 미리 받은 크레딧에서 차감한다.

| 항목 | 결정 |
|---|---|
| 경매 방식 | 최고가를 공개하는 가격 상승형 경쟁 경매 |
| 낙찰 금액 | 낙찰자가 직접 낸 최종 입찰 금액 |
| 운영 | 여러 경매를 동시에 운영한다 |
| 동시 참여 | 사용 가능 크레딧 범위에서 여러 경매에 입찰할 수 있다 |
| 결제 | 크레딧을 입찰 때 확보하고 낙찰 때 차감한다 |
| 개발 순서 | 기능 구현 → 병목 측정 → 고도화 |

## 2. 1차 구현 범위

1차 목표는 **다른 도메인과 연동하지 않고 경매만** 완성하는 것이다.

| 포함 | 제외 (DEFERRED) |
|---|---|
| 경매 등록, 시작 전 수정·삭제 | 티켓 소유자 입장 조건 (`access_policy`는 `ALL`만 받는다) |
| 목록, 상세, 결과, 내 입찰 조회 | 공연 연결 (`performance_id`, `required_performance_id`는 받지 않고 NULL) |
| 입찰, 크레딧 확보·해제, 종료 시각 연장 | 경매 이미지 (`auction_images` 테이블은 쓰지 않는다) |
| 시작·종료 스케줄러, 낙찰 확정, 크레딧 차감 | PG 결제로 크레딧 구매 (결제 모듈에 `PayableType` 추가 필요, 결제 담당과 합의) |
| 테스트용 크레딧 지급 | 입찰 전체 내역 화면, 서버 여러 대 사이 실시간 전달 |
| SSE 실시간 전달 | |

## 3. 역할과 권한

| 역할 | 뜻 | 경매에서 할 수 있는 일 |
|---|---|---|
| `USER` | 일반 회원 | 조회, 입찰, 크레딧 |
| `ORGANIZER` | 주최자(판매자) | USER 권한 + 경매 등록, 자기 경매 수정·삭제 |
| `ADMIN` | 시스템 관리자 | 모든 권한. 다른 주최자의 경매도 수정·삭제할 수 있다 |

- `ORGANIZER` 역할은 회원 모듈 담당자가 추가한다. 경매 등록 구현은 이 역할이 추가된 뒤에 한다.
- 등록, 수정, 삭제는 같은 `/api/auctions` 경로를 쓰고 Spring Security에서 역할로 막는다. 프론트가 버튼을 숨기는 것과 별개로 서버가 막는다.
- 자기 경매인지(`seller_user_id`)는 Security가 아니라 서비스 코드에서 확인한다.
- 조회와 실시간 스트림은 로그인 없이 볼 수 있다. 입찰과 크레딧은 로그인이 필요하다.

## 4. 경매 등록, 수정, 삭제

| 항목 | 규칙 |
|---|---|
| 입력 | 제목, 물품 이름, 물품 설명, 시작가, 최소 인상액, 시작 시각, 종료 시각, 연장 시간 |
| 시작가 | 1 이상 |
| 최소 인상액 | 1 이상 |
| 일정 | 등록 시점보다 뒤에 시작하고, 시작 시각 < 종료 시각 |
| 연장 시간 | 기본 60초. 판매자가 30초 ~ 300초 사이로 정할 수 있다 |
| 입장 조건 | 1차는 전체 회원(`ALL`)만 |
| 수정 | 시작 전(`지금 < starts_at`)에만, 본인 또는 ADMIN. 등록 때 받은 항목을 모두 바꿀 수 있다 |
| 삭제 | 시작 전에만, 본인 또는 ADMIN. 시작 전에는 입찰과 크레딧 확보가 있을 수 없으므로 행을 실제로 지운다 |

등록하면 `base_ends_at`과 `ends_at`은 둘 다 입력한 종료 시각이다. `base_ends_at`은 바뀌지 않고, `ends_at`만 연장으로 늘어난다.

## 5. 입찰

| 항목 | 규칙 |
|---|---|
| 입찰 가능 시각 | `starts_at <= 지금 < ends_at`. 상태 컬럼이 아니라 시각으로 판단한다 (6절) |
| 첫 입찰 | 시작가 이상 |
| 다음 입찰 | 현재 최고가 + 최소 인상액 이상 |
| 금액 입력 | 사용자가 직접 입력한다. 서버가 금액을 자동으로 올리지 않는다 |
| 판매자 | 자기 경매에 입찰할 수 없다 |
| 현재 최고 입찰자 | 같은 경매에 다시 입찰할 수 없다 |
| 크레딧 | 사용 가능 크레딧이 입찰 금액 이상이어야 한다 |
| 취소 | 수락된 입찰은 취소할 수 없다 |
| 화면 이탈, 연결 끊김 | 입찰 효력과 크레딧 확보에 영향이 없다 |
| 추월 | 추월된 입찰 기록은 남기고, 확보한 크레딧만 해제한다 |
| 중복 요청 | 같은 회원이 같은 `Idempotency-Key`로 다시 보내면 처음 결과를 그대로 돌려준다. 입찰, 확보, 연장을 다시 하지 않는다 |
| 거절 응답 | 금액 부족으로 거절하면 그 시점의 최소 입찰 가능 금액을 함께 돌려준다 |

동시에 같은 금액이 여러 건 오면 경매 행 잠금 순서상 먼저 처리된 한 건만 수락된다. 앞사람보다 충분히 높은 금액은 같이 몰려 와도 차례대로 수락된다.

수락된 입찰은 모두 `auction_bids`에 저장한다. 거절된 입찰은 저장하지 않는다.

## 6. 시작, 종료, 연장

**연장:** 종료 전에 수락된 입찰마다 종료 시각을 다시 계산한다. 횟수와 총 연장 시간에는 상한이 없다.

```text
새 종료 시각 = max(현재 종료 시각, 입찰 수락 시각 + 연장 시간)
```

예시 (연장 시간 1분):

| 입찰 수락 시각 | 기존 종료 시각 | 새 종료 시각 |
|---|---|---|
| 05:00 | 10:00 | 10:00 |
| 09:30 | 10:00 | 10:30 |
| 10:20 | 10:30 | 11:20 |

거절된 입찰과 중복 요청은 연장하지 않는다.

**상태 갱신:** 스케줄러가 1초마다 다음을 처리한다.

- `starts_at`이 지난 경매를 `SCHEDULED → OPEN`으로 바꾼다.
- `ends_at`이 지난 경매를 종료한다.

입찰 수락 여부는 시각으로 판단하므로, 스케줄러가 늦어도 종료 시각 이후의 입찰은 거절된다. 상태 컬럼은 목록 표시와 종료 처리 여부를 기록하는 데 쓴다.

**종료:**

- 입찰이 없으면 미낙찰(`NO_BID`) 결과를 남긴다.
- 입찰이 있으면 최고 입찰자를 낙찰(`WON`)로 확정하고, 그 입찰의 확보 크레딧을 차감한다.
- 실시간 전달이나 알림에 실패해도 이미 확정된 낙찰은 취소하지 않는다.

## 7. 크레딧

```text
사용 가능 크레딧 = 보유 크레딧(balance) − 묶인 크레딧(reserved)
```

| 사건 | 보유 | 묶인 금액 |
|---|---|---|
| 지급 | + 금액 | 변화 없음 |
| 입찰 수락 | 변화 없음 | + 입찰 금액 |
| 추월당함 | 변화 없음 | − 그 입찰 금액 |
| 낙찰 확정 | − 낙찰 금액 | − 낙찰 금액 |

예시:

| 상황 | 보유 | 묶인 금액 | 사용 가능 |
|---|---|---|---|
| 최초 | 100,000 | 0 | 100,000 |
| A 경매에 60,000 입찰 | 100,000 | 60,000 | 40,000 |
| B 경매에 30,000 입찰 | 100,000 | 90,000 | 10,000 |
| A 경매에서 다른 사람이 최고가 갱신 | 100,000 | 30,000 | 70,000 |
| B 경매에서 30,000에 낙찰 | 70,000 | 0 | 70,000 |

- 크레딧은 1차에서 경매에서만 쓴다.
- 지갑은 회원당 하나다. 지갑이 없는 회원의 사용 가능 크레딧은 0으로 본다.
- **테스트용 지급:** 버튼 한 번에 10,000을 지급한다. 횟수 제한은 없다. 운영(prod) 프로필에서는 이 API를 비활성화한다.
- 모든 변동은 `credit_transactions`에 한 번씩 기록한다.

## 8. 실시간 전달

| 항목 | 결정 |
|---|---|
| 방식 | SSE (`GET /api/auctions/{auctionId}/stream`). 입찰은 일반 `POST`로 받는다 |
| 보내는 내용 | 최신 상태 하나: 상태, 현재 최고 입찰(닉네임, 금액, 시각), 최소 입찰 가능 금액, 종료 시각, 종료 결과, `revision` |
| 보내는 간격 | 경매별로 변경을 모아 0.2초마다 최신 상태를 보낸다. 간격은 설정값이다 |
| 순서 | `revision`이 작거나 같은 메시지는 클라이언트가 무시한다 |
| 재접속 | 상세 API로 최신 상태를 받은 뒤 스트림을 다시 연다 |
| 실패 | 전달 실패는 로그와 메트릭으로 남긴다. 입찰과 낙찰 결과에는 영향이 없다 |

화면에는 현재 최고 입찰 하나만 보여 준다.

## 9. 미결정 (OPEN)

| 항목 | 상태 |
|---|---|
| 티켓 소유자 입장 조건, 입장 후 티켓 취소 시 처리 | 2차, 티켓팅 담당과 합의 |
| 공연 취소 시 연결된 경매 처리 | 2차 |
| PG로 크레딧 구매 | 2차, 결제 담당과 합의 |
| 서버 여러 대일 때 실시간 전달과 스케줄러 중복 실행 | 단일 서버 측정 후 |
| 경매 행 잠금에 요청이 몰릴 때의 대기 상한, DB 연결 풀 크기 | 8단계 측정 후 |
