# 경매 1차 구현 평가

- 기준일: 2026-11-15, dev `f672b52` (#131까지)
- 대조 대상: 원본 명세 [design.md](design.md), 담당자 목표, 구현 기준 문서([policy.md](policy.md) 등), 코드와 테스트
- 범위: 1차 구현 0~7단계. 8단계(측정)는 아직 하지 않았으므로 성능 관련 항목은 "8단계"로 표시한다.

## 1. 결론

1차 범위의 기능은 모두 구현됐고, 처음 세운 세 목표 중 두 개는 테스트로 확인된다. **"낙찰 결과와 크레딧 차감의 일치"는 구현은 됐지만 중간 실패를 넣어 확인하는 테스트가 없다.** 8단계 전에 이 테스트를 채우는 것을 권한다 (5절).

| 표시 | 뜻 |
|---|---|
| ✅ | 구현과 테스트가 모두 있음 |
| 🟡 | 구현은 있으나 테스트가 부족하거나 일부만 충족 |
| ⏸ | 1차에서 의도적으로 제외 (policy.md 2절) |
| ❓ | 정책 미정 |

## 3. 원본 명세 대조

### 3.1 기능 요구사항 (design.md 2절)

| 기능 | 결과 | 구현 / 비고 |
|---|---|---|
| 경매 등록 | ✅ | `POST /api/auctions`. 입장 조건은 `ALL`만 (⏸ 티켓 소유자) |
| 경매 목록 조회 (진행 중, 예정, 종료) | ✅ | `GET /api/auctions?status=` 상태별 정렬 |
| 경매 상세 조회 | ✅ | 물품, 현재 최고가, 최소 입찰 가능 금액, 종료 시각, `revision` |

| 내 입찰 조회 | ✅ | `GET /api/me/bids`. 경매별 마지막 입찰, `HIGHEST`/`OUTBID`/`WON`, 경매 상태 |
| 재접속 (최신 경매 상태와 **자신의 입찰 상태** 복원) | 🟡 | 경매 상태는 상세 API와 SSE 첫 메시지로 복원된다. 자신의 입찰 상태는 `GET /api/me/bids` 목록에서 찾아야 하고, 특정 경매 하나의 내 상태를 바로 주는 API는 없다 |

### 3.5 원본의 미결정 사항 (design.md 12절)

| 항목 | 1차 결정 |
|---|---|
| 연장 시간 | 기본 60초, 판매자가 30 ~ 300초로 설정 |
| 경매 일정 | 등록 시점보다 뒤에 시작, 시작 < 종료. 최대 진행 시간 제한 없음 |
| 가격 범위 | 시작가·최소 인상액 1 이상. 최대 입찰 금액은 따로 두지 않고 사용 가능 크레딧이 상한 |
| 등록 권한 | `ORGANIZER` 역할(DB 지정)과 `ADMIN` |
| 수정 및 취소 | 시작 전에만 수정·삭제(실제 삭제). 진행 중 취소와 운영자 강제 종료는 없음 |
| 티켓 자격 | ⏸ 2차 |
| 공개 정보 | 현재 최고 입찰자의 닉네임·금액·시각만 로그인 회원에게 공개. 입찰 전체 내역은 공개하지 않음 |
| 초기 크레딧 지급 | 버튼당 10,000, 횟수·보유 한도 없음, prod에는 없음 |
| 거래 후속 처리 (배송, 정산, 환불) | 1차에 없음. 범위 미정 ([policy.md](policy.md) 9절) |
| 기술 구조 | MySQL 행 잠금으로 직렬화, SSE 실시간 전달, 커밋 후 이벤트, 단일 서버 |

## 4. 원본과 다르게 정한 것

원본을 바꾼 것이 아니라 원본이 열어 둔 부분을 정한 것이다. 이유는 각 문서에 있다.

- 입찰 상태는 저장하지 않고 계산한다 (state-machines.md 2절).
- 유찰도 결과 행(`UNSOLD`)으로 남긴다 (`V20261112_1045`).
- 크레딧은 `com.restless.credit` 패키지로 분리했다.
- 원본 7절의 입찰 순서(크레딧 확인 → 확보 → 저장)와 달리, 확보 행이 입찰 ID를 가리키므로 입찰을 먼저 저장하고 확보한다. 한 트랜잭션이라 결과는 같다 (transactions.md TX-AU-2).
