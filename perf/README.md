# 부하 테스트

EXP-01~04([성능 실험 계획](../docs/testing/performance.md))를 실행하는 도구를 둔다. 결과(원자료, 보고서)는 각자 PC의 `.ai-output/perf/<날짜>-<실험>/`에 측정 조건과 함께 남기고 레포에 올리지 않는다.

| 폴더 | 내용 |
|---|---|
| [seed/](seed/README.md) | 실험 입력 데이터. 빈 스키마에 대량 시드, 토큰 CSV, 정합성 점검 |
| [scenarios/](scenarios/README.md) | k6 시나리오. EXP-01 드롭 재고 점유 스파이크, 계단식 용량 측정 |
| [ec2/](ec2/README.md) | 배포 서버를 perf로 빌리는 순서와 명령. 시드, 토큰 전달, 정리, DB 프로브 (`db-probe.sh`). 서버 두 대 측정은 [실행 절차 7절](../docs/testing/drop-performance-procedure.md#7-alb-멀티-인스턴스-측정) |

## 원칙

- 실제 MySQL을 쓴다. H2나 Mock DB는 쓰지 않는다. 결제 PG만 앱의 가짜 PG(`perf` 프로필)를 쓴다. 실제 토스 API에는 부하를 주지 않는다.
- 쓰기 경합(재고 점유, 좌석 선점, 응모, 입찰)을 읽기보다 먼저 본다. 정합성 위반 0건이 P0다.
- 시드는 한 벌만 만들고 스냅샷으로 남긴다. 실험마다 복원해서 데이터 오염 없이 비교한다.
- 한 비교에서는 변수 하나만 바꾼다.

## 실행 환경

팀 AWS 한도는 승인 없이 EC2 1대(medium 이하)와 RDS 1대(small 이하)다. 부하 테스트 전용 서버를 따로 두지 않고 배포 서버를 테스트 시간에만 빌려 쓴다. 판정 회차의 k6는 앱 서버와 같은 리전, 같은 서브넷의 EC2에서 보낸다. 노트북 k6는 축소 시드 진단에만 쓴다.

| 구성 | 테스트 중 | 평소 |
|---|---|---|
| 앱 (EC2 t3.small) | `SPRING_PROFILES_ACTIVE=perf`. 가짜 PG, 관리 포트 8081 | `prod` |
| DB (RDS MySQL small) | 같은 인스턴스의 `perf-restless` 데이터베이스 | 배포 데이터베이스 |
| 부하 발생기 | 같은 서브넷 EC2의 k6. 노트북은 축소 시드 진단만 | 없음 |

- 배포 서버는 실제 운영이 아닌 포트폴리오 데모라서 테스트 시간 동안 느려져도 된다.
- 시드는 `perf-restless`에만 넣는다. 배포 데이터베이스와 섞지 않는다.
- `prod` 프로필은 토스를 호출하므로 그대로 부하를 주지 않는다. 테스트 중에는 반드시 `perf` 프로필로 띄운다.
- 시나리오는 `perf-`로 시작하는 호스트만 허용한다. 부하 발생기 `/etc/hosts`에 `perf-app`을 EC2 주소로 등록하고 `BASE_URL=http://perf-app:8080`, `PERF_ALLOWED_APP_HOSTS=perf-app`으로 실행한다.
- 시드는 호스트나 DB 이름에 prod가 들어 있으면 멈춘다. RDS 식별자에 prod를 넣지 않는다.
- 보안 그룹은 8080과 8081을 부하 발생기 IP에만 연다. 부하 발생기 EC2의 공인 IP는 시작할 때마다 바뀌므로 시작한 뒤 규칙을 확인한다. RDS 3306은 EC2 보안 그룹에만 열고, 시드를 넣을 때만 내 IP를 잠시 추가한다.
- t3는 버스터블이다. 테스트하는 동안만 크레딧 사양을 무제한으로 두고 끝나면 표준으로 되돌린다. 보고서에 CPU 크레딧 잔량을 함께 기록한다.
- 테스트 중에는 자동 배포를 멈추고 perf 컨테이너를 `restless-perf` 이름으로 띄운다 ([deploy/ec2](../deploy/ec2/README.md#부하-테스트와-함께-쓰기)).

### perf 전용 기간

2026-11-18에 시작했다. 처음에는 2026-11-30에 끝낼 계획이었지만 연장했고, 종료일은 아직 정하지 않았다.

이 기간에는 EC2를 배포 서버로 되돌리지 않는다. 테스트가 끝날 때마다 prod로 바꾸는 절차를 없애려는 운영 규칙이다. 프로필, yml, 스크립트는 그대로다.

- 테스트가 끝나도 `perf-ec2.sh finish`를 실행하지 않는다. 자동 배포는 멈춘 채로 둔다.
- 끝낸 사람은 perf.env에서 실험용으로 바꾼 값을 되돌리고 추가한 줄은 지운다. 대기열(`RESTLESS_DROP_QUEUE_REQUIRED`)은 운영과 같게 `true`로 둔다.
- 예약 경로 용량 측정과 순간 몰림 측정(`drop-reservation-capacity.js`, `drop-reservation-spike.js`)만 대기열을 끄고 돌린다. 끝나면 `true`로 되돌린다.
- 다음 사람은 자기 perf.env 값과 DB로 `start`부터 한다. `start`가 남아 있는 `restless-perf`를 바꿔 띄운다.
- 기간 중에는 데모 사이트가 열리지 않고 dev 머지가 서버에 반영되지 않는다.
- 기간이 끝나는 날에 `finish`를 한 번 실행해 배포 컨테이너로 되돌린다. 종료일이 정해지면 이 절에 적는다.

### 이 환경에서 믿을 수 있는 것

- 정합성 위반 0건과 같은 환경에서의 개선 전후 비교는 유효하다.
- 지연은 서버 지표(8081의 `http.server.requests`)로 본다. 노트북 k6 지연에는 집 네트워크 왕복이 섞이므로 사용자 체감값으로만 기록한다.
- RPS와 P95 절대값은 앱 사양, DB 사양, 부하 발생기 위치를 붙여서만 쓴다.
- 비교는 같은 부하 발생기 위치에서 한다. 노트북으로 진단할 때는 같은 장소, 같은 네트워크에서 하고 가능하면 유선으로 연결한다. 테스트 전 서버까지 왕복 지연을 기록한다.

### 부하 발생기 위치

판정 회차의 k6는 앱 서버와 같은 리전, 같은 서브넷의 EC2에서 돌린다. 노트북 k6는 축소 시드로 진단할 때만 쓰고 그 결과로 합격과 실패를 판정하지 않는다. 규칙과 근거는 [측정 규약 4절](../docs/testing/drop-performance-measurement.md#4-수집과-실행-유효성)에 있다.

- 2026-11-27 오전 노트북 k6 회차에서 TCP 연결 시간이 1, 2, 3, 4초로 뛰는 SYN 재전송 모양이 나타나 회차가 무너졌다. ALB 노드 두 개와 ALB를 거치지 않는 EC2 SSH 대상이 같은 순간에 함께 느려져 원인은 노트북이나 집 네트워크였다.
- 같은 서브넷의 m7g.xlarge로 옮긴 뒤 연결 p95는 36ms에서 1ms로 줄었다. 참여자 10,000명에 k6 메모리 약 6.9GB, CPU 5 ~ 30%를 썼다.
- 부하 발생기 EC2의 공인 IP는 시작할 때마다 바뀐다. 시작한 뒤 보안 그룹 규칙을 확인한다.
- 노트북 진단 회차에는 macOS 임시 포트 범위와 TCP MSL 사전 검사를 그대로 한다 ([실행 절차 7-2절](../docs/testing/drop-performance-procedure.md#7-2-서버별-지표-수집과-k6)).

### 부하 발생기를 EC2로 옮기는 기준

서버에는 여유가 있는데 k6 결과만 나빠지면 부하 발생기가 병목이다. 노트북 진단 회차에서 아래 신호가 보이면 같은 서브넷의 EC2로 옮긴다. EC2 부하 발생기에서도 같은 값을 기록해서, 결과가 서버 한계인지 부하 발생기 한계인지 근거를 남긴다.

- `dropped_iterations`가 쌓이거나 목표 도착률을 채우지 못한다.
- 테스트 중 부하 발생기 CPU가 80~90%를 넘거나 메모리가 모자란다.
- k6 P95는 오르는데 서버 지표의 P95와 서버 CPU는 낮다.
- `http_req_connecting`, `http_req_blocked`가 크거나 연결 오류가 나는데 서버 로그에는 오류가 없다.
- 같은 조건 두 번의 결과 차이가 개선 폭보다 크다.

### 판정 회차에 돌리는 것

판정 회차에는 앱 서버에서 vmstat(1초)만 돌린다. DB 통계는 판매 직전과 판매 시작 약 20초 뒤에 한 번씩 DB 호스트에서 읽는다. 잠금 대기 폴링, 짧은 간격의 문장 폴링, CPU 프로파일러는 진단 회차에서만 쓰고, 진단 회차는 판정에 쓰지 않는다. 2026-11-28 앱 서버 한 대에서 0.2 ~ 1초마다 mysql 클라이언트를 띄우는 수집기가 그 서버만 2.5 ~ 3.5배 느리게 만들고 전체 p95를 끌어올렸다.

서버가 여러 대면 회차마다 서버별 점유와 승인 p95(R1), 판매 전 CPU(R2)로 유효성을 검사한다. 무효면 한 번 다시 돌린다. 정의는 [측정 규약 4절](../docs/testing/drop-performance-measurement.md#4-수집과-실행-유효성)에 있다.

## 목표 수치 (미측정)

아래는 일반 가이드에서 가져온 출발점이다. 우리 시스템에서 측정한 값이 아니다. 드롭의 목표는 [성능 개선 계획 1절](../docs/testing/drop-performance-plan.md#1-목표)을 따른다.

| 항목 | 목표 |
|---|---|
| 처리량 | 1,000~10,000 RPS, 동시 접속 약 1만 |
| 지연 | P95 500ms 이하, 읽기는 100ms 미만 지향 |
| 자원 | CPU 80% 미만, 앱과 DB 따로 측정 |

## 진행 방식

병목 하나를 풀고 다음 병목으로 넘어간다 ([성능 상위 계획 3절](../docs/testing/performance.md#3-반복-방법)).

1. 측정해서 병목을 찾는다.
2. 원인을 확인하고 그 병목 하나만 고친다. 매번 정합성 위반 0건을 확인한다.
3. 같은 조건으로 다시 측정해 전후를 비교한다.
4. 다음 병목을 찾는다.

쓰기 병목을 먼저 푼다. 읽기 측정과 읽기와 쓰기를 섞은 측정은 쓰기 병목을 푼 뒤 다음 병목 후보로 다룬다.
