# 부하 테스트

EXP-01~04([성능 실험 계획](../docs/testing/performance.md))를 실행하는 도구를 둔다. 결과 요약은 [docs/reports/](../docs/reports/)에 측정 조건과 함께 남긴다.

| 폴더 | 내용 |
|---|---|
| [seed/](seed/README.md) | 실험 입력 데이터. 빈 스키마에 대량 시드, 토큰 CSV, 정합성 점검 |
| scenarios/ | k6 시나리오. 아직 없다 |

## 원칙

- 실제 MySQL을 쓴다. H2나 Mock DB는 쓰지 않는다. 결제 PG만 앱의 가짜 PG(`perf` 프로필)를 쓴다. 실제 토스 API에는 부하를 주지 않는다.
- 쓰기 경합(재고 점유, 좌석 선점, 응모, 입찰)을 읽기보다 먼저 본다. 정합성 위반 0건이 P0다.
- 시드는 한 벌만 만들고 스냅샷으로 남긴다. 실험마다 복원해서 데이터 오염 없이 비교한다.
- 한 비교에서는 변수 하나만 바꾼다.

## 실행 환경

앱, DB, k6를 EC2 3대에 나눈다. 같은 VPC, 같은 AZ에 두고 버스터블(t 계열) 인스턴스는 쓰지 않는다.
사양은 출발점일 뿐 아직 측정하지 않았다. 첫 실행에서 앱과 DB 각각의 CPU, 커넥션 수, 락 대기를 기록하고 증설 여부를 정한다.
DB를 RDS로 할지 EC2에 직접 설치할지는 아직 정하지 않았다. 시드 도구는 어느 쪽이든 같고 스냅샷 절차만 다르다 ([seed/README.md](seed/README.md#스냅샷과-복원)).

## 목표 수치 (미측정)

아래는 일반 가이드에서 가져온 출발점이다. 우리 시스템에서 측정한 값이 아니다. 성능 실험 계획 2절의 TBD는 팀 확인 전에는 바꾸지 않는다.

| 항목 | 목표 |
|---|---|
| 처리량 | 1,000~10,000 RPS, 동시 접속 약 1만 |
| 지연 | P95 500ms 이하, 읽기는 100ms 미만 지향 |
| 자원 | CPU 80% 미만, 앱과 DB 따로 측정 |

## 실험 순서

1. 쓰기 단독 측정으로 기준선을 잡는다.
2. 쓰기를 개선한다. 변수 하나씩 바꾸고 매번 정합성 위반 0건을 확인한다.
3. 읽기 단독 측정
4. 읽기 개선
5. 혼합 시나리오 검증. 읽기와 쓰기 지표를 같은 화면에서 본다.
